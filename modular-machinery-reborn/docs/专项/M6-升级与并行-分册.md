> 本文件是 `移植方案-v2.md` 第 4 节 **M6 · 升级与并行体系（R）** 的展开分册，产生于 M6 开工前的勘测。
> 目标：让实现者不必重读旧版源码即可动手，并把 M6 拆成可独立验证的子里程碑。

> 旧版源码**只读**：本项目的结论是 1.12.2 的渲染/组件/线程栈不可平移（`移植方案-v2.md:62`），只有语义与数值可以照抄。

## 0. 一句话结论

M6 在旧版里**不是一个功能，而是三套互相咬合的系统**：升级（数据 + 物品 + 总线）提供"往机器里插东西"，
并行（并行控制器 + 逐需求并行上限）提供"同时跑几份"，工厂（多线程控制器）提供"一个控制器跑多条不同配方"。
三者共享同一个 `RecipeModifier`（配方修改器）与 `RecipeThread`（配方运行状态）抽象。
因此拆分必须让**数据层先行**：升级与修改器都是数据，方块与线程都是消费者。

### 1.4 并行的实际执行：逐需求上限，而不是线程

**这一条是本分册最重要的发现：旧版的"并行"不是一个线程池，而是一个数值缩减过程。**

- `TileMultiblockMachineController.getMaxParallelism()`（`TileMultiblockMachineController.java:293-304`）：
  `machine.getInternalParallelism()` 起底，累加结构里每个并行控制器的 `getParallelism()`，超过
  `machine.getMaxParallelism()` 就截断，最后 `Math.max(1, …)`。
- `TileMultiblockMachineController.isParallelized()`（`:322-328`）= `machine.isParallelizable() && getMaxParallelism() > 1`。
- `RecipeCraftingContext.getMaxParallelism(parallelizable)`（`RecipeCraftingContext.java:434-455`）：
  从 `activeRecipe.getMaxParallelism()` 起，对每个"可并行需求"取
  `Math.min(当前值, requirement.getMaxParallelism(组件副本, context, 当前值))`，一旦 ≤0 立即返回 0。
- 每个需求类型自己实现这个上限：`RequirementItem:273`、`RequirementFluid:153`、`RequirementFluidPerTick:92`、
  `RequirementEnergy:119`、`RequirementGas:107`、`RequirementGasPerTick:81`、`RequirementIngredientArray:182`、
  `RequirementCatalyst:64`、`RequirementItemDurability:63`。
- 入口是 `canStartCrafting()`（`:466-478`）：只有当配方是 parallelized 且 `maxParallelism > 1` 且
  **所有当前组件都可并行**时才走并行分支，否则退回 `canStartCrafting(true)`。
- `ActiveMachineRecipe` 持有 `maxParallelism` / `parallelism`（`ActiveMachineRecipe.java:43`），
  `setMaxParallelism` 由 `MachineRecipeThread.tryRestartRecipe`（`MachineRecipeThread.java:85`）与
  `FactoryRecipeThread.tryRestartRecipe`（`FactoryRecipeThread.java:144`）喂入。

**并行的"线程"只出现在工厂系统里**：`FactoryRecipeThread` 的类注释自己写明
「不是真正意义上的线程 / Not a thread in the true sense of the word」（`:33-38`）。
它是一条**独立的配方运行状态槽**，工厂控制器按 `maxThreads` 数量持有它们
（`AbstractMachine.maxThreads`，默认 `Config.defaultFactoryMaxThread = 20`，`Config.java:47`）。

因此"并行"与"工厂多线程"是**两件不同的事**，必须分片实现：
并行 = 同一条配方同时结算 N 份；工厂 = 同时跑 N 条不同配方。

### M6a · 升级数据层（**已实施**，0.18.0）

- 交付：升级类型与注册表、数据包/配置目录声明格式、物品 → 升级映射、加载期校验与告警。
- 不做：物品能力、方块、界面、配方修改器求值、并行。
- 验收：放一份声明文件 → `/reload` 后注册表里有它；写坏字段 → 日志给出**该写什么**的错误；
  未知机器名与未知物品 id → 告警而不是静默。
- 为什么第一：升级总线（M6b）需要一个"升级是什么"的答案才能做槽位与兼容性；
  升级携带的修改器（M6c）也需要它。它是纯数据层，无方块、无渲染，风险最低。

### M6b · 升级总线（能力 + 方块 + 界面）

- 依赖：**M6a**。理由：总线的槽位只存"有升级声明的物品"，兼容性判定来自 `UpgradeType`，
  自定义 NBT 的 key 是升级名。
- 交付：`MachineUpgrade` 实例层（固定/动态两种）、物品能力（`AttachCapabilitiesEvent<ItemStack>`）、
  物品 tooltip、升级总线方块（5 级）+ BE + 容器 + 界面（`guiupgradebus.png`，176×213，
  文本 0.72 起点 (92,23)，滚动条 156/17/106，槽位 (8,17) 每行 3 个）、破坏喷出库存。
- 不改控制器逻辑：总线只是"被结构扫描到的组件"。
- 验收：把升级物品放进总线槽 → 界面按原版行序列出"Nx 升级名 / 可否兼容警告"；
  破坏总线 → 升级物品掉落；世界重载 → 槽位与总线自定义 NBT 保持。
- 风险：**"总线如何知道它属于哪台机器"没有现成机制**。本项目 `HatchCollection` 只认
  `MachineHatchBlockEntity`（`MachineControllerBlockEntity.java:228-239`），总线不是仓口。
  旧版靠 `MachineComponentTile` 接口 + 结构扫描。本项目需要给控制器加一条"收集总线"的路径
  （见第 4 节）。

### M6c · 配方修改器 + 并行上限计算（**解锁 3 项已登记的阻塞**）

- 依赖：无（只依赖 M2 的配方引擎）。可与 M6b 并行。
- 交付：
  1. `RecipeModifier` 求值 —— 加到 `MachineRecipe` 的 `canStart/start/canTick/tick/canFinish/finish`
     每一条上（数值路径），并在 JEI 与 tooltip 里反映；
  2. 机器 JSON 的 `modifiers` 真正求值（结构位置 → 修改器生效）；
  3. 机器定义上的 `internal-parallelism` / `max-parallelism` / `parallelizable` 三个字段；
  4. 并行上限计算 —— 每个需求实现自己的上限，按旧版 `getMaxParallelism` 取最小值；
  5. 控制器 GUI 的**并行度两行**（`gui.controller.parallelism` / `max_parallelism`，旧版
     `GuiMachineController.java:145-154`，**仅当 parallelism > 1 才显示**）；
  6. 预览「机器信息」按钮的**内置并行数 / 最大并行数**两行（key 已存在）；
  7. 控制器 GUI 的**性能尾行**（`Avg: %sμs/t (Search: %sms), WorkMode: %s`，旧版 `:157-172`）
     —— 需要 `TimeRecorder` 等价物（`TileMultiblockMachineController.usedTimeAvg()` / `recipeSearchUsedTimeAvg()`，`:273-279`）。
- **这就是解锁那三项已登记阻塞的那一片**：
  | 已登记阻塞 | 出处 | 由本片的哪一项解锁 |
  |---|---|---|
  | 控制器 GUI 并行度行 | `移植方案-v2.md:352`（M4a 未做）、`:407`、`交接文档.md:191` | 第 5 项 |

- 验收：搭一台带并行控制器（M6d 之前可先用配置给机器写死并行数）的机器 →
  一次开工同时扣 N 份输入、一次完工产出 N 份；`alloy_furnace` 控制器上方换通风口 → 产出翻倍；
  控制器界面出现并行度两行与性能尾行；预览按钮出现并行数两行。
- 为什么排在 M6b 之后而在 M6d 之前：并行上限是纯数值，不需要任何新方块就能验证
  （用机器字段把 `maxParallelism` 直接设成 >1 即可）。先做它，才有资格判断并行控制器是否接对。

### M6d · 并行控制器 + 智能接口

- 依赖：**M6c**（不然 `parallelism` 改了没人读）。
- 交付：并行控制器方块（5 级，4/16/64/256/512）+ BE + `parallelism` 网络包 + 界面

  并行数被夹在 `[0, max]`；世界重载后保持；结构里取走控制器 → 并行数回落。

### M6e · 工厂控制器（多线程引擎 + 界面）

- 依赖：**M6d**（工厂并行度来自 `getAvailableParallelism()`，它按当前并行占用扣减，
  旧版 `TileFactoryController.java:400-417`）。
- 交付：`RecipeThread` 等价物（本项目自研，**不是**平移旧版 292 行）、线程槽模型
  （core thread / 普通 thread / `idleTime` / `recipeSet`）、工厂控制器方块 + BE + 界面
  （`guifactory.png` 280×213 + `guifactoryelements.png`）、`max-threads` 机器字段、
  以及 D8 留给 M6 的**每机器工厂控制器方块** `<机器名>_factory_controller`
  （`移植方案-v2.md:119` 与 `交接文档.md:177` 都把它记在 M6）。
- 关于「每机器工厂控制器」：它需要 `has-factory` / `factory-only` 求值，而这两个字段
  必须在**构造期**可知才能注册方块——和 D8 的绑定控制器是同一个约束。因此它落在 M6e
  的最后一步：`has-factory: true` 的机器声明要在配置目录里，构造期扫描后注册
  `<机器名>_factory_controller`。这是 M6 唯一会动注册表的切片。
- 验收：工厂控制器界面按原版列出"线程 #N / 运行中 / 最大线程数"；一条线程一份配方；
  核心线程按名字持久化；拆卸结构后线程回收。
- 这是 M6 最重的一片：旧版相关代码 292+152+291+99 = 834 行，加 `TileFactoryController` 约 660 行
  与 `GuiFactoryController` 约 380 行。**规模评估见 §6。**

### 排序理由汇总

1. **M6a 必须第一**：三类消费者（总线、修改器、工厂线程）都需要"升级是什么"的定义；
   而且它是唯一**不含任何运行时行为**的切片，出错代价最低。
2. **M6c 早于 M6d**：并行上限是数值，无需新方块即可验证；反之若先做控制器方块，
   没有任何东西读 `parallelism`，验收只能靠"数字显示出来了"——那属于方案第 5 节明令
   不可作为完成证据的弱标准（`移植方案-v2.md:433-438`）。
3. **M6c 与 M6b 可并行**：二者互不依赖（一个走配方数值，一个走物品能力与方块）。
4. **M6e 必须最后**：它是唯一同时依赖并行上限（M6d）与"多线程"抽象（自研）的切片，
   且是唯一动注册表的切片。

## 3. 数据模型设计

### 3.1 与旧版的根本差别

| 维度 | 旧版 | 本项目 |
|---|---|---|
| 升级定义从哪来 | CraftTweaker 脚本在运行时 `new UpgradeType(...)` 并注册 | **数据包 + 配置目录的 JSON**（D3/D9/D10 的同一路线） |
| 升级等级 | `UpgradeType` 是普通 class，`level` 字段**无消费者** | 保留字段但同样只解析（不假装它有语义） |
| 并行/总线等级 | 两套硬编码枚举（`:9-14`） | 见 §3.4：本项目**应做成数据字段**，但这属 M6c/M6b，本片不做 |
| 机器兼容性 | `Set<DynamicMachine>`（对象引用，构造后填充） | `Set<ResourceLocation>`（**注册名**），按名比较 |

**为什么换成注册名**：旧版能持有 `DynamicMachine` 对象，是因为机器定义在它的注册表冻结之前就已加载
（`RegistryUpgrade` 的表在脚本加载时填充）。本项目 M1 起机器定义来自数据包（`移植方案-v2.md:75`），
`/reload` 之后**对象会被整体替换**（`MachineRegistry.replace(loaded)`，`MachineLoader.java:91`），
持有对象引用必然指到上一代实例。注册名是稳定的。

**这一点也是本项目必须偏离旧版的第一处**，明确记录：旧版 `UpgradeType.addCompatibleMachine` 会
立刻拿机器对象（`UpgradeType.java:31-36`），本项目**声明期只写名字**，解析放到加载期之后
（`UpgradeLoader` 第二遍），并且**未知机器名只告警不报错**——因为升级声明与机器定义可能来自
不同的数据包，顺序无法保证。这与 `MachineLoader.java:106-113` 对"有控制器无定义"的处理一致。

### 3.2 声明格式（M6a 已实施）

**升级类型**：`data/<命名空间>/upgrade/<名字>.json` 或 `config/modular_machinery_reborn/upgrade/<名字>.json`

```json
{
  "name": "modular_machinery_reborn:example_speed",
  "localizedname": "Example Speed Upgrade",
  "level": 1.5,
  "max-stack": 16,
  "dynamic": false,
  "compatible-machines": ["modular_machinery_reborn:alloy_furnace"],
  "incompatible-machines": [],
  "descriptions": ["Machine tooltip line one.", "Machine tooltip line two."]
}
```

| 字段 | 必填 | 缺省 | 语义 |
|---|---|---|---|
| `name` | **是** | — | 升级的唯一 id。可写全限定，也可只写路径（补本模组命名空间） |
| `localizedname` | 否 | `name` 的路径 | 显示名。**若存在同名语言键 `<ns>.<path>` 则以语言键为准**——与 `MachineDefinition.displayName()` 同一套（`MachineDefinition.java:45-47`） |
| `level` | 否 | `0` | 旧版 `UpgradeType.level`。旧版无消费者，本项目**如实只解析**并在注释里写明 |
| `max-stack` | 否 | `1` | 单个升级物品可叠加的份数，必须 ≥1 |
| `dynamic` | 否 | `false` | `true` = 每份升级在物品上带自己的 NBT（旧版 `DynamicMachineUpgrade`）；`false` = 全部状态在总线上（旧版 `SimpleMachineUpgrade`） |
| `compatible-machines` | 否 | 空 | **白名单**。非空则只对这些机器生效 |
| `incompatible-machines` | 否 | 空 | **黑名单**。白名单为空时生效。两者同时非空 → **加载报错**（旧版 `UpgradeType.java:31-43` 会在运行时抛，本项目提前到加载期） |
| `descriptions` | 否 | 空 | 升级物品 tooltip 的附加行（旧版 `SimpleMachineUpgrade.descriptions`，`SimpleMachineUpgrade.java:38-40`） |

**物品 → 升级映射**：同名目录下的 `<名字>.item.json`

```json
{
  "upgrade": "modular_machinery_reborn:example_speed",
  "item": "minecraft:golden_axe"
}
```

| 字段 | 必填 | 语义 |
|---|---|---|
| `upgrade` | **是** | 引用一份升级声明的 `name`（同一批或上一次加载的均可）。找不到 → **报错**（数据自相矛盾，必须出声） |
| `item` | **是** | 物品注册名。**加载期必须已注册**，否则报错——这与 `ModRecipeSerializers` 对未知流体的处理一致（`ModRecipeSerializers.java:136-138`） |

**为什么物品映射也要数据驱动**：旧版用 CraftTweaker 的 `registerSupportedItem` /
`addFixedUpgrade`（`MachineUpgradeHelper.java:28-53`）。本项目没有 CraftTweaker，
若不外置，包作者就永远无法给自己的物品挂升级——这正是 D9 对机器定义解决的问题，
在升级上必须用同一条路线。

### 3.3 第 3.2 节的两条设计取舍（记录理由）

1. **物品映射不放进 `UpgradeType`**。旧版是两张分离的表（`RegistryUpgrade.UPGRADES` 与
   `ITEM_UPGRADES`，`RegistryUpgrade.java:20-21`），本项目保持分离，好处是
   **一个升级可以挂在多个物品上**，且物品映射可以单独 reload。
2. **`dynamic` 是布尔而不是两个类**。旧版用继承（`SimpleMachineUpgrade` vs
   `SimpleDynamicMachineUpgrade`）。本项目 M6a 只是数据层，没有"实例"这个概念，
   一个布尔足够表达"NBT 存在物品上还是总线上"；到 M6b 需要真实例时再分成两个类。
   **这是一处有意的简化，不是遗漏**。

### 3.4 并行等级数值该放哪（M6b/M6d 的前置决定，本片不做）

旧版是两套硬编码枚举加配置文件覆盖（`ParallelControllerData.java:23-29`、`UpgradeBusData.java:23-29`）。
本项目的既有惯例是**一切数值来自数据或配置**。建议（M6d 采用）：

- 方块等级**必须**是编译期常量（方块注册不可延后，D8 已论证），所以等级枚举本身留在代码里；
- 但**每一级的数值**应从配置读，并保留旧版默认：并行 4/16/64/256/512，总线槽位 3/6/9/12/18；
- 机器自身的 `max-parallelism`（旧版 `Config.maxMachineParallelism = 2048`，`Config.java:46`）
  与 `internal-parallelism` 应作为**机器 JSON 的根字段**——这是本项目对旧版的**第二处有意偏离**。
  理由：旧版只能靠 CraftTweaker 的 `MachineModifier.setMaxParallelism`（`MachineModifier.java:43-53`）
  改它，而数据包作者没有脚本能力。把这两个字段放进机器定义，正好补上
  `MachineLoader.UNIMPLEMENTED_ROOT_FIELDS`（`MachineLoader.java:242-245`）里
  `has-factory` 一族的位置，也符合 D3 的"字段与旧版对齐"原则。

> **需要项目所有者确认的第二处偏离**：给机器 JSON 增加 `max-parallelism` / `internal-parallelism` /
> `parallelizable` 三个**旧版 schema 里不存在**的根字段。旧版对应物是 CraftTweaker 的
> `MachineModifier`，不是 JSON。若不接受，退路是只给配置目录机器读这三个字段（但那样数据包机器
> 就永远无法并行）。

### 3.5 为什么 M6a 不含物品能力（`CapabilityUpgrade`）

旧版 `CapabilityUpgrade` 的 NBT 形状是「key = 升级名，value = 该升级的 NBT」
（`CapabilityUpgrade.java:47-75`），而 upgrade 实例（`MachineUpgrade`）只存在于运行时。
本项目 M6a **不引入实例层**，所以：

- 本片交付的是 `UpgradeTarget`（"这个物品被声明成某升级的载体"）这个**声明**，
  它已经足够回答"这个物品是不是升级载体"（M6b 做槽位过滤时的唯一问题）；
- 实例层（固定/动态两类的 `MachineUpgrade` 等价物、NBT 读写、能力挂载）整体移到 **M6b**，
  因为它的唯一消费者是总线槽位与物品 tooltip。

这是本片范围裁剪的唯一实质决定，写在这里以便复核。

## 5. 风险与未知

### 5.1 线程（本分册最需要警惕的一点）

现有引擎**完全没有线程，也没有线程安全的意识**：

- `MachineControllerBlockEntity.tick`（`MachineControllerBlockEntity.java:83-166`）是服务端主线程里
  一个纯粹的"读进度 → 扣资源 → 写进度"序列，状态只有 `progress` / `maxProgress` /
  `activeRecipeId` 三个标量（`:55-72`）。
- 没有 `RecipeThread` 等价物，没有 `RecipeCraftingContext`，没有上下文池。
- 配方匹配是**遍历** `level.getRecipeManager().getAllRecipesFor(...)`（`:219`），
  取第一个 `canStart` 通过的——旧版有 `RecipeSearchTask` 在 ForkJoin 池里跑搜索并带超时
  （`RecipeThread.java:105-138`、`:150-166`）。

这对 M6 的含义：

| 切片 | 线程风险 | 判断 |
|---|---|---|
| M6a | 无 | 纯数据，reload 在服务端主线程 |
| M6b | 低 | 总线 tick 的 `boundedMachine` 清理（旧版 20 tick 一次）可在主线程做；但 `TileUpgradeBus` 的 `synchronized (this)` / `synchronized (parentBus)`（`TileUpgradeBus.java:94`、`UpgradeMachineEventHandler.java:41`）在无并发时是**多余**的——本项目**不要照抄锁**，否则只会制造"以为有并发"的错觉 |
| M6c | **中** | 并行上限计算本身是纯函数；但"一个 tick 结算 N 份"会让 `HatchCollection` 的每次模拟/扣减开销 ×N。本项目没有 `RecipeCraftingContextPool`，必须自己决定是"循环 N 次"还是"一次性按 N 倍数量算"。**旧版的做法是后者**（需求按数量整体扣，见 `RecipeCraftingContext`），本项目若照抄需小心不要漏掉"任一条不满足则整体不成立"的语义 |
| M6d | 低 | 只改一个 int，但**本项目没有自定义网络包**（`交接文档.md:83`：流体仓交互走菜单按钮）。要么引入第一个 `SimpleChannel`，要么把并行数塞进菜单的 `ContainerData`（`MachineControllerMenu` 已有 `ContainerData`，`交接文档.md:42`）。**建议后者**——不改网络层，风险最小 |
| M6e | **高** | 这是真正需要并发/异步的切片：旧版用 ForkJoinTask 跑配方搜索。本项目的机器 tick 是同步的，工厂要么退化为"主线程顺序跑 N 条线程槽"（无并发、可接受、语义等价），要么引入真正的异步（要重做状态可见性与持久化）。**建议 M6e 第一版明确做成"顺序多槽"**，并在文档里说明这不是并发实现 |

### 5.2 其它风险

| 风险 | 说明 | 对策 |
|---|---|---|
| **总线归属无现成机制** | 见 M6b 说明。项目里只有仓口会被"结构扫描"收集 | 新增一条收集路径；**不要**把总线伪装成仓口（会污染 `HatchKind` 与结构可接受方块） |
| **升级声明的机器名可能先于机器定义** | 数据包加载顺序不保证 | 未知机器名**告警**而非报错（已实施） |
| **物品 id 未注册** | 数据包可以在 mod 之外卸载 | 报错并给出"物品注册名必须已注册"的提示（已实施） |
| **`UpgradeType.level` 没有语义** | 旧版注释自己写着"暂无作用" | 如实只解析，注释写明，**不要**给它编一个语义 |
| **`modifiers` 与升级的修改器同类型不同来源** | 两处都会用 `RecipeModifier` | M6c 一次性把两者的求值路径分开实现，不要合并成一条 |
| **工厂方块必须构造期注册** | 与 D8 同源 | `has-factory` 机器的声明必须落在配置目录；文档明说 |
| **旧版 `Config` 里的并行/线程默认值** | `maxMachineParallelism=2048`、`defaultFactoryMaxThread=20`、`machineParallelizeEnabledByDefault=true`、`enableFactoryControllerByDefault=false`（`Config.java:38-47`） | M6c/M6d/M6e 采用同一组默认值，不要另编 |
| **`guifactory.png` 是 280×213 实体尺寸** | 不是 256 图集切片 | blit 时必须显式给源宽高（`移植方案-v2.md:208`） |

### 5.3 未验证事项（明确标注）

1. **`UpgradeType.level` 的真实用途**：旧版源码里找不到消费者，但可能存在
