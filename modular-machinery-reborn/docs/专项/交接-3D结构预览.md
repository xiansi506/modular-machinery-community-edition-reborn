## 0.9 结构预览按钮从不触发：JEI 的输入坐标空间（0.17.1 已修）

**这是一条值得记住的 JEI 陷阱，不是本模组的普通 bug。**

`RecipeLayoutInputHandler.handleInput` 会**先减 `RecipeLayout.getRect()`，再减 handler 自己 `getArea()` 的原点**，然后才把坐标交给 handler：

```
 23: localX = mouseX - rect.getX()
 91: MathUtil.contains(area, localX, localY)     // area 在配方局部空间判定
104: x = localX - area.getPosition().getX()      // ← 连自己的 area 原点也减
134: handler.handleInput(x, y, input)
```

而 `IRecipeCategory.draw` / `getTooltip` **只减 `RecipeLayout.getRect()`**，拿到的是普通配方局部坐标。

**所以 `getArea()` 不只是命中过滤范围，它还是 handler 的坐标原点。** 当 `getArea()` 返回视口矩形 `(6, 26, 172, 150)` 时，面板收到的每个鼠标位置都平移了 **−(6, 26)**：按钮带相对点击位置上移 26px，没有按钮被 arm；平移后的按压仍落在视口带内，于是 `mousePressed` 落到视口兜底返回**误导性的 true**，释放时无按钮可触发返回 **false**。而 **hover tooltip 正常**，因为 `getTooltip` 走的是未平移的面板空间——**这个「悬停正常、点击失效」的分裂症状就是本陷阱的指纹**。

**修法**：`getArea()` 返回**整面板** `(0, 0, PANEL_WIDTH, PANEL_HEIGHT)`，让输入与绘制共用同一原点；区域语义改由面板自身的 `isOverPreview`/`contains` 判断。

**排查这类问题的方法**：日志同时打印**收到的 y** 与**目标元素的 y 区间**，一眼就能看出平移量。

## 0.7 已确认的根因之三：投影 Y 轴缩放的负号（0.15.4）

### 症状
用户报告：**JEI 里的模型是倒过来的**，并且**方块渲染还是有问题**。**两个症状，一个符号。**

### 推导

```java
// GameRenderer 的 GUI 正交投影：
setOrtho(0, width, height, 0, 1000, 21000)     // bottom = height, top = 0
// ⇒ GUI y=0 映射到 NDC +1 ⇒ GUI 的 NDC 里 +Y 本来就指向屏幕上方
```

而透视矩阵产出的也是标准 +Y 向上的 NDC。**两者约定一致，所以垂直轴应当乘一个正数。**
那个 viewport 里却是：

```java
viewport.m00(boxPixels / guiWidth);
viewport.m11(-boxPixels / guiHeight);   // ← 多翻了一次
```

**一个符号造成两件事：**

1. **画面垂直镜像** → 模型上下颠倒。
2. **投影行列式变负** → **三角形绕序被镜像**。方块 RenderType 开启背面剔除，
   于是**被剔除的是正面**，留下的是远侧内表面 → **方块显示自己的内部** → 「像被挖空」。

判定线索：`m00` 为正而 `m11` 为负，**这种不对称本身就不合理**——一致的映射不会只翻一个轴。

### 修复

```java
viewport.m11(boxPixels / guiHeight);
```

`m31`（把框心放到面板中心）在 +Y-up 约定下本来就是对的，**未改动**。

### 为什么这次能直接定位
前两次（法线、光方向）都只能靠反汇编 + 对照截图逐步排除；这次**纯靠读约定与符号**即可判定，
因为「GUI NDC 的 Y 朝上」在 `GameRenderer` 的 `setOrtho` 参数里写得很明白，而且
`m00`/`m11` 的正负不一致本身就是强烈的可疑信号。

## 0.5 已确认的根因：光照用错了 API（证据链完整）

### 症状
同一组方块，**JEI 预览里比游戏世界里明显偏暗**，亮暗分布读起来像「向内凹」。

### 取证过程（全部可复现）

1. **两处渲染用的光照 API 不同。**
   `javap -c` 反汇编 `LevelRenderer`：
   ```
   678: aload_1                              // renderLevel(PoseStack ...) 收到的那个 PoseStack
   679: invokevirtual PoseStack.last()
   682: invokevirtual PoseStack$Pose.pose()   // → Matrix4f
   685: invokestatic  Lighting.setupLevel(Matrix4f)
   ```
   即**地形用 `Lighting.setupLevel(变换顶点的同一个矩阵)`**；而预览用的是 `Lighting.setupFor3DItems()`。

2. **两者用的光向量其实完全相同**——反汇编 `Lighting.<clinit>`：
   ```
   DIFFUSE_LIGHT_0 = new Vector3f( 0.2, 1.0, -0.7).normalize()
   DIFFUSE_LIGHT_1 = new Vector3f(-0.2, 1.0,  0.7).normalize()
   setupLevel(m)        → RenderSystem.setupLevelDiffuseLighting(DIFFUSE_LIGHT_0, DIFFUSE_LIGHT_1, m)
   setupFor3DItems()    → RenderSystem.setupGui3DDiffuseLighting(DIFFUSE_LIGHT_0, DIFFUSE_LIGHT_1)
   ```
   **差异不在常量，而在变换矩阵。**

3. **关键差异在 `GlStateManager`**——反汇编它：
   ```java
   // setupLevelDiffuseLighting(light0, light1, matrix)
   //   → 用「传进来的 matrix」变换光向量，然后 setShaderLights

   // setupGui3DDiffuseLighting(light0, light1)   ← setupFor3DItems 走的这条
   Matrix4f m = new Matrix4f()
        .rotationYXZ(1.0821041f, 3.2375858f, 0f)     // 约 62° / 185.5°
        .rotateYXZ(-0.3926991f, 2.3561945f, 0f);     // 约 -22.5° / 135°
   setupLevelDiffuseLighting(light0, light1, m);
   ```
   **`setupFor3DItems()` 把光方向按一套写死的「GUI 物品」朝向旋转**——那是为了让背包里的物品模型看起来好看，
   **与当前相机、当前世界毫无关系**。于是每个面的漫反射项都与世界里不同，
   **顶面比游戏内暗**，亮暗关系反过来 → 看起来像被从内部照亮（"向内凹"）。

### 修复（0.15.3）

`StructurePreviewRenderer.render()` 里改为与地形同构：

```java
Matrix4f view = cameraView(cameraDistance, yaw, pitch);
pose.mulPoseMatrix(view);
...
// 地形是 Lighting.setupLevel(poseStack.last().pose())——用它变换顶点的同一个矩阵来变换光方向
Lighting.setupLevel(new Matrix4f(view).setTranslation(0.0F, 0.0F, 0.0F));
```

**必须去掉平移分量**：`setupLevelDiffuseLighting` 内部是 `matrix.transform(new Vector4f(light, 1.0f))`，
即把光向量当成 **w=1 的点**来变换；若矩阵带平移，光方向会被**平移歪**而不是被旋转。相机矩阵的平移在
GUI 像素尺度上（几十个单位）远大于光向量模长 1，所以这一点不能省。

### 为什么这条以前没被发现
§6 第 3 条曾把 `Lighting.setupFor3DItems()` 列为"未验证假设"，但当时**没有反汇编进 `GlStateManager` 看那套硬编码旋转**，
所以只停留在"可能有关系"。**能看见画面之后（对照截图）才把它确定为真凶**——这也印证了 §10 那句：请把"看一眼"当作最有力的调试工具。

## 0.6 相机/绕序问题的状态（由他人修复，已接受）

上一版实现的 `Axis.XP.rotationDegrees(180)` 用**模型空间旋转**去兼容屏幕 Y 轴，
副作用是**法线也被旋转**（顶面法线朝下）→ 顶面被按底面光照 → 同样导致"向内凹"。

现版本已改为**把 Y 翻转放进投影层**（`perspectiveProjection()` 里的 `viewport.m11(-boxPixels / guiHeight)`），
**模型保持世界坐标 +Y 向上**，投影变换不影响法线。**方向正确，予以保留。**

注意：**相机/绕序与光照是两件独立的事**——前者决定"哪个面朝哪"，后者决定"每个面的漫反射强度"。
本次只修了后者；两者都曾各自造成"向内凹"。

### 本轮重构（参考原版 `WorldSceneRendererWidget` / `BlockArray`）

当前源码已按原版语义重整：预览相机使用原版的 yaw/pitch 约定（yaw 垂直钳制、pitch 水平旋转），包围盒中心按方块中心计算，缩放按三轴对角线拟合。蓝图界面支持左键旋转、右键平移、滚轮缩放和中键复位。成分列表现在按原版 descriptive stack list 合并数量，并把控制器放在首位；JEI 底部使用真实 recipe slots，保留隐藏槽位索引，具备 JEI tooltip/focus 行为。

`StructurePreviewRenderer` 仍使用 `BlockRenderDispatcher.renderSingleBlock` 绘制方块，但相机部分已从 GUI 正交变换改为透视投影：

- 使用原版 `WorldSceneRendererWidget` 的相机约定计算 `lookAt` 矩阵；
- 模型保持世界坐标的 **+Y 向上**，不再用 `Axis.XP.rotationDegrees(180)` 把模型翻到另一侧；
- 透视画面通过 viewport 矩阵映射到 JEI/蓝图的预览框，屏幕坐标的 Y 翻转只发生在投影层，因此不会翻转模型法线；
- 临时替换全局 projection/model-view 前先 `graphics.flush()`，绘制完成后恢复 RenderSystem 状态；
- 深度范围映射到 GUI 面板前方，缩放到最大值时仍把相机保持在结构包围球外。

这套实现已离线构建成功并部署到 `D:\.minecraft\versions\彩虹花园\mods\modular_machinery_reborn-0.15.2.jar`。尚未在加载该时间戳之后的游戏日志中确认最终像素效果；若重启后仍然偏暗，应保留新截图再继续调整相机光照，而不要重新加回 180°翻转。

- 结构**大小**合适吗？太小/太大/超出面板？
- 结构有没有**画到面板外面**、或**盖住 JEI 自己的标题与翻页箭头**？
- 方块之间**遮挡**对吗？还是近处被远处穿透？
- 各**机箱变体**看起来不一样吗？还是整片同色（=代表状态没生效）？
- 整体是否**偏平、看不出立体**（=光照问题）？
- **底部方块行**：图标对不对？鼠标悬停有没有 tooltip？（§7-A）
- 机器名/文字位置对不对？
- **游戏内右键蓝图的界面**是否正常？（这是最有价值的对照实验，见下）

### 为什么"右键蓝图界面"这个对照实验最关键

两个入口走**同一个渲染器**（`StructurePreviewRenderer.render`），但**绘制上下文不同**：

| | pose | 裁剪 | 调用方 |
|---|---|---|---|
| 游戏内蓝图界面 | **未平移**（绝对屏幕坐标） | 有（`clip()`，绝对坐标正确） | 我方的 `Screen` |
| JEI 类别 | **已平移**到配方原点 | **无**（0.15.1 起刻意去掉） | JEI |

所以：

- **界面正常 + JEI 有问题** → 问题在 **JEI 绘制上下文**（pose/裁剪/缓冲/绘制时机），渲染器本身没问题。
- **两个都不正常** → 问题在**渲染器本身**（投影、绕序、光照、Z 值）。
- **界面打不开/崩溃** → 问题在**物品 `use` 逻辑或客户端类加载**，与渲染无关。

**先做这个实验，能省掉一半的排查范围。**

## 5. 已核实的 1.20.1 API 事实（不要重新踩）

全部用 `javap` 对 `forge-1.20.1-47.2.0_mapped_official_1.20.1.jar` 核实过：

| API | 结论 |
|---|---|
| `GuiGraphics.enableScissor(int,int,int,int)` | **绝对屏幕坐标，不感知 pose**（见 §1） |
| `GuiGraphics` | 有 `pose()` / `bufferSource()` / `flush()` / `enableScissor` / `disableScissor` / `renderItem(ItemStack,int,int)` / `fill(int×4,int)` / `drawCenteredString(Font,Component,int,int,int)` / `renderTooltip(Font,Component,int,int)` |
| `BlockRenderDispatcher.renderSingleBlock` | 有 5 参版 `(BlockState, PoseStack, MultiBufferSource, int, int)` 与 6 参版 `+ModelData, RenderType` |
| `Lighting` | 在 **`com.mojang.blaze3d.platform.Lighting`**（不是 `net.minecraft.client.renderer`），有 `setupFor3DItems()` / `setupForFlatItems()`；`GuiGraphics` 内部也用它们 |
| `Screen` | **只有 `renderBackground(GuiGraphics)` 一个重载**，**没有** 4 参的 `(GuiGraphics,int,int,float)`。写成 4 参会编译失败（这个坑踩过一次） |
| `Item.use` | 返回 **`InteractionResultHolder<ItemStack>`**，签名 `use(Level, Player, InteractionHand)` |
| `mouseDragged` / `mouseScrolled` | 由 `GuiEventListener` 提供 default 实现，**`Screen` 未声明**（`javap Screen` 看不到，别因此以为不能重写） |
| `DistExecutor` | 在 **fmlcore**，不在 mapped forge jar 里（`javap` 搜不到≠不存在） |
| `Matrix4f` | JOML，`m30()/m31()` 是平移分量（用于 `clip()`） |

### 5.1 由用户实测**反推**出的一条重要事实

用户报告"结构出现在预览区里了"（0.15.1）→ 说明按类别内坐标绘制**落在了正确位置** → **JEI 调用 `draw` 时确实把 pose 平移到了配方原点**。

这条之前只是推断（上一任因此不敢在 JEI 里加裁剪），现在**已被实机证实**。它直接决定了 §7-B 的可行性。

## 6. 我做过但**没有验证过**的假设 ← 最危险的部分

以下全部是**推理，不是事实**。改动/排查时请优先怀疑它们：

1. **绕 X 轴 180° 旋转是"对"的**（L98）。它把世界 +Y 正确映射到屏幕上方，且**保持三角形绕序**（负缩放会翻转绕序而方块 RenderType 开背面剔除 → 会看到错误的面）。**但它同时翻转了 Z** → 结构是从"另一侧"看的，**前后是镜像的**。这是最可能被用户察觉的视觉问题之一。
2. **正交投影 + 旋转 pose 的等轴测观感是对的**（原版用透视相机）。观感差异未经确认。
3. ~~**`Lighting.setupFor3DItems()` 是渲染方块的正确包夹**~~ —— **已证伪并修复（§0.5）**。它确实是 vanilla 给
   **物品**用的：它把光方向按一套写死的 GUI 朝向旋转（`rotationYXZ(62°, 185.5°, 0)·rotateYXZ(-22.5°, 135°, 0)`），
   与相机无关 → 预览每个面都比世界里暗。地形用的是 `Lighting.setupLevel(变换顶点的矩阵)`，0.15.3 起改为同构。
4. **`LightTexture.FULL_BRIGHT` + 依赖模型渲染器的方向性明暗**足够让立方体看得出立体。若没有方向性明暗，所有面亮度相同，结构会像一块平板。
5. **深度关系**：结构整体被推到 `z = 200 + halfSpan`，假定"GUI 里 z 越大越靠前"（依据：vanilla 把容器槽物品放在 z=100、tooltip 在 z=400）。**若这个方向搞反了，近处会被远处穿透。**
6. **拟合公式** `scale = boxPixels / (largestExtent * 1.9)` → 旋转后最长轴约占框 **0.91**，因此"不会溢出"所以 JEI 不需要裁剪。这个推算只对轴对齐的包围盒成立，**未对任意角度几何验证**。
7. **居中**用 `(min + max) / 2.0`，假定它就是视觉中心。
8. **`z` 值不会与 GUI 深度缓冲冲突**（GUi 正交投影 near=1000/far=21000、modelview 平移 −11000 的推算）。
9. **JEI 不缩放绘制用的 pose**（否则 `clip()` 的 `m30/m31` 就不是屏幕像素）。

## 7. 候选项：按可能性排序 + 判定方法 + 修法

### A. 底部方块行**没有 tooltip / 不能被 JEI 聚焦**（已在本轮重构处理）

**当前状态**：JEI 行已改成真实 recipe slots，悬停 tooltip、ingredient focus 和隐藏槽位搜索索引均由 JEI 处理；蓝图界面仍保留手工绘制，但已补充对应的方块 tooltip。若实机仍有交互问题，应先检查 JEI 版本对 `INPUT` 槽位的绘制行为。

**判定**：鼠标悬停在方块图标上——没有 tooltip 就是它。

**修法**：把可见行改成 JEI 的真实槽位（`builder.addSlot(role, x, y)` 放在可见坐标），再按需把整行居中；或保留手工绘制但自行为该区域补 `renderTooltip`。注意隐藏槽位（`HIDDEN_SLOT`）目前**专门负责 JEI 的搜索索引**，改的时候别把那个丢了。

### B. 结构**溢出面板 / 盖住 JEI 自己的 UI**

**为什么可能**：0.15.1 起 JEI 侧**刻意去掉了裁剪**。虽然 §6.6 推算不会溢出，但那是推算。另外结构被推到 **z≈200+**（很靠前），可能盖住 JEI 的标题、翻页箭头、书签按钮。

**判定**：看结构四角有没有越出暗区；看 JEI 页面箭头是否被方块遮住。

**修法**：§5.1 已证实 JEI 会平移 pose，所以**现在可以安全启用 pose 感知的 `StructurePreviewRenderer.clip()`**（L66 已实现，从 pose 读回平移）。之前不敢用是因为无法确认 pose 是否被平移，这个顾虑已消除。
**⚠️ 但有一个坑**：若 JEI 是用 `RenderSystem.enableScissor` **直接**设置裁剪（而非经 `GuiGraphics`），那么 `GuiGraphics.disableScissor()` 在自身栈为空时会**关掉 JEI 的裁剪**。启用前先确认，或改用不依赖 `GuiGraphics` 栈的做法。

### C. 结构**方向不对**（前后镜像 / 上下颠倒）

**判定**：拿一台**不对称**的机器（如合金炉、不朽花冠聚合机）看能否指出"控制器在哪一侧"。

**修法**：L98 的 `Axis.XP.rotationDegrees(180.0F)` 调换为绕 Y（`Axis.YP.rotationDegrees(180.0F)`）可只翻前后不改上下；或对 `yaw` 加 180。**注意绕序**：只有**旋转**能保绕序，**任何负缩放都会翻转绕序并让背面剔除显示错误的面**。

### D. 比例 / 居中不对

**判定**：结构是否明显偏小、偏向一角。
**修法**：`render()` 里的 `* 1.9F` 拟合系数与 `(min+max)/2.0` 中心计算（L78 起）。

### E. **光照**（主因已修，见 §0.5）

**已修（0.15.3）**：偏暗/向内凹的主因是**光方向用错了 API**——`setupFor3DItems()` 会按固定 GUI 朝向旋转光方向。
已改为 `Lighting.setupLevel(去掉平移的相机矩阵)`，与地形同构。

**仍可能存在**：`LightTexture.FULL_BRIGHT` 意味着所有面用同一张光照贴图，只靠方向性漫反射区分明暗
（原版有环境光与光照开关）。若仍觉得偏平，可考虑给每个位置算真实 `packedLight`，或保留现状。
**判定**：修完 0.15.3 后与游戏内同一结构再对照一次截图。

### F. 文字位置不对

**判定**：机器名（y=205）是否落在贴图边框上；成分行（179..197）与名字是否有重叠（0.15.2 已修掉提示文字那一处，但名字本身未验证）。
**修法**：`PreviewLayout` 里调常量。注意**面板底部区域 179..220 在原版里还塞了 `bottomMenu`(161) 与 `statusBar`**，可供参考的图面信息有限。

### G. 游戏内蓝图界面本身的问题

用户**还没试过**。开了才知道。若打不开/崩溃，问题在 `BlueprintItem.use` → `DistExecutor` → `ClientPreview.openBlueprint` 这条链，与渲染无关。

## 9. 已知限制 / 不要做的事

**已知限制**

1. **原版预览面板的按钮行没有复刻**（图层开关、重置视角、逐层 2D 视图等），它建立在原版 **422 行的 widget 框架**上。本实现只有拖动旋转 + 滚轮缩放。
2. **结构编辑工具仍是空壳**：`itemconstructtool`、`machine_projector`、`ItemDebugStruct` 已注册但无行为。
3. **专用服务器客户端上两个预览都不显示**：机器定义**未同步到客户端**，`MachineRegistry` 在那里是空的。这是项目级已知限制（控制器名、创造栏蓝图同样受影响）。
4. **光照统一**（`FULL_BRIGHT`），原版有环境光与光照开关。

**不要做的事**

- **不要把 `WorldSceneRenderer`（847 行）移植过来**。它建立在 1.12.2 的 `GlStateManager`/`Tessellator` 与假世界+区块渲染管线上，1.20.1 无法平移，而且结构预览只是每帧画几十个方块。
- **不要用负缩放翻转 Y**。会翻转三角形绕序；方块 RenderType 开背面剔除，结果是看到错误的面。要翻轴就用**旋转**。
- **不要假定 `GuiGraphics.enableScissor` 会考虑 pose**（§5）。
- **不要用 4 参的 `Screen.renderBackground`**（这个版本没有）。
- **不要把"编译通过"当成"渲染正确"**——这块的所有问题都是运行时视觉问题，编译期一律发现不了。
