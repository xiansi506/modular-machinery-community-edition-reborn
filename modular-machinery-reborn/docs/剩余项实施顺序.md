## 0. 一句话总览

**只剩两项是「真功能缺口」**（v2b 的 KJS 扩展字段、装配线依赖的可变尺寸结构），
其余是**小项**（算术、文案、配置）或**世界空间/视觉工作**（投影器、`color`、光照、机器定义同步）。
所以顺序是：**先做完那两项功能缺口与一批小项，再把所有需要眼睛的东西集中成一个波次。**

| 波 | 内容 | 数量 | 离线比例 | 互相耦合 |
|---|---|---|---|---|
| **1** | **v2b：KJS 机器定义 11 个扩展字段** | 1 项 | **高**（schema 侧已全部就绪） | 独立 |
| **2** | 小项批（升级体系 / 配置算术 / 需求文案）**三条并行轨** | 8 项 | **高** | 轨内独立；仅「失败文案」与波 6 的 `color` 抢同一文件 |
| **3** | `dynamic-patterns` → 内置**装配线 `assembly_line`** | 2 项 | 中 | 与波 4 抢 `MachineRegistry.java`，**必须串行** |
| **4** | 机器定义**同步到客户端** | 1 项 | 中 | 抢 `MachineRegistry.java`；是波 5 的接口前置 |
| **5** | **KubeJS 入口扩展**（把旧版 DSL 的形状搬进来；**不接 CraftTweaker 桥**） | 中 | **高**（纯扩 API、无新依赖） | 依赖波 1 的 schema 与波 4 的注册表形状 |
| **6** | **需要眼睛的波**：光照均匀 → `color` → 投影器 | 3 项 | **低** | 各自独立，但**不批处理** |
| **7** | 发布收口（版本号 + 文案 + 归档） | — | — | 每次发布都要做 |

**关键路径**：波 1 → 波 3 → 波 4 → 波 5 → 发布。波 2 可以**全程并行**，不占关键路径。

## 1. 波 1 · v2b：KJS 机器定义的 11 个扩展字段

**为什么第一**：`移植方案-v2.md` §9 的第 1 项，也是**唯一剩下的发布阻塞项**。
`docs/简介.md` 的「❌ 未完成」第一条就是它。

**为什么离线比例高**：11 个字段的**求值、校验、错误文案在 `MachineSchema` 里已全部就绪**，
数据包与配置目录早就在用；缺的只是 `MachineBuilderJS` 的方法面（脚本目前被
`DEFERRED_ROOT_FIELDS` **按名拒绝**）。所以这不是「实现 11 个字段」，而是
「给 11 个已经能用的字段补上脚本拼写方式」。

**唯一的技术不确定性**：脚本对象 → `JsonElement` 的转换路线（三条候选未实测）。
**动工第一步就是把它实测掉**，否则后面要返工。

- **交付物**：`MachineBuilderJS` 的新方法；`DEFERRED_ROOT_FIELDS` 清空/删除；复现器段 Z 的正向断言；
  八处文案同步；**最小实机清单**（必查 7）。
- **离机能证**：两条路径产出逐字段相同的 `MachineDefinition`；构建器不复刻 schema 校验（段 Z6 字节码断言）；
  新方法在真实 Rhino 下的解析落点（段 Z10 模板）；注入缺陷后新断言会变红。
- **必须实机**：KubeJS **真的把脚本跑起来了**（复现器 classpath 上故意没有 KubeJS 运行时）。
- **完整交接**：[`专项/交接-v2b-KJS扩展字段.md`](专项/交接-v2b-KJS扩展字段.md)（逐字段的精确 JSON 形状、
  三条硬约束、复现器要改的每一处、10 条实机清单）。
- **规模**：小—中。**版本**：`0.31.0`。

> ⚠️ **排版要求（所有者 2026-10-04 定）**：交付时把「KJS 扩展字段」从 `docs/简介.md` 的「❌ 未完成」

## 3. 波 3 · 最后一项真功能缺口：可变尺寸结构 → 装配线

**为什么排在功能缺口里**：这是**旧版有而新版无**的最后一处实质缺口——
旧版 4 台内置机器，现只移植 3 台，缺的正是 `assembly_line`。

**依赖链**：`dynamic-patterns` ──► `assembly_line`。**必须先做前者**。

### 3.1 `dynamic-patterns`（可变尺寸结构）

- **现状**：在 `MachineSchema.UNIMPLEMENTED_ROOT_FIELDS` 里，**只识别 + 告警，不求值**。
- **为什么先勘测**：`MachinePattern` 目前是「固定坐标 → 可接受方块」的映射，而动态结构是
  一组**带变量的尺寸参数**要把坐标算出来；这会牵动 `MachinePattern`、`MachineRegistry` 的匹配、
  以及**按朝向旋转**。**未勘测就动手 = M6e 的失败重演。**
- **第一步**：产出一份**短勘测/设计说明**（旧版 `MultiBlockModifierReplacement` / `DynamicModifierReplacement`
  的语义、变量从哪来、与现有 `parts` 的关系），**不写代码**。
- **离线**：中（坐标算术、变量展开、旋转可离机驱动）。
- **规模**：中—大。

### 3.2 `assembly_line`（内置装配线）

- **依赖**：3.1 完成。
- **交付物**：第 4 台内置机器（数据包定义 + 控制器声明 + 配方），并入 `example-datapack/`。
- **离线**：中（结构匹配可离机驱动）。
- **必须实机**：**结构真的能搭出来并成型**（这是「内置机器」的验收标准）。
- ⚠️ **文件冲突**：本波与波 4 的「客户端同步」都要改 `MachineRegistry.java`，**必须串行**。

## 5. 波 5 · KubeJS 入口扩展（→ 兼容层框架 → 按模组模块）

> **所有者 2026-10-04 决定**：① **M7 兼容层在项目目标内**（原先 `移植方案-v2.md` L87 的
> 「不计入主线完成度」**随之作废**）；② **「CraftTweaker 等价 API」取「扩 KubeJS 入口」这一形状**。
>
> ⚠️ **② 的含义要读准**：**不移植 CraftTweaker 桥本身**（旧版 27 文件 / 3210 行**不做**）。
> 交付的是**它的能力**——旧版脚本能写的东西，本版用 KubeJS 入口提供。
> 好处：**不新增依赖**、与 D7（给包作者一个可用入口）一致、作者只需装 KubeJS。

### 5.1 范围勘测：旧版脚本面 vs 本版 KubeJS 入口（**先做这一步**）

**规模已量过**（旧版源码实测）：桥共 **27 文件 / 3210 行**，`RecipePrimer` 一个类 **84 个 public 方法**，
另有 **10 个脚本侧 builder 类型**（`RecipeBuilder` / `MachineBuilder` / `BlockArrayBuilder` /
`RecipeAdapterBuilder` / `RecipeModifierBuilder` / `IngredientArrayBuilder` …）。
**这是旧版「脚本可写内容」的全集**，也就是本波要**用 KubeJS 表达**的目标清单。

**勘测要产出的东西**：一张「旧版能写 → 本版 KubeJS 现在能不能写」的对照表，据此分三类：
**已有** / **该补** / **有意不补**（例如适配器、只有 CT 可达的死类型）。

> **与波 1 的关系**：波 1（v2b）补的是**机器定义**那 11 个字段，
> 旧版的 `MachineBuilder` / `BlockArrayBuilder` 大体就对应它——**两者是同一目标的两半，不是重复**。
> 所以本波的重点落在**配方侧与升级声明侧**（旧版 `RecipeBuilder` / `RecipeModifierBuilder` /
> `RecipeAdapterBuilder` 对应的地方），以及 KubeJS 写法的**易用性**（旧版的 builder 链比现在的
> `{...}` 字面量更好写）。

### 5.2 兼容层框架（框架本身**离线可控**）

- **交付物**：一个 `compat/` 形态的接入层（可选依赖、模块自注册），以及**需求类型的注册表**——
  目前需求种类是 `ModRecipeSerializers` 里的**三个字符串常量 + 一个 switch**，要接兼容模块必须先把它变成**可注册**的。
- **离线**：高（框架与注册表是纯逻辑）。
- ⚠️ **依赖波 4**：兼容层要往注册表里加**方块与需求类型**，所以**必须在机器定义同步之后**，
  否则注册表接口会被改两次。

### 5.3 按模组模块（**每一个都无法离线开工**）

**已核实：本机只有 Botania 的 jar，AE2 / GregTech / TConstruct / TheOneProbe / FluxNetworks / Mekanism
全部没有。**

所以**每一个模块的第一步都是**：① 取得该模组的 1.20.1 API jar（放进 `libs/`，注意第三方 jar `未入库` 的既有约定）；
② 勘测该 API 的 1.20.1 形状（旧版写的是 1.12.2 API，**大多已被重写**）；③ 再写模块。

- ⚠️ **气体需求属于这里**：旧版用 `mekanism.api.gas.*`（**新版 Mekanism 已不存在**，改为 chemical 体系），
  见 §10。它是**本波的一个模块**，不是主线小项。
- **建议顺序**（按「依赖 API 的复杂度」从低到高）：**FluxNetworks（72 行）→ TConstruct（127）→
  AE2（943）→ GregTech（401）→ 气体（Mekanism）→ 其余**。
  先做小模块是为了**把框架本身验证一遍**，而不是一上来就啃大模块。

### 6.1 `ItemDebugStruct` 不移植的依据（**所有者 2026-10-04 决定**）

旧作者自己就写着 `TODO: Realize it.`，核实源码后确认它**在上游从未进入游戏、且实现是坏的**：

1. **从来没被注册过**：全仓库搜 `ItemDebugStruct` / `itemdebugstruct`，命中**只有它自己的类文件**——
   没有注册调用，**没有贴图、没有模型、没有语言键**。是死代码。
2. **输出是半成品**：结构**匹配成功时一句都不打印**；`blueprintMachine()` 取不到机器时**完全静默**。
3. **旋转循环是错的**：它按四个朝向循环比对，但**世界坐标 `pos` 始终没跟着转**（只转 `pattern` / `replacements` / `face`），
   所以除当前朝向那一次外，**另外三次报的是无意义的位置**——会主动误导人。

**它想提供的诊断我们这边本来就有**：`MachinePattern.firstMismatch(Level, BlockPos)` 已实现
（注释即「第一个不匹配的相对位置」）。**更好的是它不该靠一件物品**——旧版用物品是因为
它**没有控制器界面诊断**；本版该走界面（控制器界面在「结构不完整」时给出首个不匹配位置）。

> ⚠️ **连带的技术债（务必登记）**：`MachinePattern.firstMismatch()` 目前**全仓库零调用**
> （已 grep 确认），是**死代码**。既然决定了不做这个功能，就必须二选一：
> **① 删掉它**（清理，符合本项目「没有消费者的字段不留」的一贯做法）；
> **② 保留并加注释**说明「为将来的结构诊断预留」——**但不能留着不说**，
> 否则下一个人会以为有消费者。**建议 ①**，等真的要做界面诊断时再加回来（它是三行循环，重建成本极低）。
>
> 这与「不做」的决定**不冲突**：不做的是**移植那件物品**，而删除死代码是**卫生**。

## 9. 环境陷阱（每次都踩，先记住）

| 陷阱 | 处理 |
|---|---|
| `git` / `gh` **不在 PATH** | `$env:PATH = "C:\Program Files\Git\cmd;C:\Program Files\GitHub CLI;" + $env:PATH`（`gh` 内部要调 `git`） |
| **`git push` 报 schannel `SEC_E_NO_CREDENTIALS`** | **与认证无关**（令牌写进 URL 也一样失败）。加 **`-c http.sslBackend=openssl`** 即可推送成功。判定指纹：`gh api user` 能通而 `curl https://github.com` 返回 000 |
| **离线构建**必须显式覆盖 | `-Puse_local_deps=true`（仓库默认 `false`，会去 maven 找第三方 jar 而失败）；三个第三方 jar 在本地 `libs/` 但**未入库** |
| 许可证与署名 | 在 `src/main/resources/META-INF/mods.toml`，**不在 `build.gradle`**（0.30.1 为此白跑三遍） |
