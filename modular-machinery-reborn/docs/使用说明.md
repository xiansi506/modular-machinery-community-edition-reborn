# 使用说明：从空实例到一台能跑的机器

本模组是一个**框架**：它**不携带任何机器，也不携带任何配方**。
机器（结构）与配方（需求列表）**全部由你提供**——数据包、配置目录或 KubeJS 脚本，三选一。
模组自己只提供：控制器、机箱、仓口、结构判定、配方引擎、界面与 JEI。

> **状态**：随 **0.30.0** 整理。0.30.0 相对 0.29.0 **没有功能改动**（见 `../迁移日志.md`）。
> 本文只写**在游戏里验证过**的行为；凡是没逐字跑过的，一律标出来，不写「应该可以」。
>
> **标记的含义**
>
> - ✅ **实机验证**：这份内容在游戏里逐字跑过，标记后写明版本与日期。
> - ⚠️ **未逐字实机跑过**：形状取自实机验证过的机器/配方，但**这一份具体的组合**没有在游戏里执行过。
> - ❌ **做不到**：模组没有这个能力，原因见 [`已知限制.md`](已知限制.md)。
>
> 配套文档：[`KJS-配方指南.md`](KJS-配方指南.md)（KubeJS 的完整字段表与排错）、
> [`已知限制.md`](已知限制.md)（做不到什么、为什么）。本文**只做索引与最小可粘贴示例**，字段细节不重复。

## 一、这是什么，不是什么

**装完 jar 进游戏，世界里一台机器都没有，JEI 里一条配方都没有。** 这是刻意的设计（内容外置，M10），不是安装失败。

你在创造栏里能拿到的东西：

| 物品 | 说明 |
|---|---|
| `machine_controller`（通用机器控制器） | 不绑定任何机器，按结构找**任意**一台能匹配的机器 |
| `factory_controller`（通用工厂控制器） | 同上，但只认定义里写了 `has-factory` 的机器 |
| 机箱 `blockcasing`（**6 个变体**） | `plain` / `vent` / `firebox` / `gearbox` / `reinforced` / `circuitry`；定义里写成 `modular_machinery_reborn:blockcasing[casing=reinforced]`，**只写方块 id 则匹配任意变体** |
| 6 个仓口家族（物品/流体/能源 × 输入/输出） | 每个家族各有自己的等级阶梯，**共 46 个等级物品**；`elements` 不写状态属性时匹配该方块任意等级 |
| 并行控制器（5 档）、升级总线（5 档） | 必须在结构里占据一个**定义允许**的位置才起作用 |
| 蓝图（每台已注册机器一个）、建造选择工具、扳手、`modularium`、`redstone_signal` | 旧版那套物品 |
| `machine_projector`（投影器） | **有物品、没有行为**：世界空间的幽灵预览属**本次发布不做**（所有者决定） |
| 控制器界面、仓口界面、工厂控制器界面、3D 结构预览、JEI 类别 | 全部随 jar 提供 |

你看不到的：**任何机器结构与任何配方**。它们必须由你写出来，方式见 §二、§三。

**一台机器真正跑起来需要三样东西**，缺一不可：

1. **机器定义**（结构）：哪些相对坐标上放什么方块；
2. **控制器**：结构中心那个方块（通用或专属，见 §四）；
3. **配方**：这台机器做什么、消耗什么、耗时多少。

> ⚠️ **机器的进出全部经过仓口。** 控制器只有一个蓝图槽，**不暴露任何物品/能源/流体能力**（0.12.0 起与原版一致）。
> 所以：**`parts` 里没有仓口的位置，这台机器就永远不会开工**——它会成型、会显示界面，但配方没有地方收料、也没有地方放产物。
> 这是新手最容易卡住的一格，§七 的 Hello World 会明确演示它。

## 二、三种定义机器的方式

同一份机器可以来自三个地方，**用哪个取决于你要什么**（对照表见 §二.5）。三种都走**同一份校验代码**
（`machine/MachineSchema.java`），所以报错的句子是同一套。

### 二.1 数据包 —— 可以 `/reload` 热改，但拿不到专属控制器

**文件放这里**（`<存档>` 是你的世界文件夹名）：

```
saves/<存档>/datapacks/my_machines/
├── pack.mcmeta
└── data/my_machines/machinery/hello_stone.json
```

`pack.mcmeta`（`pack_format` 对 1.20.1 是 `15`）：

```json
{
  "pack": {
    "pack_format": 15,
    "description": "My machines"
  }
}
```

`data/my_machines/machinery/hello_stone.json` —— 一份**完整的最小机器**：

```json
{
  "registryname": "hello_stone",
  "localizedname": "Hello Stone",
  "parts": [
    { "x": 1, "y": -1, "z": 0, "elements": "minecraft:stone" },
    { "x": -1, "y": -1, "z": 0, "elements": "minecraft:stone" },
    { "x": 0, "y": -1, "z": 1, "elements": "minecraft:stone" },
    { "x": 0, "y": -1, "z": -1, "elements": "minecraft:stone" }
  ]
}
```

- `registryname` **必填**：裸写路径（`hello_stone`）自动补本模组命名空间，即 `modular_machinery_reborn:hello_stone`。
- `localizedname` 可选；有语言键 `<命名空间>.<路径>` 时**语言键优先**。
- 坐标是**相对控制器**的（控制器自己在 `(0,0,0)`，写进去也会被跳过）。
- 装好后执行 **`/reload`**。

**日志里会出现**（`N` 是你这台机器加进来的总数）：

```
[modular_machinery_reborn] Loaded 1 machine definition(s) from 0 variable set(s)
[modular_machinery_reborn]   modular_machinery_reborn:hello_stone -> 4 parts, size 3x1x3, y -1..-1
[modular_machinery_reborn] 1 machine(s) have no controller block of their own and use the generic machine_controller: modular_machinery_reborn:hello_stone. Put a definition in …/config/modular_machinery_reborn/machinery to give one its own controller (it takes effect on the next launch). …
```

**用哪个控制器**：通用 `machine_controller`。数据包**创建不了方块**（方块在模组构造期注册，数据包在那之后才读），
所以这条路线上的机器**不可能**有 `<机器名>控制器`——详见 §四。

> 实机状态：❌ 放 `<实例>/datapacks/`（对全部存档生效）从**没有**在游戏里确认过；本文不依赖它，请用 `saves/<存档>/datapacks/`。

### 二.2 配置目录 —— **要重启**，这是拿到专属控制器的唯一方式

**文件放这里**（`<实例>` 就是 `.minecraft` 那一层）：

```
<实例>/config/modular_machinery_reborn/machinery/hello_stone.json
```

内容与数据包那份**完全一样**（同一份 schema），只是换了目录：

```json
{
  "registryname": "hello_stone",
  "localizedname": "Hello Stone",
  "parts": [
    { "x": 1, "y": -1, "z": 0, "elements": "minecraft:stone" },
    { "x": -1, "y": -1, "z": 0, "elements": "minecraft:stone" },
    { "x": 0, "y": -1, "z": 1, "elements": "minecraft:stone" },
    { "x": 0, "y": -1, "z": -1, "elements": "minecraft:stone" }
  ]
}
```

**必须重启游戏**。启动时的构造期会扫描这个目录，为每个 `registryname` 注册一个 `<路径>控制器`：

```
[modular_machinery_reborn] 1 controller block(s) registered for machines declared in C:\…\config\modular_machinery_reborn\machinery
```

重启后你就有了 `hello_stone_controller`，**只认这一台机器**；而通用 `machine_controller` 也能照常成型它。

之后**只改 `parts`（结构）不需要再重启**——`/reload` 就会重新读取完整定义。**只有「新增/删除一台机器」才需要重启**，
因为那是在动方块注册表：

| 你做的改动 | 生效方式 |
|---|---|
| 改已存在机器的 `parts` / `localizedname` | `/reload` |
| **新增**一个机器文件（或删掉） | 定义 `/reload` 就加载；**专属控制器方块要重启才有**（不重启那一轮日志会告诉你它这轮只能用通用控制器） |

**判定规则很简单**：文件**含 `parts` 就是定义**，**不含就是「控制器声明」**——声明只写 `registryname`
（可再加 `has-factory`），把定义留在数据包，从而同时得到「有专属控制器」和「结构可 `/reload` 热改」。
声明怎么写、以及 `has-factory` 为什么必须在声明里写，见 [`已知限制.md`](已知限制.md) §六。

> ⚠️ 文件名**不影响任何东西**，决定机器身份的是文件里的 `registryname`。

### 二.3 KubeJS —— 可以 `/reload`，也拿不到专属控制器

**脚本放这里**：

```
<实例>/kubejs/server_scripts/hello_machine.js
```

```js
MachineRegistryEvents.registry(event => {
  event.machine('scripted_smoke')                    // registryname（裸路径补本模组命名空间）
    .localizedName('Scripted Smoke')                 // 显示名
    .part(1, -1, 0, 'minecraft:stone')               // 单格：x, y, z, 接受的方块…
    .part(-1, -1, 0, 'minecraft:stone')
    .part(0, -1, 1, 'minecraft:stone')
    .part(0, -1, -1, 'minecraft:stone')
    .register()                                      // ★ 必需，漏了不报错（见 §八）
})
```

放好后 **`/reload`**。字段表、`.part` / `.parts` 的区别、被推迟的字段、合并优先级见
[`KJS-配方指南.md`](KJS-配方指南.md) §六 与 §八——**本文不复述**。

**日志里会出现**：

```
[modular_machinery_reborn] KubeJS schema registered: event.recipes.modular_machinery_reborn.machine
[modular_machinery_reborn] KubeJS defined machine 'modular_machinery_reborn:scripted_smoke' (4 part(s))
[modular_machinery_reborn] KubeJS machine registry event posted; 1 machine definition(s) were staged by scripts and will be merged by the machine loader
[modular_machinery_reborn] Loaded 1 machine definition(s) from 0 variable set(s)
[modular_machinery_reborn]   modular_machinery_reborn:scripted_smoke -> 4 parts, size 3x1x3, y -1..-1
[modular_machinery_reborn] 1 machine(s) have no controller block of their own and use the generic machine_controller: … A machine defined by a KubeJS script cannot have one at all: blocks are registered before any script runs (see D8 …).
```

`KubeJS schema registered` 那一行是**接线探针**：没有它说明 KubeJS 没发现本模组的插件（0.27.0 及更早的缺陷），
此时**配方调用是静默无操作**。

> 实机状态：✅ **实机验证**（0.28.2，2026-10-01）：`posted; 1`、`scripted_smoke -> 4 parts`、结构成型、
> `/reload` 两次机器仍在、删脚本后 `/reload` 机器消失。

### 二.4 同一个名字被多处定义时谁赢

优先级从高到低：**KubeJS 脚本 > 配置目录 > 数据包**。脚本覆盖别的来源时日志会**点名**该 id 并说明两边各来自哪里，
不会静默生效。删掉脚本 → 下一次 `/reload` 起那台机器不存在（脚本层不跨轮缓存）。

### 二.5 该用哪一个

| 你要什么 | 数据包 | 配置目录 | KubeJS |
|---|---|---|---|
| 生效方式 | `/reload` | **新增机器要重启**；改结构 `/reload` | `/reload` |
| 专属控制器 `<机器名>控制器` | ❌ | ✅ | ❌ |
| 工厂控制器（`has-factory`） | ❌（只能写声明） | ✅（声明里写 `has-factory: true`） | ❌ |
| 需要装 KubeJS | 否 | 否 | 是 |
| 适合 | 打包分发、反复调结构 | 自己写的机器、想要专属控制器 | 已经在用 KubeJS 的整合包 |
| 最小例子 | §二.1 | §二.2 | §二.3 |

## 三、两种定义配方的方式

配方是**需求列表**：这台机器吃什么、产什么、多久。**配方只在对应机器成型时才会被选中开工**——
机器没搭好，配方存在也不跑。

### 三.1 KubeJS

```js
ServerEvents.recipes(event => {
  event.recipes.modular_machinery_reborn.machine({
    machine: 'alloy_furnace',        // 必填：机器注册名（与机器定义的 registryname 比对）
    registryName: 'kubejs_demo',     // 可选：配方 id
    recipeTime: 100,                 // 可选：耗时 tick，默认 100，必须 >= 1
    requirements: [                  // 必填、非空数组
      { type: 'modular_machinery_reborn:energy', 'io-type': 'input', energyPerTick: 40 },
      { type: 'modular_machinery_reborn:item', 'io-type': 'input', item: 'minecraft:copper_ingot', amount: 2 },
      { type: 'modular_machinery_reborn:item', 'io-type': 'output', item: 'minecraft:iron_ingot', amount: 1, chance: 0.75 },
      { type: 'modular_machinery_reborn:fluid', 'io-type': 'input', fluid: 'minecraft:water', amount: 100 }
    ]
  })
})
```

- **根级 `type` 由 KubeJS 自动写入**，脚本里不写。
- 上面这段就是 **0.27.1 实机跑过**的那一份（当时绑的是 `alloy_furnace`，那台机器来自 `example-datapack/`）。
  要绑自己的机器，就把 `machine` 换成你的 `registryname`——配方只按 `machine` 字段与**当前成型的机器**比对。
- 实机状态：✅ **实机验证**（0.27.1，2026-10-01）：日志出现 `KubeJS schema registered: event.recipes.modular_machinery_reborn.machine`，配方在游戏里正常显示并被识别。

### 三.2 手写 JSON

同一份内容写成 JSON 文件，**根级 `"type"` 必须自己写**：

```json
{
  "type": "modular_machinery_reborn:machine",
  "machine": "alloy_furnace",
  "registryName": "kubejs_demo",
  "recipeTime": 100,
  "requirements": [
    { "type": "modular_machinery_reborn:energy", "io-type": "input", "energyPerTick": 40 },
    { "type": "modular_machinery_reborn:item", "io-type": "input", "item": "minecraft:copper_ingot", "amount": 2 },
    { "type": "modular_machinery_reborn:item", "io-type": "output", "item": "minecraft:iron_ingot", "amount": 1, "chance": 0.75 },
    { "type": "modular_machinery_reborn:fluid", "io-type": "input", "fluid": "minecraft:water", "amount": 100 }
  ]
}
```

> ⚠️ **根级 `type` 不是可选项。** 原版 `RecipeManager` 先读它决定把文件交给哪个序列化器；缺了就在
> **本模组看到它之前**把文件丢掉，日志只留一句 `Missing type, expected to find a string`。
> 从旧版（1.12.2）直接抄来的配方**一律缺这个字段**——旧版是 mod 自己加载配方的。
> 注意区分：**根级** `type` 是 `modular_machinery_reborn:machine`；`requirements[]` 里每项的 `type` 是需求种类。

**两个存放位置**（两个都 `/reload` 生效，都不需要重启）：

| 放哪 | 例子路径 | 配方 id |
|---|---|---|
| 数据包 | `saves/<存档>/datapacks/my_machines/data/my_machines/recipes/demo.json` | `<命名空间>:demo` |
| 配置目录 | `config/modular_machinery_reborn/recipes/a/demo.json` | `modular_machinery_reborn:a/demo` |

配置目录那份会被当成一个**强制 SERVER_DATA 数据包**暴露给游戏（日志里有一行 `Exposing N recipe file(s) … as a data pack`）。
两个来源同 id 时按常规数据包优先级竞争，**建议用不同 id**。

### 三.3 字段与需求类型

**字段速查**（完整表见 [`KJS-配方指南.md`](KJS-配方指南.md) §四）：

| 用途 | 字段 |
|---|---|
| 指定机器 | `machine`（**必填**） |
| 配方 id | `registryName`（可选） |
| 耗时 | `recipeTime`（可选，默认 100，**≥ 1**） |
| 需求列表 | `requirements`（**必填非空**） |
| 物品 | `item`（`minecraft:xxx` / `#forge:…` 标签 / 旧版 `ore:ingotIron`）+ `amount`；输出可用 `chance`、`minAmount`/`maxAmount` |
| 流体 | `fluid` + `amount`，可按 tick 消耗用 `perTick` |
| 能源 | `energyPerTick` |
| 输入还是输出 | `io-type`（`input` / `output`） |

**已实现的需求类型**：`item`、`fluid`、`energy`、`interface_number_input`（0.24.0）、
`ingredient_array_input`（0.26.0，**组内只消耗其中一个**）。

**未支持**：`gas` / `gas_pertick` / `fluid_pertick`（依赖气体 API）——写了**加载即报错**
（`Unknown requirement type '…'`），不会静默跳过。
另外 `catalyst` 与 `item_durability` **在原版里根本不是需求类型**（所以**不是缺口**，见
[`已知限制.md`](已知限制.md) §一）；作为 `type` 写出来同样会报上面那条错。

> 时序（写配方时要知道）：**输入在开工时扣除**，能源与 per-tick 流体**每 tick 扣**，
> 产物在**完工时**写入且**逐条独立掷 `chance`**；完工前的空间检查按**必定产出**的数量算。

## 四、用哪个控制器

方块**只能在模组构造期注册**（本项目 D8 约束），所以「有没有专属控制器」取决于**机器定义放在哪里**。
这张表是 [`已知限制.md`](已知限制.md) §六 的索引版，**以那一节为准**：

| 定义放哪 | 专属控制器 | 用哪个控制器 | 生效时机 |
|---|---|---|---|
| **配置目录** `config/modular_machinery_reborn/machinery/` | ✅ **有** | `<注册名>控制器` | **需要重启游戏**（构造期扫描） |
| **数据包** `data/<命名空间>/machinery/` | ❌ 没有 | **通用** `machine_controller` | `/reload` |
| **KubeJS 脚本** | ❌ 没有 | **通用** `machine_controller` | `/reload` |
| 数据包定义 **+ 控制器声明** | ✅ **有** | `<注册名>控制器` | **需要重启游戏** |

一句话原因：**方块注册发生在模组构造期，数据包与脚本都在那之后才跑**，所以后两者不可能凭空多出一个方块。
加载器每轮 `/reload` 都会打印一行，点名哪些机器只能用通用控制器。

## 五、建造选择工具：从世界里「抄」出一个 `parts`

这件工具是**「选区 → 机器 JSON 片段」的导出器**，**不是方块放置器**（旧版也没有放置这一半）。完整说明见
[`已知限制.md`](已知限制.md) §六，这里只给工作流：

1. **准备**：创造模式 + 有命令权限（OP），手里拿**建造选择工具**。
2. **右键方块**逐格切换选区（白色线框会亮；**再右键一次取消**）。选**除了控制器之外**你要收录的每个方块。
3. **右键那台机器的控制器** → 工具把选区导出成 JSON 文件到
   `<实例>/config/modular_machinery_reborn/machinery/`，文件名是 `machine-<你的名字>-<年-月-日_时.分.秒>.json`。
   聊天栏会报告「控制器面朝 …」，控制器不朝北时还会报「保存时将结构旋转 … 度」。
4. 打开那个文件：**只有 `parts` 一个字段**，坐标**相对控制器**，方块连**每个状态属性**都写出来了。
   **补上两个字段**再放回去：

   ```json
   {
     "registryname": "my_machine",
     "localizedname": "我的机器",
     "parts": [ … 工具导出的内容 … ]
   }
   ```

5. **重启游戏** → 出现 `my_machine控制器`。**之后改 `parts` 只需 `/reload`，不用再重启。**

**旋转不用你手工做**：工具已经把结构写成「控制器朝北」的样子，填回定义后控制器随便朝哪一面都能成型。
反过来，**照抄别人定义里的坐标时，先让控制器朝北**（放控制器前站在它**北侧、面朝南**，或放好后按 F3 看 `facing=`），
否则整份结构要跟着转。

## 六、`/reload` 还是重启——最常踩的一格

| 你改了什么 | 生效方式 |
|---|---|
| 数据包里的机器定义 | `/reload` |
| 配置目录里**已存在**机器的 `parts` / `localizedname` | `/reload` |
| 配置目录里**新增/删除**一个机器文件 | 定义 `/reload` 就加载；**专属控制器方块要重启** |
| 控制器声明（只有 `registryname` / `has-factory` 的文件）新增或改动 | **重启** |
| KubeJS 机器脚本（新增、修改、删除） | `/reload` |
| 任何配方（数据包 / 配置目录 / KubeJS） | `/reload` |
| 升级声明（数据包 / 配置目录） | `/reload` |
| `config/modular_machinery_reborn-common.toml` | **重启** |

记忆点只有一条：**凡是「新增一个方块」的改动都要重启**（专属控制器、工厂控制器），
**凡是「改数据」的改动都只要 `/reload`**。

## 七、Hello World：最小机器 + 配方

目标：从空实例开始，做出**一台能成型、能看到配方的机器**，再把它补成**真的能加工**的样子。

### 七.1 这台机器的形状（十字五格）

```
控制器那一层（y = 0）                    脚下一层（y = -1）
        x=-1   x=0   x=1                       x=-1   x=0   x=1
z=-1     ·      ·     ·                 z=-1     ·    石头    ·
z= 0     ·   [控制器]  ·                 z= 0   石头    ·   石头
z= 1     ·      ·     ·                 z= 1     ·    石头    ·
```

**石头都在控制器脚下一层（`y = -1`）**，四格分别在控制器的**正东、正西、正南、正北**——一个十字，中心留空。
**是 `minecraft:stone`（石头），不是圆石**；放错不报错，只会显示「找到结构：无」。

### 七.2 文件（一份脚本，机器 + 配方）

存成 `<实例>/kubejs/server_scripts/hello_machine.js`：

```js
MachineRegistryEvents.registry(event => {
  event.machine('scripted_smoke')
    .localizedName('Scripted Smoke')
    .part(1, -1, 0, 'minecraft:stone')
    .part(-1, -1, 0, 'minecraft:stone')
    .part(0, -1, 1, 'minecraft:stone')
    .part(0, -1, -1, 'minecraft:stone')
    .register()                                      // ★ 漏了它不会报错，机器也不会存在
})

ServerEvents.recipes(event => {
  event.recipes.modular_machinery_reborn.machine({
    machine: 'scripted_smoke',
    registryName: 'scripted_smoke_demo',
    recipeTime: 40,
    requirements: [
      { type: 'modular_machinery_reborn:item', 'io-type': 'input', item: 'minecraft:cobblestone', amount: 1 },
      { type: 'modular_machinery_reborn:item', 'io-type': 'output', item: 'minecraft:stone', amount: 1 }
    ]
  })
})
```

### 七.3 进游戏 `/reload`，先看日志

必须出现（顺序就是这样）：

1. `KubeJS schema registered: event.recipes.modular_machinery_reborn.machine`
2. `KubeJS defined machine 'modular_machinery_reborn:scripted_smoke' (4 part(s))`
3. `KubeJS machine registry event posted; 1 machine definition(s) were staged …`
4. `Loaded 1 machine definition(s) from 0 variable set(s)` 以及 `scripted_smoke -> 4 parts, size 3x1x3, y -1..-1`
5. `1 machine(s) have no controller block of their own and use the generic machine_controller: … scripted_smoke …`

第 3 条如果是 `posted; 0`，而 KubeJS 又**没有报任何错**，那一定是漏了 `.register()`（§八 第一条）。

### 七.4 搭机器

1. 先让控制器**朝北**：站在要放控制器位置的**北侧**、面朝**南**放下（控制器正面朝向你，也就是朝北）。
   放好后按 **F3** 对着它看 `machine_controller[facing=north]` 确认。
2. 放**通用机器控制器**。
3. 在它脚下一层摆那四块石头（十字）。
4. 右键控制器 → 界面里 **「找到结构：Scripted Smoke」**。

### 七.5 它现在还**不会**加工——这是刻意的

这台机器的 `parts` 里**一个仓口都没有**，所以配方虽然被加载了，却**永远开不了工**：
没有物品输入仓收圆石、也没有物品输出仓放石头（控制器自己不放东西，见 §一）。

**要让它真的产出，给 `parts` 加两格**（控制器东侧一格 `x=+1` 与西侧一格 `x=-1`，都在 `y = 0` 那一层），
并把两个仓口摆上去：

```js
    .part(1, 0, 0, 'modular_machinery_reborn:item_input_hatch')
    .part(-1, 0, 0, 'modular_machinery_reborn:item_output_hatch')
```

然后：`/reload` → **物品输入仓**里放 1 个圆石 → 仓口界面/控制器界面看进度 → 约 40 tick 后
**物品输出仓**里出现 1 个石头。仓口用哪个等级都行（`elements` 不写状态属性时匹配该方块的**任意**变体）。

> ⚠️ **未逐字实机跑过**：那四格石头的形状与配方形状都各自实机验证过（见下），
> 但**「scripted_smoke + 仓口 + 这条配方」这个具体组合**没有在游戏里逐字执行过。
> 实机跑过的是：形状相关（0.28.2）与配方形状（0.27.1）。

### 七.6 本节的实机状态

| 内容 | 状态 |
|---|---|
| `scripted_smoke` 那四格石头（KJS 机器定义） | ✅ 实机验证（0.28.2，2026-10-01：`posted; 1`、`4 parts`、成型、`/reload` 两次仍在、删脚本后消失） |
| KubeJS 配方这段形状 | ✅ 实机验证（0.27.1，2026-10-01：schema 注册、配方在游戏里显示并被识别） |
| 这份 `scripted_smoke_demo` 配方 | ⚠️ 未逐字实机跑过（配方内容照抄 `example-datapack` 里实机验证过的机器所用的同形状配方） |
| 上面的仓口那两格 | ⚠️ 未逐字实机跑过（方块写法取自实机验证过的 `alloy_furnace` 定义） |
| 数据包 / 配置目录两种写法 | ⚠️ 形状与实机验证过的机器**同一份**（KJS 构建器产出的 JSON 与数据包定义**逐字相同**，见 `KJS-配方指南.md` §六）；数据包路线本身由 `example-datapack` 的机器在游戏里验证过 |

## 八、出问题时看什么

**先看 `logs/latest.log`**（实例的 `logs/` 目录），按现象搜这些字符串：

| 现象 | 搜什么 | 含义 / 怎么办 |
|---|---|---|
| KJS 脚本**零报错**，但机器不存在 | `posted; 0 machine definition(s)` | **漏了 `.register()`**。这是本模组**唯一一处漏了不报错**的地方：没有它，构建器只是组装了一个 JSON 对象，不登记、不报错。判据：**脚本 0 错误 + 登记数 0 → 先查 `.register()`** |
| KJS 脚本第一行就报 `Cannot find function registry in object MachineRegistryEvents` | 同上 | 0.27.0 及更早的绑定形状缺陷，升级到 0.28.1+；**`onEvent('machineRegistry', …)` 不是替代写法**（KubeJS 6 已移除） |
| 配方调用**静默无操作** | `KubeJS schema registered` | 没有这一行 = KubeJS 没发现本模组的插件（0.27.0 及更早把声明文件放错了目录）。0.27.1+ 应出现 |
| 手写 JSON 配方**一条都加载不了** | `Missing type, expected to find a string` | 缺**根级** `"type": "modular_machinery_reborn:machine"`（§三.2） |
| 配方加载报错 | `Unknown requirement type` | 写了本版没有的需求类型（`gas` / `gas_pertick` / `fluid_pertick`），或把原版里**根本不是需求类型**的 `catalyst` / `item_durability` 当成 `type` 写；日志会列出已实现的那几类 |
| 「找到结构：无」 | — | 方块放错（**石头不是圆石**）、方块状态属性不匹配（`blockcasing[casing=plain]` 与实际的 `vent` 不同）、或**控制器朝向**与坐标不符（§五、§七.4） |
| 机器成型但**永远不加工** | 状态一直 `idle` / `no_recipe` | **结构里没有仓口**（§一、§七.5），或者所需的那一类仓口（物品/流体/能源）没放 |
| 配置目录的机器**没有专属控制器** | `N controller block(s) registered for machines declared in` | 没**重启**（`/reload` 不够），或者文件里没有合法的 `registryname` |
| 出现了**永远无法成型**的控制器方块 | `_controller exists as a block but no machine definition` | 有声明、没有对应定义（死方块），补上定义即可 |
| 机器有了，日志说只能用通用控制器 | `machine(s) have no controller block of their own` | 正常：数据包 / KJS 定义的机器就是这样（§四） |
| 构造工具导出的文件被加载器拒绝 | `Missing required field 'registryname'` | **预期内**，不是要修的 bug：导出的是**片段**，补 `registryname` + `localizedname` 后才是一份定义（§五） |
| 机器不成型、日志里有告警 | `has root field(s) this loader does not know` | 定义里写了本版不认识的字段（被忽略）；字段清单见 `移植方案-v2.md` 的决策记录 |

**通用起手式**：搜 `modular_machinery_reborn` 这一个字符串，把这一轮 `/reload` 或启动打出来的行连着读一遍——
加载器**每一轮都会**报「加载了几台机器」「哪几台只能用通用控制器」「哪几台有声明没定义」。
