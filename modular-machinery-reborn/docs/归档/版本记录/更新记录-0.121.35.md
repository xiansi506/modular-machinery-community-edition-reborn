## 真实失败（Codex 验收确认）

0.121.34 的 `startFailureKey()` 客户端分支在 ordinal 为无失败/无效时**无条件**回退更新标签镜像的旧完整字符串。已知失败键被菜单清除后（清除的 ContainerData 先于清除的 BE 更新标签到达），访问器把**已知键的旧快照**当自定义键返回——同一客户端 BE 上 `craftcheck.failure.item.input` 等八个已知键各复现2个退化场景（菜单清除先到、无效 ordinal `Integer.MAX_VALUE`），0.121.32 在相同断言上全部通过。旧 E3 夹具大多每包新建客户端对象接收快照，未覆盖同一 BE 的跨通道组合，因此首轮未测出。

## 修复（0.121.35）

`block/MachineControllerBlockEntity.java` 的 `startFailureKey()` 客户端分支：ordinal 能解出已知键则返回之（契约不变）；否则只有当镜像字符串本身**不在 `START_FAILURE_KEYS` 已知表**（`failureIndex(full) == NO_START_FAILURE`）时才回退。效果：

- 已知键清除先到 → 立即 `null`；无效 ordinal → `null`；不复活旧已知键（回归消除）。
- 自定义接口键（`audit.mode.mismatch`）与魔法键（`craftcheck.failure.magic.input`）经真实服务器 tick → updatePacket → 同一客户端 onDataPacket 仍可见（改善保留）。
- 清除自定义键：其清除标签抵达后返回 null；标签未到时旧自定义文本保持——旧 ordinal 通道无法区分"清除"与"自定义键"，该窗口如实保留并描述，未用白名单塞键/扩展协议/引入修订状态机解决。
- `failureCauseText`（C2b 通道）与菜单八个 ordinal 索引契约不变；`MachineControllerScreen.java` 无改动。
