# P03-b：机器字段与动态结构

基线：Reborn 0.121.0、协议 12，Git HEAD `f94ba299e37f0975ac5255f90671f990bacfc61a`。范围为 `MachineSchema`、`MachineRootFields` 的字段处理及必要的结构匹配/展开调用链。配置配方与失败重载留给 P03-c；未修改业务代码或启动游戏。

## 问题

### P03-06：零步进动态段可导致极长循环或无法结束（P1，特定配置）

**触发：** 机器定义的动态段省略 `structure-size-offset`（或显式设为零向量），起始位置的部件与世界方块匹配，且 `maxSize` 设置为 `2147483647`。`matchesSize` 每次反复检查相同坐标；计数器是 int，增加到上限后回绕，无法满足 `count > maxSize`，匹配不会自行通过该条件结束。常见较小上限也会重复检查同一格直到超过上限，并判定不匹配，而不是注释所说的只能匹配一节。结构检查在服务端 tick 路径运行，故此配置被触发时存在服务端卡住风险。

**证据与限制：** 实际 schema 接受零步进及 int 最大上限；离线调用实际 `DynamicPattern.matchesSize`，限定检查全部指向同一坐标，在 10001 次处主动抛出测试专用异常；另测上限 3 的情形，检查 4 次后返回不匹配。int 最大值递增回绕和比较结果按 Java int 实际行为另行验证，**没有实际执行到 20 亿次或在真实服务器造成卡死**。必须由有配置权限的作者提供异常定义，之后符合结构的普通玩家操作可能触发检查；不是普通玩家发送网络包即可制造此定义。

**位置：** `machine/MachineSchema.java:968-1002,1006-1013`、`machine/DynamicPattern.java:245-254`、`block/MachineControllerBlockEntity.java:623-628`。旧版 `github/kasuminova/mmce/common/util/DynamicPattern.java:140-151` 也使用相同计数和零步进方式，这是保留下来的边界风险。建议在 schema 对重复段的零步进给出明确拒绝/兼容语义，给重复次数与展开总量设合理上限；运行时使用不会溢出的有界计数，并回归零段、收尾段、最大合法值及正常动态段。

### P03-07：错误的蓝图布尔字段会静默关闭蓝图要求（P2）

**触发与影响：** 配置作者把 `"requires-blueprint": true` 误写成字符串 `"ture"` 等非布尔值时，Gson `getAsBoolean()` 将其变成 false。机器定义仍加载，通用控制器无需蓝图即可匹配该结构，与作者意图不符。该风险来自有权限作者编辑定义，不是绕过玩家权限的远程攻击。

**证据与限制：** 实际 schema 解析后 `requiresBlueprint()` 为 false；在合成世界中使用实际 `MachineRegistry.findMatch`，无蓝图可匹配；布尔 `true` 的对照样本无蓝图时被拒。未在游戏放置机器。旧版 1.12.2 `DynamicMachinePreDeserializer.getRequireBlueprint` 明确要求 JSON 布尔类型，故这是可复核的移植行为差异。

**位置：** `machine/MachineSchema.java:174-175`、`machine/MachineRegistry.java:201-219`；旧版 `common/machine/DynamicMachinePreDeserializer.java:53-58`。建议与 `has-factory` 一样严格校验布尔并报字段/来源，覆盖字符串、数字、null、真假及默认值；排查其他直接调用 `getAsBoolean` 的机器字段。

**P04-c 补充：** 流体配方的 perTick 也直接调用 getAsBoolean，字符串 "ture" 被接受为 false。实际 start 加 3 次 recipe tick 中，每份 10 mB 的需求从逐 tick 支付变成只在开工支付 10 mB。详见 [P04-c 报告](P04-c-流体气体与能源解析.md)，沿用 P03-07；这是本版开关的校验问题，不据此断言旧版存在同名开关。

### P03-08：同名动态段导致重新展开结果不同于实际匹配（P2）

**触发与影响：** 同一机器声明两个名称相同的动态段，它们实际匹配到不同长度时，schema 接受两项；`MachineStructures` 按名称寻找保存的状态且取最后一个匹配结果，两个段都使用后者长度重新展开。因此诊断和投影等使用 `runtimeStructure`/`ghostStructure` 的功能可能出现不存在的部件或漏掉部件。初次结构匹配使用每段自己的结果，不能仅凭此断言机器结算有误。

**证据与限制：** 实际解析、`MachineRegistry.findMatch` 和 `MachineStructures.runtimeStructure` 在模拟世界执行：两个同名段分别匹配 1 节/2 节，重建把第一个段也扩成 2 节，产生实际匹配结构里没有的坐标。没有游戏内渲染测试。旧版机器动态段由名称映射保存，重复名称不会保留为两个独立段，不能把本版现状视为等价。

**位置：** `machine/MachineSchema.java:870-908`、`machine/MachineStructures.java:57-65`；旧版 `common/machine/DynamicMachine.java:87-96,329-381`。建议在加载时拒绝重复名称并指出两个条目；若须兼容现有重复数据，先定义稳定身份及存档迁移规则。

### P03-09：整数型机器字段接受小数并发生 int 回绕（P2）

**2026-10-31升级入口扩展：** [P06-c2a](P06-c2a-升级定义实例与效果汇总.md)实际UpgradeLoader.readType将max-stack=1.9/4294967297都读为1，继续沿用P03-09的精确整数校验问题；正常0拒绝对照通过，未新增重复编号。

**触发与影响：** `max-threads`、`max-parallelism`、动态段大小、位置坐标等检查 JSON 类型为 number 后直接 `getAsInt()`，没有检查整数精确性与 int 范围。例如 `4294967297` 被解析为 `1`，`-1.8` 被解析为 `-1`。作者可能得到不同线程上限、并行上限或结构坐标，日志却没有对应字段错误。

**证据与限制：** 实际 schema 离线解析：`max-threads` 与 `max-parallelism` 的 `4294967297` 均得到 1，坐标 `(4294967297,-1.8,0)` 得到 `(1,-1,0)`。未穷举所有字段；旧版部分动态大小也使用 `getAsInt()`，故不把所有输入都归为新移植回归。位置：`machine/MachineSchema.java:369-386,589-606,968-997,1058-1084`。建议仅对要求整数的字段用精确解析并在溢出/小数时报出来源；其他浮点字段不应被误限制。

**P04-a 补充：** 配方根 `recipeTime`、`max-parallelism`、`priority` 和命令 `interval` 的独立解析入口也已原生复现同类截断/回绕；时长还接受旧版拒绝的数字字符串。特别是超大间隔 `4294967296` 转成 0 后在 tick 1 就执行。详见 [P04-a 报告](P04-a-配方根字段与通用序列化.md)，沿用 P03-09 编号，不另算一项新问题。

**P04-b 补充：** item.amount 与备选原料条目的 amount 同样将 `4294967297` 接受为 1；catalyst 共用备选原料数量读取器。入口、夹具与边界见 [P04-b 报告](P04-b-物品NBT与备选原料.md)，仍沿用 P03-09，不重复编号。

**P04-c 补充：** 范围扩大到 fluid/gas.amount 的 int 和 energyPerTick 的 long。原生复现 Long.MAX_VALUE+1 被归零、2^64+1 被接受为 1、1.9 截为 1；合法大额 long 的精度和实际收付对照通过。详见 [P04-c 报告](P04-c-流体气体与能源解析.md)，不另编号；统一校验需同时覆盖 int/long。

**P04-d 补充：** mana/aura/LP 先转换 double 再判断整数，会把 1.0000000000000001 接受为 1；mana 的 1e-1000 变为 0，并在空余额的有效测试端口上实际开工成功。压缩空气的精确 int 读取能拒绝近整数小数。详见 [P04-d 报告](P04-d-魔法资源需求解析.md)，沿用 P03-09，精确校验应发生在有损浮点转换之前。

### P03-10：智能接口默认值可溢出为无穷大（P2，极端输入）

**触发与影响：** 写入合法 JSON 数字 `1e1000` 作为智能接口默认值时，`getAsFloat()` 得到 `Infinity`，schema 接受并让 `SmartInterfaceStore.bind` 保存它；而后续 `SmartInterfaceStore.set` 明确拒绝非有限值。带有限数值范围的接口需求可能因此不满足，表现与正常可编辑值不一致。

**证据与限制：** 实际 schema 和存储绑定离线执行，确认默认值为正无穷，而同一存储的显式无穷输入被拒绝；未验证 GUI 或配方完整运行。位置：`machine/MachineSchema.java:521-529,577-583`、`machine/SmartInterfaceStore.java:87-95,113-121`。建议在解析时检查 `Float.isFinite`，并对旧存档中的非有限值明确恢复策略。

## 其他观察、对照与边界

- 坐标数组按三个轴做笛卡尔积；长度分别为 X、Y、Z 时单条部件循环次数为 X×Y×Z。当前未看到总展开量检查，较大输入可能占用大量加载时间与内存；尚未做资源基准，列为优化/健壮性候选，不声称已测得真实卡顿。
- `factory-only` 的数据包定义不能在方块注册冻结后新增/移除专属控制器，是项目已有记录的设计限制；本轮不将该既有取舍自动计为缺陷。
- 实际测试调用了机器解析、注册表匹配、动态段展开和智能接口存储，测试世界为替身；没有 Forge 游戏、多人网络或 GUI 验收。测试输入均来自隔离夹具，未写用户游戏配置。复现器与日志位于工作区同级 `_audit/code-survey-0.121.0/P03-b/SchemaAuditCheck.java`、`run.py`、`checks.log`。
- 本子批次完成上述字段与动态结构的离线勘测；不是对全部字段取值和所有模组组合的穷举。P03-c 继续配置配方、配置项与失败/重载生命周期；P04 单独深入配方需求解析，P06 检查运行中机器的重载边界。
