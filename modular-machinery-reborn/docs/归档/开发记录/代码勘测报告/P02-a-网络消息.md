# P02-a：网络消息勘测

基线：0.121.0、协议 12，Git HEAD `f94ba299e37f0975ac5255f90671f990bacfc61a`；2026-10-28。**状态：P02-a 离线勘测完成，联机及实机验证待做；整个 P02 未完成。** 本轮只读业务代码，未修复或实机测试。

## 已确认问题

### P02-01：ME 输入总线配置物品时丢失 NBT（P2）

**触发：** 普通玩家打开 ME 物品输入总线，鼠标携带带 NBT 的物品并左键配置格。屏幕将物品交给 `MeFluidConfigPacket.sendItem`，但发送的只有注册名和数量；服务端按注册名新建无 NBT 的物品栈，写入配置。后续输入逻辑按物品及 NBT 判断，并用配置栈构建 `AEItemKey` 提取。因此，网络只有带指定 NBT 的版本时无法按原样拉取；同时存在无 NBT 版本时可能拉取非预期版本。物品计数等同类信息并不等同于 NBT 匹配。

**位置：** `client/MeItemBusScreen.java:214`，`network/MeFluidConfigPacket.java:87-96,123-126`，`block/MeItemBusLogic.java:68,95`，`compat/ae2/MeItemBusBlockEntity.java:450`。

**证据：** 实际消息编码/解码和实际 `MeItemBusLogic.tickInput` 离线执行：原物品有标记，重建配置无标记，提取请求无标记。服务端重建这一步根据实际 handler 代码复现；未启动 Forge 或 AE2 网络，尚需实机验证完整操作。修复时应确定选择信任的服务端光标栈还是传受限物品栈，并保留合法 NBT、限制数据大小，补充多种带标签物品和恶意包验证。

**旧版补充对照：** 1.12.2 的 `ContainerMEItemInputBus` 配置格使用 AE2 `SlotFake`；其 JEI 配方转移消息 `PktMEInputBusRecipeTransfer` 对完整物品栈进行 NBT 序列化并复制到配置格。两版 UI/协议不同，但旧版这条转移路径并非只保留 ID。

### P02-02：输入组号的服务端到客户端同步发生截断，并可能覆盖服务端组号（P2）

**触发：** 组号允许达到 `Integer.MAX_VALUE`，但 `HatchGroupMenu` 用一个 `ContainerData` 项传输它。实际 1.20.1 依赖中的 `ClientboundContainerSetDataPacket` 将值写成 short 并按有符号 short 读取：例如 32768 变为 -32768，菜单 getter 又将负数夹为 0；65536 变为 0。用户随后点击启用/禁用，屏幕把错误镜像值连同开关发回，服务端写入错误组号。

**位置：** `menu/HatchGroupMenu.java:54,91`，`client/HatchGroupScreen.java:215-220`，`network/HatchGroupUpdatePacket.java:69`。

**证据：** 离线执行实际原版容器数据包的编码与解码：32767→32767、32768→-32768、40000→-25536、65536→0；菜单的 `Math.max(0, ...)` 根据代码计算。实际服务器传输和界面显示尚未实机验证。建议完整同步 int（例如明确拆分高低位或使用带校验的专用同步），同时让开关更新只修改开关，避免错误镜像回写。

**P02-b 补充：** 同一传输宽度问题还影响可配置的大容量流体/气体仓、并行控制器及部分控制器显示。流体与并行控制器的实际包及客户端菜单已离线复现，详见[P02-b 报告](P02-b-菜单与命令.md)；仍归本编号，不重复计数。

### P02-03：提交组号并点击开关可能立即把新组号覆盖为旧值（P2）

**触发：** 在组隔离已开启时，将输入框中组号改为新值且保持焦点，直接点击关闭按钮。`mouseClicked` 先调用 `commitValueField`，发出“新组号、已启用”；随后同一次点击调用 `setGroupInput(false)`，它读取尚未更新的 `menu.groupId()`，再发出“旧组号、已禁用”。服务端对每个包同时写两项，第二个包因此可能覆盖第一个包提交的新组号。类似情况也可发生在提交之后、同步抵达之前操作开关。

**位置：** `client/HatchGroupScreen.java:150-164,199-220`，`network/HatchGroupUpdatePacket.java:54-69`。旧版 `PktGroupInputConfig` 将组号和开关分开发送，分别更新；本版合并包改变了这个并发语义。

**证据：** 静态调用链确认；尚未在游戏内复现及核对实际帧/网络时序。同一次点击在客户端连续发包的路径明确，不以恶意客户端为前提。建议按操作类型只更新服务端一项，或引入服务端权威的修订与冲突处理；补充输入框失焦、回车后立即切换、多人同时编辑和延迟网络的组合回归。

### P02-04：投影应答中的无效候选未按预期隔离（P3，异常输入）

**触发：** 客户端收到的投影结构中，某个位置的候选描述符全部无法解析时，处理器捕获了解析错误，却仍将空候选列表传给 `MachinePattern.Builder.add`；该方法明确拒绝空列表，抛出 `JsonParseException`，因此后续位置也无法继续处理。正常服务端用已解析的结构生成描述符，尚未证明普通游戏会产生这种应答；此项是针对异常或不一致数据的健壮性问题，不是普通玩家可向服务端发送该包的漏洞。

**位置：** `network/ProjectorResponsePacket.java:75-90`，`machine/MachinePattern.java:230-234`。该消息注册方向为服务端到客户端。

**证据：** 使用实际消息处理器和同步执行的测试上下文，传入单个无效描述符，观察到空列表异常从回调逃逸；空结构控制样本正常返回。没有启动真实 Forge 网络线程，故不能断言客户端崩溃或连接断开。建议跳过没有有效候选的位置，必要时诊断并拒绝整次投影，明确部分结构的语义，补充混合有效/无效候选回归。

## 低优先级观察与待核实

- `network/MePatternPacket.java:51` 在 sender、菜单、槽位检查之前对每个收到的消息写 INFO 日志。连接用户可以反复发送即使之后被拒绝的包，造成额外日志；尚未测量吞吐与磁盘影响，不声称已证明服务端拒绝服务。可考虑校验后记录、降为 DEBUG 或限频。
- `network/ProjectorRequestPacket.java:70-71` 每次请求先更新最后时间，再拒绝短于 5 tick 的请求，连续高频请求会持续推迟下一次成功；需要结合实际交互和时延判断是否值得调整。也需核查切换目标、退出世界、旧应答及跨维度等场景，不能仅据此宣称已存在实机故障。
- **菜单切换后的旧消息：** 并行控制器、智能接口、输入组及 ME 输入配置包没有窗口 ID，按服务端处理时的当前菜单选择目标。离线夹具使用真实并行包编解码和 `ParallelControllerUpdatePacket.apply`：先构造原菜单的包、再模拟服务端切换到另一台有效控制器、最后执行旧包，值写入新控制器；实体已移除、距离过远、没有菜单或 sender 为空时被拒绝。普通客户端操作是否能在实际网络/服务端调度中形成该顺序尚未复现；TCP 有序性、打开菜单的服务端触发方式都要纳入验证，不能把模拟时序当作已证实的普通游玩漏洞。其他三个处理器按静态代码有同类绑定风险，尚未做相同的原生执行。可考虑绑定容器 ID 与目标/会话，并测试服务端主动更换菜单等情况。
- **旧投影应答：** 消息不含请求序号或请求维度；客户端落点使用当前世界和应答坐标。离线直接依次投递两个应答时，后投递的旧应答会替换当前预览，并绑定当时客户端所在的维度。断线事件自身会清除投影；是否存在真实跨维度或重连后旧应答落地的时序尚未证明。若修复，可绑定维度和请求代号，并在退出、切换世界或取消时撤销待处理请求。
- 输入组屏幕只在 `init` 读取菜单值、随后不同步控件的问题已在 P02-b 离线复现，记为 [P02-06](P02-b-菜单与命令.md)；与传输截断、组合写回分别记录。
- 机器定义和投影同步的预分配上限并非条目总数上限；定义 JSON 单条限制为 1 MiB。投影构建会遍历动态结构及修饰器，供应器菜单摘要也会遍历缓冲。尚未对大结构/大量缓冲测量 CPU、包大小或实际传输上限，不把没有测量的规模推断成性能故障；数据加载及缓冲成本分别留给 P03、P08 深查。
