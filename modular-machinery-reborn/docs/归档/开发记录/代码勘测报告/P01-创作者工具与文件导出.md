### P01-01：原文切回表单缺少结构校验

位置：[RecipeEditorScreen.java](../../../../src/main/java/com/reborn/modularmachinery/client/RecipeEditorScreen.java)，主要为 `collect()`（75 行起）、`change()`（87 行）、`current()`（71 行）与 `init()`（94 行起）。

“原文”页使用 `RecipeDocument.read()`，只保证顶层是 JSON 对象；成功后直接替换 `root`。随后切换到“需求”页，`init()` 在异常保护之外假定 `requirements` 是数组、每项是对象且必有 `type`。

复现步骤：打开编辑器，进入原文，将下面的机器 ID 换成现有机器或保留为测试值，再点击“需求”：

```json
{
  "type": "modular_machinery_reborn:machine",
  "machine": "test:machine",
  "recipeTime": 100,
  "requirements": [1]
}
```

实际原生按钮回调抛出 `IllegalStateException`；`requirements: {}` 和 `requirements: [{}]` 分别复现 `ClassCastException`、`NullPointerException`。这些输入语法合法但不符合配方结构，应该留在原文页并提示作者修正，而非使界面进入未捕获异常路径。

影响限定在有权限使用编辑器的作者客户端。没有运行真实游戏窗口，因此不把离线异常写成“已实测游戏退出”；真实客户端上的最终错误处理和恢复表现待验收。

建议：提交原文到表单模型前检查表单所依赖的结构，或让表单以可恢复错误处理无效结构。保留未完成／错误的原文，不必强迫作者每敲一次键就满足完整配方语义，也不要丢弃未知高级字段。

### P01-02：迟到回包覆盖尚未收集的新输入

位置：[RecipeEditorScreen.java](../../../../src/main/java/com/reborn/modularmachinery/client/RecipeEditorScreen.java) 的 `update()`（48 行起）、`reviewMatches()`、`dirty()`、`tick()`（190 行）；[ConstructToolScreen.java](../../../../src/main/java/com/reborn/modularmachinery/client/ConstructToolScreen.java) 的 `update()`（23 行起）与超时分支（73 行）。

复现次序：

1. 发送当前草稿的操作，回包延迟超过客户端 100 tick 的等待上限。
2. 原生 `tick()` 恢复编辑，作者输入新值，但尚未切页、再次校验或显式收集表单。
3. 同一会话的旧成功回包到达客户端接收入口。

配方编辑器中，原值为 `recipeTime:100`，超时后输入 `200`。文本框响应器只执行 `dirty()`，没有立即更新 `root`。回包比较的是旧 `root` 与已校验源码，仍然匹配；随后重建界面，新输入被恢复为 `100`。此前针对“root 已变化”的回包检查并不能覆盖尚未收集的控件文本。

结构工具中，超时后填写新的显示名称；`update()` 虽然先收集输入，但成功分支紧接着用服务端旧 `options` 覆盖它。复现中 `New local draft` 被恢复为 `Custom Machine`。

夹具执行了真实超时分支和客户端接收方法，配方回包 token 与当前界面一致；控件使用实际 `EditBox`。网络延迟由回调时序模拟，没有运行真实 Netty 联机。

建议：记录本地编辑代次／请求发送时的控件快照，把未收集文本也纳入判定。回包可以更新服务端 revision 和状态，但不能覆盖请求之后的新输入；对于当前仍无效的原文／数值也要保留。服务器端的源码匹配和再次校验仍需保留。

### P01-03：流体默认数量摘要错误

位置：[RecipeDocument.java](../../../../src/main/java/com/reborn/modularmachinery/authoring/RecipeDocument.java) 的 `summary()`，141 行；对照 [RequirementTypes.java](../../../../src/main/java/com/reborn/modularmachinery/recipe/RequirementTypes.java) 的流体处理器，358 行。

需求：

```json
{ "type": "fluid", "io-type": "input", "fluid": "minecraft:water" }
```

正式解析器缺省 `amount=1`；编辑器摘要却只给物品使用默认 1，对其他类型统一使用 0。原生对照得到实际需求 `1 mB`，摘要为 `0 mB/craft`。作者在表单清空流体数量，或从原文导入省略默认数量的合法配方，就可能看到这一差异。

这会误导创作者，未证明实际结算错误或能免费加工。建议从正式解析结果生成摘要，或至少统一已支持类型的默认值；其余类型的完整默认值对照留待 P04，不重复建立同一流体问题。

### P01-04：原文预扫描与实际接受的 JSON 语法不一致

位置：[RecipeDocument.java](../../../../src/main/java/com/reborn/modularmachinery/authoring/RecipeDocument.java) 的 `read()`，31–38 行；另见 `validate()` 中 96 行的规范化复检。

深度扫描器只识别双引号字符串，实际 `JsonParser.parseString()` 也接受单引号字符串。将一串 `}` 放在单引号值中，扫描器会错误扣减深度。复现输入总长 679 字符，却可让包含 200 层嵌套数组的对象通过宣称上限为 64 的 `read()`。

重要边界：本次 5000 层、15178 字符的配方在后续原生校验中被 `IllegalArgumentException` 拒绝；规范化后的 `read(root.toString())` 重新挡住了深度。**没有证实绕过服务端最终校验，更没有证实服务端崩溃。** 这里确认的是原文读取阶段的限制失效，不按普通玩家远程攻击定性。

建议：在格式化、深拷贝和构建表单前，对解析树迭代检查实际深度；或保证预扫描与解析器接受的语法一致。不要仅依赖下一阶段恰好再次校验，也不建议用笼统捕获 `Error` 代替输入边界。

## 优化建议

### P01-05：按需读取方块实体 NBT

位置：[ConstructExport.java](../../../../src/main/java/com/reborn/modularmachinery/selection/ConstructExport.java)，72 行。

`definition()` 对每个符合条件的方块实体无条件执行 `saveWithoutMetadata()`，之后才分别检查 `matchingNbt` 与 `previewNbt` 是否为空。默认两个筛选均为空，导出根本不使用该 NBT。计数炉子实体夹具在默认选项下仍记录 1 次 `saveAdditional()`，输出却无 NBT 字段。

建议在确实请求至少一种 NBT 时才读取和序列化；需要两种时仍共享同一份快照。收益随具有库存／复杂数据的实体数量增长；预览与保存复核各自扫描，均可避免这部分无用工作。本次测到了调用数量，没有实测大型模组库存的耗时，不给出虚构的性能提升百分比。

### P01-06：预览翻页避免重复发送不变的选区

位置：[ConstructToolService.java](../../../../src/main/java/com/reborn/modularmachinery/selection/ConstructToolService.java) 的翻页分支与 `sync()`（72 行起）；[SelectionSyncPacket.java](../../../../src/main/java/com/reborn/modularmachinery/network/SelectionSyncPacket.java) 的 `encode()`（56 行起）。

`PREVIOUS_PAGE`、`NEXT_PAGE` 并不改变选区，但最终同样走全量 `SelectionSyncPacket.sendTo()`。使用真实 `FriendlyByteBuf` 编码 32768 个位置，消息体为 **393240 字节，即 384 KiB＋24 字节**，还没有计算另一个预览状态包。

这是**未压缩的编码体大小**，不是测得的线上流量；Minecraft 的网络压缩可能明显降低传输量。建议拆分选区变更同步和预览页同步，仅在选区变化时发送坐标，生命周期重置和客户端首次打开仍要显式同步。是否需要进一步压缩／增量编码，应先测量，不直接改变协议。
