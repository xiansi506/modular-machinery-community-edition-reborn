## P04-01：加载时不检查文本协议上限，错误延迟到同步或加工副本创建（P2）

**分类与确认：** 稳定性/加载校验问题，离线原生复现。触发者是有权限编写配方的作者；没有确认普通玩家能够上传任意配方，不按远程越权漏洞描述。

**触发与结果：**

| 输入 | JSON 加载 | 后续实际调用 |
|---|---|---|
| 根 `tooltips` 单字符串含 32,767 个 ASCII 字符 | 成功 | 实际 `toNetwork → fromNetwork` 成功 |
| 根 `tooltips` 单字符串含 32,768 个 ASCII 字符 | 成功 | `toNetwork` 抛 `EncoderException: String too big ... max 32767` |
| `script-tooltip` 对应整个 options JSON 的长度恰好为 32,767 | 成功 | `executionCopy()` 成功 |
| `script-tooltip` 值本身含 32,768 个字符 | 成功 | options JSON 长度变成 32,789；`executionCopy()` 抛同类异常 |
| item 的 `script-modifiers` 含 4,000 个短回调键 `callback_0`～`callback_3999` | 成功，每个键都通过字符串校验 | 整个 options JSON 长度为 62,912，`executionCopy()` 抛同类异常 |

最后一项说明，仅限制每个键的长度仍不足以保证协议可写，必须考虑容器序列化后的总长度及转义开销。测试日志中的 PASS 表示成功复现预期的当前行为，**不表示问题已修好**。

**调用链与影响：** 根提示行在加载时直接收集，最终用默认 `writeUtf` 写出。通用选项先通过形状校验，再把整个 JSON 作为一个字符串写出；`MachineRecipe.executionCopy()` 又复用这套网络序列化来复制每条需求。因此问题不仅存在于配方同步：普通控制器 `executionCopyOf` 和工厂候选检查也会调用该复制入口，异常会在取得执行副本时抛出。原生夹具直接验证到副本创建失败，未运行控制器 tick 或真实玩家登录；实际服务器是否断开连接、如何报告 tick 异常，需要游戏验收，不能将其写成已经实机崩服。

**位置：** `recipe/ModRecipeSerializers.java:145-164,227-247`，`recipe/MachineRequirement.java:85-114`，`recipe/MachineRequirementParser.java:191-197,227-236`，`recipe/MachineRecipe.java:631-634`；调用者见 `block/MachineControllerBlockEntity.java:1625-1635`、`factory/FactoryEngine.java:318`。

**最小修复方向：** 在配方加载/创作者校验阶段检查根文本及通用选项最终编码长度，附带配方 ID 和字段定位，拒绝无法同步的数据。若确需支持更长内容，应设计成对的有界读写协议并评估总包大小及协议版本；不要仅放开 writer 或直接无限放大上限。执行副本可考虑独立的类型化复制契约，使服务端复制不受文本网络协议限制，但必须保留选择标签、并行标志、回调键及执行状态隔离，不能只作浅拷贝。

**应补回归：** 上限前后、中文、引号/反斜杠转义、多个短键组合、JSON/KubeJS 两条创建路径；正常登录、在线 `/reload`、控制器和工厂读取同一配方。未测总同步包的容量上限，不以单字段成功证明整包可发送。

**P04-b 扩展：** item 的 NBT 模板 source 同样可能通过 JSON 加载而在执行副本复制时超过 writeUtf 上限，已原生复现。详见 [P04-b 报告](P04-b-物品NBT与备选原料.md)，沿用 P04-01，不重复编号。

## P03-09 的配方入口扩展：整数转换后才检查，原值含义会改变（P2，沿用旧编号）

原发现见 [P03-b](P03-b-机器字段与动态结构.md)。本轮确认配方根字段和命令间隔也存在未经精确边界检查的 `getAsInt()` 转换；这些入口独立于 `MachineSchema`，修复时不能只修改机器结构解析器。

| 实际输入 | 原生解析/执行结果 |
|---|---|
| `recipeTime: 1.9` | 接受，时长变成 1 tick |
| `recipeTime: 4294967297` 或 `-4294967295` | 均接受，时长变成 1 tick |
| `max-parallelism: 1.9`、`4294967297` 或 `-4294967295` | 均接受，上限变成 1 |
| `priority: 2147483648` | 接受，变成 `Integer.MIN_VALUE` |
| `processingCommands: [{"command":"say interval","interval":4294967296}]` | 间隔变成 0；实际调用 `runProcessing(1, sink)` 已执行命令 |
| `recipeTime: "100"` | 接受字符串并转换为 100；旧版此字段要求 JSON number |

**影响边界：** 时长、并行限制和优先级与文件原值不符；超大命令间隔还会转成每次触发都运行，改变命令频率。测试使用记录字符串的 sink，没有执行游戏命令，也没有证明额外权限获得。正常的 `interval: 0` 按项目既有约定代表每次执行；问题是范围外的非零输入意外转换为 0，不是建议移除已支持的 0。

**旧版对照：** 本地 1.12.2 `MachineRecipe.Deserializer` 对 `recipeTime`/`priority` 以及 `RecipeRunnableCommand.Deserializer` 对 `interval` 同样用了 `getAsInt()`；其中部分截断属于沿袭的缺陷，不能描述成移植新引入。旧版时长曾先确认 number；当前时长直接转换，字符串限制比旧版更松。每配方 `max-parallelism` 是本版新增入口。未把旧版有意保留的排序权重 int 算法另报成漏洞。

**位置与建议：** `recipe/ModRecipeSerializers.java:53-58,175-191`、`recipe/MachineRecipe.java:460-472`、`recipe/RecipeCommands.java:121-134`。用保留精度的整数读取助手，在转换前检查 JSON 类型、是否为整数及 int 范围，再校验各字段自己的合法范围；priority 保留合法负数，命令间隔保留明确支持的 -1/0 语义。共同需求的 `trigger-time` 已有额外整数检查，本轮测试的负数、小数、超 int 和巨大指数均被拒绝，不把所有数值字段一概描述成失效。

## 已通过的正常路径与未计为新漏洞的观察

- 缺省时长 100、配方并行上限 0（使用机器上限）、priority 0、取消失败 false；缺省 registryName 为配方 ID path。
- 多机器归属、裸名称补本模组命名空间、旧需求命名空间别名可解析；网络往返保留机器列表、registryName、时长、并行上限、priority、服务端 sortId/buildWeight、提示行和取消标志。
- item 通用选择标签、固定并行、checker/modifier 键、耐久/燃料标志、输出检查标志、触发时间/重复标志、tooltip 键在组合往返中保留；另一个 energy 输出的 `9,000,000,000,000,000,000` long 值未丢失。
- 命令 start/processing/finish 往返后由真实调度方法执行，processing 的间隔 3 在 tick 1 不执行、tick 3 执行；未执行服务器命令源。
- 创建执行副本后修改其 triggered 状态，不改变原配方；typed JSON builder 生成的快照不受随后修改 builder 影响。此结论不等于完整 KubeJS/Rhino 生命周期已验证。
- 空机器数组、字符串形式的根取消标志、错误形状的通用布尔/回调列表，以及不适用于 energy 的物品选项均被拒绝。适配器声明元数据不在线上传输是既有设计：占位声明不参与普通配方同步，不能仅因 wire 没有 adapter 字段就报告丢数据。
- 网络读取部分计数没有独立业务上限；这里是服务器向客户端发送的配方数据，尚未找到普通客户端把它作为 C2S 注入的路径，因此没有将其列为已确认服务端内存攻击。
- 维护建议：`ModRecipeSerializers` 类注释和 `MachineRequirementParser.unknownType` 仍写着 gas/fluid_pertick 未移植等旧结论。应按现行注册表更新诊断和历史注释，避免作者被误导；这不是新增移植缺口，也没有性能收益证据，不另计问题编号。
