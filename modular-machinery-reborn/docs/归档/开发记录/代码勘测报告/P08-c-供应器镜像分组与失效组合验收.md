## P08-04：共享隔离供应器被另一控制器改写组号，活跃配方停在旧组

严重性 **P2**，确定的当前代码问题，未修复。触发需要共享隔离供应器、上下文分组冲突，以及第一台输入端口刷新；不能描述为任意多机共享必定卡住。

### 最小过程及对照

1. 供应器P隔离缓冲0放1煤+1钻石。控制器A通过真实镜像接P，四tick配方在开始扣1煤、`trigger-time=2`再扣1钻石，完成出1石头，失败策略`still`。
2. A实际首次tick完成结构匹配/收集/启动，进度1/4，锁定组65536，煤已扣。
3. B形成并收集同一P。两种场景分别验证：①B普通输入仓口配置组65536；②B先收集另一隔离供应器Q的36组，再通过镜像收集P，**不需要人为设置高组号**。P缓冲0的共享偏好分别被改为65537、65572。
4. 对A镜像调用实际同目标bind，触发真实依赖通知；A下次tick刷新输入。新端口不再含旧组65536，但活跃配方仍持有旧组。
5. A再运行三tick，停在2/4，1钻石仍在P中，输出无石头。没有直接修改组号数组或注入activeCraft。

同一世界壳、实际配方/供应器/镜像/绑定操作下，两组对照分别让B不形成、B形成但普通仓口为65535：A均四tick完成，钻石扣除，产出1石头。因此不能把原因泛化成镜像bind或B形成本身。

### 根因及旧版对照

- `block/ControllerPortCollector.java:51–58`：每台控制器每次收集自建 usedGroups/IdentityHashMap，根据本上下文重新分配。
- `compat/ae2/ProviderState.java:72–79`：appendInputs 将分配结果写回**供应器共享** groups[]。
- `block/MachineControllerBlockEntity.java:898`：启动保存 activeGroupId；`:805–806` 后续按同数值筛选；`:2083` 输入刷新没有保留该逻辑资源的组映射。
- `client/HatchGroupScreen.java:206–207` 和 `network/HatchGroupUpdatePacket.java`：普通仓口允许到Integer.MAX_VALUE，65536场景可由正常设置路径表达；第二供应器场景更无需此设置。

本地1.12.2源码 `MEPatternProvider.java:129–162` 的隔离组合组件各自持有 `final long groupId = getUniqueGroupID()`；`tile/base/MachineCombinationComponent.java:11,24–25` 由全局AtomicLong生成，注释要求缓存。旧版此处没有按每控制器收集上下文回写组件组号的设计。此为静态语义对照，**未运行旧版或证明其所有共享场景无缺陷**。

建议修复方向是稳定的隔离缓冲逻辑身份与控制器映射，并保证已启动配方刷新后仍关联原资源；兼顾手动组、普通仓口、标签、多个镜像、其他供应器及存读档。不能简单把活跃组改成任意新组（可能串料），也不能只限制普通仓口到65535（第二供应器场景仍成立）。修复后需把上述反例作为回归并补存读档/工厂线程组合。
