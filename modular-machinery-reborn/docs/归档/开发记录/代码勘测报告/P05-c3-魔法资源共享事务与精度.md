## P05-06：时长补偿在单份取整后才乘并行，整数魔法整组成本可以归零（P2）

**分类与状态：** 有条件的数值/资源结算错误，实际配方 canTick/tick 已离线复现；端口为测试实现。需要作者启用 `general.enable-duration-multiplier` 并应用产生分数补偿的时长修改器。默认关闭时，本例不触发；不是普通玩家可自行提交配方的越权漏洞。

**最小复现：** 基础配方时间 10，每 tick 输入 1 单位，固定 2 并行；施加 duration ×2，并调用实际 `recipe.applyDurationMultiplier(mods,true)`，得到补偿因子 0.5。给一个有效但余额为 0 的输入端口。

| 实际执行 | 结果 |
|---|---|
| MANA / AURA / LIFEESSENCE / AIR，启用补偿 | canTick 为 true，实际 tick 成功，余额仍为 0 |
| 相同输入关闭补偿 | canTick/tick 均拒绝，余额仍为 0 |
| MANA 每 tick 3、2 并行、因子 0.5、余额 100 | 实际 tick 后为 98，支付 2；按整组 `3×2×0.5` 应为 3 |
| EMBER 每 tick 0.25、2 并行、因子 0.5、余额 1 | 实际 tick 后为 0.75，支付 0.25；小数族没有这次整数取整损失 |
| MANA 一次性输入 10，启用补偿 | 实际 start 仍支付 10，问题限于逐 tick 路径 |

**原因与位置：** `magic/MagicRequirement.java:34-38` 先计算单份 rate×durationMultiplier，再对整数族 Math.floor，最后乘 count。两份各 1、因子 0.5 被计算成 `floor(1×0.5)×2=0`，而整组准确值为 1，已没有不可表达的半单位。`transfer:44` 对普通魔法的正原值/零总量还会提前成功；空气不跳过端口条件，但有效零余额、零压力端口同样支付 0。不能把两者写成完全相同的“无端口也通过”。

调用入口是 `recipe/MachineRecipe.java:675-682`；普通控制器和工厂均实际调用 applyDurationMultiplier（如 MachineControllerBlockEntity:848、FactoryEngine:407），不是仅夹具才能设置的未使用字段。此例验证了真实单 tick 结算，没有运行完整控制器加工周期。

**配置契约另需核对：** ModConfig:347-355、约 720 的说明把这个开关定义为“仅能源”，使用指南同样只说明能源；当前 MachineRecipe 也把它传给全部 MagicRequirement。已复现魔力每 tick 10 在 duration ×0.5、补偿打开后实际扣 20，关闭后扣 10。历史夹具也有“魔法遵守补偿”的检查，因此不能只凭旧版未补偿便断言新增能力一定无意；但当前配置/文档与实现范围确实不一致。主问题仍是补偿已经启用时，整数整组成本被错误舍掉，不另登记一条重复结算问题。

**建议：** 先明确该开关是否仅作用能源；如保留魔法补偿，应把整数资源的并行与补偿按整组计算后统一取整，并明确正成本的最低支付策略。覆盖 1/3 单位、1/2/多并行、0.5/2 因子、输入/输出、压力条件和禁用对照。不能无条件将所有整数修改结果钳成至少 1，作者通过数量修改器合法设置零成本的既有行为应独立处理。

## P05-07：小数资源的可表示性使可支付并行不再单调，二分会错过可支付值（P3）

**分类与状态：** 精度边界下的功能误拒绝，实际 parallelism 与 tick 已离线复现。涉及很小的小数需求相对于当前余额的 double 分辨率；未确认现有整合包出现此参数组合，未将真实 Will 后端能否达到示例余额写成已验证事实。

**最小复现：** 一个有效测试端口，余额 100000000，容量 1000000000；单份逐 tick 成本 `2^-30`（约 9.31×10^-10），允许 16 并行，无修改器。对 WILL、EMBER 两种非整数需求分别运行：

1. 实际 recipe.parallelism(...,16) 返回 **0**，检查不改变余额。
2. 对同一配方显式 setParallelism(16)，canTick 为 true，实际 tick 成功；余额精确减少 `2^-26`，即当前余额的一个 ULP，未用“返回成功但没动余额”充当可支付证明。

`MagicRequirement.parallelLimit:82-88` 的直接可用量模拟先给出上限；`MachineRecipe.parallelism:615-623` 在完整共享预留上二分。第一个候选为 8，此时支付只有半个 ULP，舍入后余额不动，`MagicPort.Planned.move:69` 正确拒绝。二分于是把 9～16 全部丢弃；但 16 的完整 ULP 支付其实可准确执行。保护条件本身合理，二分使用了这里不成立的“更小并行一定更容易支付”前提。

该例没有气体/能源的 int/long 溢出，也不是 P05-05 的单份除法上界低估：即使上界已是正确的 16，完整预留的精度判定仍让二分错过可行值，故单独编号。高余额位于 Ember 允许配置容量范围内，但夹具没有加载真实 EmberBackend；对世界 API 的结论仍需 P09。

**建议：** 先定义小数资源小于存储分辨率时的支付/量化策略，使并行可行性与搜索算法契约一致；对“8 不可付、16 可付”等离散格点补回归。不要删掉 movementMatches 以允许余额未变化却成功，也不要对最高并行仅补一次检查后就声称一般非单调情形已解决；更不能线性遍历到 Integer.MAX_VALUE 并行来修复边界。

## P05-01 的魔法扩展：默认补偿恢复依赖资源允许逆向移动

测试 Access 只允许负向扣除，未提供专用 restore；原有 100，事务预留/执行扣 40，后置步骤返回 false。默认 `MagicPort.Access.restore:36-39` 尝试正向补回 40，被拒绝后抛 `Magic resource rollback refused`，最终仍为 60，没有额外清空其余余额。

共同根因仍是通用事务假定来源可以逆向补偿，沿用 P05-01。**这个单向端口是测试能力，不是声称某个实际魔法后端已经吞料。** 当前 Botania/LP/Ember 提供专用恢复，Aura/空气提供自定义状态快照，Will 使用默认逆向恢复；它们是否在真实 API 限制、上限/分布和失效绑定下完整恢复，留 P09 验证。

六种资源的测试端口提供直接快照恢复时，late false、late exception 和执行只移动一半均恢复原值 100；异常仍传播。来源规划后改成 90，提交拒绝并保留外部新值，不用旧快照覆盖。

## 正常行为和防误报对照

- 六种资源各检查每 tick 60+60：100 时 canTick/tick 拒绝且不扣，120 时实际支付到 0。预检查不写入资源。
- 两个不同 Access 对象返回相等的环境 key，分别以 selector-tag a/b 暴露：每条输入 60，共有 100 时实际 start 拒绝、共有 120 时恰好付完；没有按仓口复制环境余额。
- 六种资源输出容量 100，60+60 的 canFinish/finish 拒绝不变，40+40 的实际 finish 得到 80；输入不能使用输出方向端口。
- 共享输入每份 20+30、余额 100，实际并行上限为 2；方法退出后原先的并行设置 7 恢复，没有把搜索候选留在需求实例中。
- 同环境的 default/corrosive Will 分别支付 0.5/0.75，余额 1/2 分别变为 0.5/1.25，变体视图不共用同一余额。非法或缺失变体、失效端口被拒绝。
- 扣除后 minimum 和生成后 maximum 按现行语义执行：10 要扣 6、保留 5 时拒绝；扣 5 成功剩 5；99 要出 2、max 100 时拒绝；出 1 成功到 100。没有把输入不使用输出上限当作缺陷。
- 测试灵气从 -10 扣 5、minimum -20 后为 -15；改为最低保留 0 后拒绝继续透支。没有把允许负灵气的既有规则算成漏洞。
- 测试空气量 500、体积 1000，在 0.5 bar 条件下支付 100 后为 400；随后同压力条件拒绝。零数量负压 -0.5 条件在 -500 成功、-400 拒绝；零空气需求仍须有效端口。这里只验证条件算法，不证明真实 PNC 体积/压力 API 的一致性。
- WILL/EMBER 的 0.1+0.2 分两需求可支付，浮点余差容忍不会变成明显欠费；可表示的 1e-300 能实际扣完；要求非零而实际移动 0 时拒绝；在 1e18 余额下不可能表示的 1 单位扣除被拒绝，没有免费成功。极端余额是精度夹具，不声称真实后端可存入该数量。
