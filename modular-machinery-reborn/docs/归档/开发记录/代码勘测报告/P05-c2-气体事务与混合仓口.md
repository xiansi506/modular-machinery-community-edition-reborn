# P05-c2：气体事务与混合仓口

日期：2026-10-30。基线 **0.121.0 / 协议 12**，HEAD `f94ba299e37f0975ac5255f90671f990bacfc61a`。本轮只勘测、离线复现和记录；未修改生产代码、升版、正式构建、部署、启动游戏、暂存、提交或推送。

**本轮未新增已确认的游戏功能问题编号。** 正常气体结算、气体/流体共享占用和失败恢复通过下述离线检查；另记录一个已在公开构建 API 上复现、但缺少正常游戏触发入口的重复端口异常线索，不把它计作已确认游戏漏洞。P05 累计仍为 P05-01～05。

## 实际范围与证据

检查 GasRequirement 的 canSatisfy、modifiedAmount、parallelLimit、reserve、apply/tick；GasIo 的 count、extract、canInsert、insert、capacity；HybridGasTank 的 transactionView、GasView、占用检查和快照恢复。配套追踪 ResourceTransaction 的 identity view、coupleFluidTank、Fluids、验证/提交/逆序恢复，以及 HatchCollection 的气体收集、事务和标签过滤。

MachineRecipe 的 canStart/start、canTick/tick、canFinish/finish、parallelism 为实际配方入口。MachineHatchBlockEntity.FluidTankWithGasPriority、realFluidStack/realFluidAmount 和 MekanismAnchor.tankOf 用于真实仓口占用规则。ControllerPortCollector 只检查端口来自唯一结构位置的调用契约，不表示已完成其世界扫描/生命周期勘测。

从当前源码重编译 **16 个生产类**，另编译 GasTransactionAuditCheck.java。使用 Minecraft/Forge 1.20.1 和映射后的 Mekanism **10.4.16.80** 的真实 GasStack、IGasHandler 和注册表；普通样例显式选用 NORMAL 仓口，原生容量 1000 mB；大数样例在创建气体半仓前将真实流体容量设为 Integer.MAX_VALUE，属于允许容量边界的离线构造，未更改玩家配置。

离线 Bootstrap 后显式注册两种气体、注册兼容模块；为构造真实 FluidPort 临时解冻当前进程的方块注册表并登记测试方块。仓口通过实际构造器创建，BlockEntityType 为 null、没有 Level；未伪造气体传输实现，也未把这套注册装置当成真实 FML 生命周期。首次装置运行因冻结注册表失败，以及早期使用 TINY 100 mB 仓口导致样例库存被限幅，均为夹具设置问题，修正后才运行下述断言，不登记成生产缺陷。

## 通过的正常路径与组合

| 检查 | 实际结果 |
|---|---|
| 两条每 tick 气体输入各 60，共享一个仓 | 库存 100 时 canTick/tick 拒绝、保留 100；库存 120 时实际 tick 成功、恰好剩 0 |
| 一个气体源通过两个 selector-tag 暴露 | 各要求 60、仅有 100 时拒绝；两个标签共用同一事务副本，没有各付一份快照 |
| 事务隔离与来源变化 | 虚拟抽走 40 时真实 100 不变；外部换成另一种气体 90 后 commit 拒绝并保留新气体 90 |
| 单气体失败恢复 | 真实提取后，后置步骤返回 false 或抛异常，均恢复原气体 100；异常继续传播 |
| 流体占用时注气 | 实仓和虚拟仓均拒绝，不覆盖原水 100 |
| 气体占用时注液 | 实仓和虚拟仓均拒绝，不形成两种介质同时占用 |
| 同一事务水→气体 | 先虚拟排空水 100，再注气 40；规划期间实仓不变，提交后水 0、气体 40 |
| 同一事务气体→流体 | 先虚拟排空气体 40，再注水 50；提交后气体 0、水 50 |
| 双介质恢复 | 水→氢气及氧气→岩浆两个方向，分别组合后置 false/异常，原介质和原数量均恢复，不残留另一种介质 |
| 两种输出争用空混合仓 | 先气后液、先液后气两个顺序，第二种介质均被拒绝；没有向同一容量重复预留 |
| 外部改变流体 | 规划向空仓注气 50 后，外部实际注水 10；commit 拒绝，保留外部水 10、气体仍为 0 |
| 实际配方双介质切换 | canTick/tick 完成满气体→水 50；下一配方 tick 排水 50→气体 70，数量准确 |
| 同气体排空再回填 | 满气体 1000，实际 tick 先抽 1000 后输出 50 成功；该路径未复现 P05-02 的旧实仓容量阻挡 |
| 共享气体输出空间 | 两项各 501、容量 1000 时 canFinish/finish 拒绝且实仓为空；两项各 40 实际 finish 得 80 |
| 气体概率和并行 | 输出每份 1、两并行、概率 0.5、种子 1，实际 finish 输出 0；与按需求整体掷一次的旧语义一致，未复现 P05-03 的物品输出概率问题 |
| 并行共享预算 | 库存 1000、每份两项分别 20/30、上限 50，实际 parallelism 返回 20，检查不扣气 |
| 大数量聚合与支付 | 两仓各 15 亿气体，count 饱和到 Integer.MAX_VALUE；实际 start 支付两并行各 10 亿后，第一仓 0、第二仓 10 亿，没有 int 聚合回绕 |
| 大容量与不同气体 | 两空大仓 capacity 饱和到 Integer.MAX_VALUE；仅含氢气的仓不被氧气需求抽走 |

以上只证明本轮装置覆盖的当前行为。自有混合气体仓提供直接快照恢复，未复现 P05-01 的受限外部能力退款失败；这不撤销 P05-01，也不能据此声称任意外部端口可回滚。

## 已知数值边界：辅助检查误判，整条配方仍安全拒绝

GasRequirement.canSatisfy（155-161）与 transfer（216-230）仍直接用 int 相乘；reserve（210-214）使用 Math.multiplyExact。每份 15 亿、两并行、实际库存 1000 的原生执行中，直接 canSatisfy 因乘积回绕而返回 true，但实际 MachineRecipe.canTick/tick 在 reserve 阶段拒绝，库存保持 1000。与 P05-b 的流体路径同类，是辅助契约不一致的维护线索，不新增“整条配方免费加工”结论。

后续若统一数量计算，应保证 check、reserve、transfer 共用精确边界；不能把 Math.multiplyExact 简单换回普通乘法。`ignore-output-check`、脚本改动与跨阶段组合留给 P05-d/P06/P11，本轮未验证这些组合能否绕过保护。

## 重复气体输出的异常线索：API 可复现，正常游戏入口待查

**最小构造：** 用 HatchCollection.builder().addGasPort 将同一原生气体仓以标签 a、b 加入输出桶各一次；需求不指定 selector-tag，输出 1001、真实容量 1000。

实际调用 recipe.canFinish 时，GasIo.canInsert（94-111）对两个相同视图分别 SIMULATE，第二次仍看见第一次没有改变的容量，误答可容纳。随后 reserve 内的 GasIo.insert（114-140）先在共享工作副本填入 1000，第二次只能拒绝余下 1，于是在**规划阶段**抛出 `Gas insertion disagreed with its own simulation`。真实仓始终为空；不能说已损失气体或已崩溃真实服务器。只保留一个输出端口的对照返回 false，不抛异常。

正常 ControllerPortCollector.collect（18-42）按 effectivePattern.positions().keySet() 收集不同位置；MekanismAnchor.tankOf（65-79）为每个实体提供各自的混合仓。因此当前没有确认普通结构会把同一个气体输出仓重复加入。该案例记录为 **P07/P08 待核实的健壮性线索**，不分配新的已确认问题编号；后续应检查真实共享端口/供应器组合是否能产生这种列表。

若未来允许同一底层端口多次暴露，容量预检应按资源身份处理别名，或在一次共享规划中实际预留模拟量；去重也必须保留 selector-tag/group 过滤语义。不能把内部不一致异常一律吞掉并宣称提交成功。
