## P05-03：并行物品输出逐份掷概率，与既定整条需求掷点语义不同（P2）

**原生复现：** 单条固定输出每份 1 石头、chance=0.5、2 并行，调用真实 recipe.finish，随机种子 1，最终得到 1 石头。独立参考 RandomSource 的第一次 nextFloat 为 0.7308782：按整条需求一次机会门控，本次应未命中，产生 0；按同一规则任何一次结果只能为 0 或 2，不可能为 1。

**原因与位置：** `ItemRequirement.java:401-416` 把机会判断放在逐并行循环里，每份各调用 nextFloat。输入分支则在整个支付前仅判断一次。范围数量本来可以每份分别生成，但这不等于每份都应独立判定是否命中。

**旧版与文档：** 本地 1.12.2 RequirementItem.finishCrafting:260-262 先 chance.canWork 一次，再进入 doItemIO；本版代码注释也描述一次结算门控，现行配方指南明确提示不要假定 N 并行独立掷 N 次。这里不是仅凭新旧代码外形推测，当前真实 finish 已得到与该约定不符的混合数量。

**影响：** 并行输出的分布、波动及同一需求内的关联性改变；平均期望值相同也不能证明语义等价。不同输出需求仍各自有机会判断，不要求整份配方共用一个随机结果。本轮没有做大量统计检验，也没有声称存在平均产量增加或刷物品。

**建议：** 先对该输出需求整体判定一次机会，再在命中分支内逐份生成范围数量；保留保守输出空间预留。回归固定/范围输出、0/1/中间概率、多个输出需求、机会修饰符、并行 1/N 和重试。不要把范围 RNG 与机会 RNG 合并成一个错误的公共抽样。

## P05-04：物品/流体总量 int 聚合回绕，库存充足却拒绝配方（P2，大容量条件）

**实际输入和结果：** 两个物品单元各含 1,500,000,000 煤，两个 FluidTank 各含 1,500,000,000 mB 水，数学总量分别为 3,000,000,000。实际 IngredientIo.count / countFluid 均返回 -1,294,967,296。分别创建仅需 1 煤/1 mB 水的实际配方，canStart 均拒绝。

**位置与原因：** `IngredientIo.java:40-49,186-197` 使用 int 累加。普通物品 inputCapacity 即使声明为 long，得到的也已经是回绕后的 int。问题发生在合法单份数量的聚合，区别于 P03-09 的 JSON 数值转换，不能只修解析器。

**触发边界：** 流体使用真实原生 FluidTank，容量为 2,000,000,000，各持有量在容量内。物品夹具将槽上限设为 Integer.MAX_VALUE，再直接设置高数量 ItemStack；这是大容量处理器的 API 场景，不表示普通原版煤可正常堆叠到 15 亿。Forge IItemHandler 的读取契约允许返回超过物品通常堆叠上限的数量。没有确认用户当前仓口配置或具体大容量模组已触发。

**建议：** 聚合使用 long，按调用者的可支付/显示范围在边界转换或饱和；任何截断策略必须保留“不足/至少够当前请求”的判断。修改所有消费者，不能只把局部变量换成 long 后仍直接强转返回。回归 int 上限前后、多个仓口、0/负异常返回的处理、共享视图及实际最大并行计算。不要为了避免溢出而扫描或分配数十亿个对象；本夹具仅改变数量字段。

## 正常路径与已知线索复核

- 两条输入分别需 3 煤和 2 煤，库存 10、机器上限 10 时，实际 parallelism 得 2；计算不消耗物品，并恢复调用前的需求并行值 7。设置 2 并行后真实 start 恰好支付 10。
- `[coal,coal]` 重叠备选库存 5 时，辅助上界为 10，但真实配方二分得到 5；start 按 5 支付到零。P04-b/P05-a 中的重复计数线索在这个具体样例由共享预留校正，没有形成刷资源结论。其他标签/不同条目数量组合仍需组合收口，不以此穷举所有候选。
- 输入机会 0.5、2 并行使用同一种子 1，整组不支付，库存仍为 2；输入/输出机会 0 和 1 均按端点保持/支付整组。chance=1 的范围 1～3、3 并行真实输出与独立参考的三次范围抽样总和相符。没有据单个种子证明随机分布全面正确。
- 物品单份 Integer.MAX_VALUE、2 并行被实际 canStart 拒绝且库存不变。流体每 tick 1,500,000,000、2 并行时，直接 canSatisfy 会因乘法回绕而错误放行，但实际 canTick/tick 的精确 reserve 拒绝，1000 mB 实仓不变。本轮未证实整台机器免费结算，该检查/执行不一致仍由后续资源组合继续覆盖。
- 2000 燃烧 tick 实际消耗 2 煤；只有 1 煤时拒绝且煤保留。熔岩桶可支付燃料时间并在原槽返回空桶；多余燃烧时间不保留是现行文档约定。
- 木镐剩 10 耐久支付 5 后剩 5；恰好剩 5 时损坏消失；只有 4 时拒绝且原损伤值不变。没有验证附魔耐久机制、模组工具钩子或特殊多件堆叠工具。
- 催化剂选中后使实际时长从 10 改为 5，并在 3 并行中保持一份支付。chance=0 保留钻石、chance=1 支付钻石，普通 3 煤均正确扣除；缺少可选催化剂时普通支付仍能开工。未据此验证所有催化剂冲突、重试或持续脚本变换。

脚本 checker/modifier 的实际 Rhino 重载/回调仍归 P11；特殊堆叠容器燃料、模组化工具、原料返还受限、支付失败后的跨资源重试等留 P05-d/P09 组合，不将上述正常原版例子当成完整兼容验收。没有新增已证明的性能优化收益。
