# P02-b：菜单与命令勘测

基线：Reborn 0.121.0，Git HEAD `f94ba299e37f0975ac5255f90671f990bacfc61a`。本轮只做离线勘测，未修改业务代码，未启动 Forge 游戏或多人服务器。

## 问题

### P02-05：方块被拆除后，普通菜单仍可操作失效库存（P1）

**触发与影响：** 普通玩家打开物品仓、升级总线或控制器的菜单时，另一玩家或世界事件移除该方块。`MachineHatchMenu`、`UpgradeBusMenu`、`MachineControllerMenu`、`FactoryControllerMenu` 的 `stillValid` 只检查与原坐标的距离，不检查方块实体是否移除、维度及世界中实体是否仍为同一个。玩家仍在距离内时，菜单可持续持有旧实体的槽位；例如仓口掉落原库存并被移除后，玩家将物品放进旧菜单，物品进入脱离世界的旧库存，可能丢失。其他菜单的具体资源转移后果还需逐个实机验证。

**证据与边界：** 离线夹具调用实际 `ItemStackDrops.clearInto`、`MachineHatchMenu.stillValid` 与 `quickMoveStack`：原槽的 3 个铁锭被清出后，标记为已移除的仓口仍返回有效；1 个钻石从玩家槽进入旧的 `ItemStackHandler`。仓口/玩家/移除过程由夹具模拟，并未执行世界拆除与真实网络收包。已用当前 1.20.1 字节码核实，服务端处理菜单点击和按钮前会依赖菜单的 `stillValid`；该测试不说明存在物品复制。`MeItemBusMenu`、`MePatternProviderMenu` 和魔法仓菜单已检查移除状态，不能将本问题直接扩大到它们。

**位置：** `menu/MachineHatchMenu.java:158,194`、`menu/UpgradeBusMenu.java:124,159`、`menu/MachineControllerMenu.java:191,225`、`menu/FactoryControllerMenu.java:261,295`；`block/MachineHatchBlock.java:123-128`、`block/ItemStackDrops.java:35-48`。并行控制器与分组菜单虽无真实库存，仍有同类生命周期校验缺口；其自定义消息另外检查实体身份。

**建议：** 拒绝已移除、跨维度、坐标对应实体不再相同的菜单；核对区块卸载、同位置替换、旁人拆除和客户端关窗，并覆盖所有涉及的槽位和流体按钮。修复前应避免对已被拆除的仓口窗口继续放入物品。

### P02-06：输入组界面不消费开窗后的同步状态（P2）

**触发与影响：** 界面初始化时只把菜单当前开关和组号复制进局部字段、按钮及输入框；随后 `ContainerData` 收到服务端状态时，`containerTick` 不刷新这些控件。若初始化时镜像仍为默认值，服务端返回“已启用，组号 7”后，屏幕仍显示禁用/0，直到其他操作重置局部状态；无法直接从按钮状态判断真实配置，且会与 P02-03 的组合更新放大误操作。

**证据与边界：** 使用实际 `HatchGroupMenu` 数据、`HatchGroupScreen.init` 与 `containerTick` 的离线夹具，先以默认值初始化，再向菜单写入启用/7，菜单 getters 为启用/7，控件仍为禁用/0。当前 Forge 的 `NetworkHooks.openScreen` 先发送打开界面消息再初始化服务端菜单同步；完整客户端消息调度尚未实机验证。此项此前在 P02-a 作为待核实线索，现在升级为独立确认的界面同步缺陷；与截断 P02-02、写回竞态 P02-03 不重复编号。

**位置：** `menu/HatchGroupMenu.java:42-68`、`client/HatchGroupScreen.java:86-105,139-141,215-220`。建议明确收到同步后刷新开关与非编辑状态的输入框；用户正在输入时保留草稿，并结合 P02-03 防止同步反馈覆盖。

### P02-07：工厂窗口忽略同步的并行上限（P2）

**触发与影响：** 服务端通过 `DATA_MAX_PARALLELISM` 发送工厂并行上限，但客户端 `FactoryControllerMenu.data.set` 未处理该索引，`get` 却读取客户端控制器的 `parallelCeiling`。它没有由该同步项更新，初始为 1；`FactoryControllerScreen` 在最大值不大于 1 时隐藏并行信息行。实际加工上限仍由服务端决定，已确认的是界面错误，未宣称改变配方结算。

**证据与边界：** 在实际客户端菜单 `ContainerData` 上模拟收到“最大线程 5、最大并行 128”：前者的 getter 为 5，后者仍为 1。夹具使用人工构造的控制器，未展示真实工厂画面。`MachineControllerBlockEntity.load` 保存/加载路径未同步 `parallelCeiling`，相关客户端菜单也没有写入该项；需在游戏验证方块更新与开窗的完整组合。

**位置：** `menu/FactoryControllerMenu.java:158-195,244`、`block/MachineControllerBlockEntity.java:1111-1113`、`client/FactoryControllerScreen.java:706-713`。建议为该字段建立明确客户端镜像，并回归初次开窗、线程变化及重连。

### P02-08：诊断命令每次扫描 4913 个位置且可能加载邻近区块（P3，优化候选）

**触发与影响：** 有权限的管理员执行 `/mm-diagnose` 时，`findController` 对三轴 -8..8 逐位置调用 `getBlockEntity`，固定为 17³＝4913 次；水平范围会涉及至多 2×2 个区块。当前 1.20.1 `Level.getBlockEntity` 调用 `getChunkAt`，对应默认查找以 `create=true` 请求 FULL 区块，因此对未加载区域可能触发加载。未做时延测量，不将其描述为已测得的卡顿或普通玩家可利用的漏洞。

**位置：** `command/DiagnoseCommand.java:52-54,537-553`；字节码对照 `Level.getBlockEntity/getChunkAt` 与 `LevelReader.getChunk`。可先跳过未加载区块、使用已有控制器索引/按区块枚举，并保持最近距离和跨区块的正确性；实际服务端测量后再决定优化。

## P02-02 的扩大影响：不重复计数

P02-a 已记录 `ContainerData` 通过有符号 short 同步导致组号截断；本轮发现同一根因还影响普通流体/气体仓、并行控制器以及部分机器进度和并行字段。流体仓配置允许容量高于 32767 mB，并行控制器配置允许上限达到 int 最大值。离线使用实际容器包与菜单回调验证：流体量 40000/容量 65536 变为 -25536/1；并行控制器最大值与当前值均为 40000 时，客户端菜单读为 1/0。并行设置界面使用客户端上限验证输入，因此受影响时不只是数字显示错误。默认流体档位最大为 32000 mB，前述流体数值需要提高配置；长耗时配方则可令进度/最大进度超出 short。服务端存储和结算是否受其他途径影响仍需各自核查。

位置：`menu/MachineHatchMenu.java:65-109`、`block/MachineHatchBlockEntity.java:379-405,547-555`、`menu/ParallelControllerMenu.java:34-45,62-68`、`block/ParallelControllerBlockEntity.java:120-150`、`client/ParallelControllerScreen.java:205-212`、`menu/MachineControllerMenu.java:76-91,132-146`。能量 long 路径已经拆成四个 16 位段，不应一概归入本问题。建议对每个需要完整 int 的字段使用成对 short 或专门同步，同时回归客户端中间态与边界。
