## 实际范围和证据边界

检查 MachineControllerBlockEntity.saveAdditional/load 中普通加工字段、pendingExecutionState、activeRecipeId/activeGroupId、冻结并行/修改器，以及 executionCopyOf/resolveRecipe 的定义选择。复核 MachineRecipe.saveExecutionState/loadExecutionState 的已触发需求下标；检查普通机持续成型时 machineId 更新、updateFactoryMode 与旧加工的关系。

配套检查 MachineScriptState 和 RecipeModifiers 的存读档/脚本贡献替换，MachineRecipeIndex 的替换表入口，以及 MachineRegistry.findMatch、MachinePattern.matches、ControllerPortCollector 的重新匹配调用链。工厂线程 NBT、真实区块生命周期、客户端 update tag 和脚本热重载仍留相应专项，不因共享 load 方法就一并宣布验收。

本轮重编译 **33 个生产类**、新的 ControllerPersistenceAuditCheck.java 和上一批装置工具 ControllerRuntimeAuditCheck.java。复用 a1 的 Level/控制器构造工具，**没有再次执行 a1 的旧测试 main**。当前 be.saveWithoutMetadata、be.load、实际控制器 tick、RecipeManager.replaceRecipes 均实际运行，没有复制保存逻辑或状态机充当生产方法。

普通恢复样例在新建控制器实例上、Level 为 null 时 load，随后接回测试 Level 和已重建端口；仓口沿用保存时已经支付后的库存。这样验证 NBT 恢复后的加工，但**没有执行真实磁盘保存、区块卸载/重新加载、Forge `/reload` 或服务器重启**。

重新绑定样例进一步使用内存方块状态/实体表，执行真实匹配器、结构变化标记、端口收集和控制器 tick。测试原生仓口方块在独立进程内解冻注册表后登记，仓口是当前真实 MachineHatchBlockEntity。控制器用带水平 FACING 的原生炉子状态作为通用控制器状态替身，保持 boundMachine=null、factoryBlock=false；没有替换生产 tick。Level 仍是未调用构造器的测试壳，isLoaded/区块可用量由装置提供，**不是已加载的 Minecraft 世界**。

## P06-03：配方同 ID 改定义后，存档恢复会将旧支付下标套给新需求（P2）

**分类与条件：** 在途加工保存/恢复的一致性与资源支付问题。需要配方作者更改同一个 ID 的定义，并在旧加工完成前保存后恢复；不是普通玩家上传任意配方或伪造网络包。单纯新建一个相同内容的配方实例不触发此缺陷，正向对照通过。

**最小复现：**

1. 旧配方 `audit:runtime`，时长 4：开工 1 煤、下标 1 的延迟输入 1 钻石（trigger-time=1）、完工 1 石头。
2. 实际控制器运行两 tick，progress=2；煤已从 3 减到 2，钻石已支付。执行副本的下标 1 被标为已触发。
3. 实际 RecipeManager.replaceRecipes 以**同 ID** 新配方替换：延迟输入改为 1 绿宝石，完工产物改为 1 钻石。此时没有绿宝石。
4. 对仍在内存运行的旧加工保存实际 NBT，然后分别验证继续运行和恢复运行两个分支。

| 分支 | 实际结果 |
|---|---|
| 不恢复实例，旧加工继续运行 | 保留开工执行副本，正常产出旧配方的石头 |
| 新控制器 load 相同 NBT，配方表为新定义 | 从新配方复制需求，把旧的 `triggered:[1]` 套给新绿宝石需求；不用绿宝石便完工，产出新配方的钻石 |
| 新配方从头正常开工的对照 | 到延迟绿宝石门槛时停在 progress=1，不能越过缺料门槛 |

两个保存后分支是独立对照：复用已付后的相同输入余额，并把对照产物移除以恢复保存时的空输出状态；没有把两条实验分支的产物加在一起当作同一次游戏加工复制资源。

**原因与位置：**

- `MachineControllerBlockEntity.executionCopyOf:1625-1635` 在内存中按激活 ID 保留原执行副本，即使 RecipeManager 中相同 ID 已换对象，也继续原定义。
- `saveAdditional:2472` 起只保存 activeRecipeId、普通进度/并行/修改器和 `scriptExecution`；没有保存这次开工使用的完整配方定义或可验证版本。
- `load:2529` 起清除 executionRecipe/executionRecipeSource，只保留 pendingExecutionState，下一次 resolveRecipe 按当前配方表的 ID 复制新定义。
- `MachineRecipe.saveExecutionState/loadExecutionState:71-79` 仅保存/恢复已触发需求的**数组下标**，只检查下标是否在当前数组范围内，不核对该位置的类型、资源、数量或所属定义版本。

这里不是 P04 的解析/网络丢字段，也不是 P06-01 的最终 tick 空间问题。即使每个单独配方和当前 NBT 都是合法数据，保存前后也可能采用不同配方的“已付款”和产物。

**建议：** 让在途加工保存与内存冻结采用一致的定义身份策略：保存可验证的开工定义快照，或保存定义指纹并在恢复时明确处理不匹配。需求换位/改材料/改数量不能仅靠下标移植付款状态。若选择取消不兼容的在途加工，应有明确状态和可追踪的取消策略，不能悄悄按新定义继续；不能用“所有触发标记都清空重付”替代设计，这会重复收取旧加工已经支付的成本。回归覆盖相同内容新实例、改材料/产物/顺序、已付/未付触发项与缺失配方。

## P06-04：持续成型但机器身份变更时，旧机器专属加工仍继续（P2）

**最小复现：**

- 两台普通机器共用输入/输出仓口，区别是相对坐标 (1,0,0) 的外壳：A 要石头、B 要泥土。使用通用控制器上下文。
- 注册一条**仅属于 A** 的三 tick 配方：1 煤 → 1 钻石；B 没有这条配方。
- 内存世界先放石头外壳。实际匹配与控制器第一 tick 成型 A、支付煤并进入 progress=1。
- 将外壳状态改为泥土，通过实际 StructureChangeTracker.mark 请求复查，再执行控制器 tick。真实匹配器此时找到 B，machineId 已是 B，但 A 的 activeRecipeId 仍在、progress 推进到 2。
- 下一 tick，控制器在 B 身份下结束 A 的加工，并向真实原生输出仓口放入钻石。

本例通过实际 findMatch/端口收集改变机器身份，**没有直接把 be.machineId 反射改成 B 来制造结论**。外壳、仓口均在可控内存方块表中，尚未运行真实游戏里的放置/破坏事件或区块边界。

**原因与位置：** `tickServer:631-705` 更新 machineId 和 hatches；previousMachine 与新 ID 不同只触发通知。`updateFactoryMode:1061-1071` 仅在普通机/工厂模式切换时复位；A、B 都是普通机，直接返回。后续 `resolveRecipe:1615-1622` 只按 activeRecipeId 查配方，不验证它是否属于当前 machineId，执行副本继续使用旧定义。

**旧版对照：** 本地 TileMultiblockMachineController.onStructureFormed:624-625 在 prevMachine 与新机器不同的时候调用 resetRecipe；TileMachineController.resetRecipe:378-380 清除 activeRecipe/context/临时修改器。本版在机器身份变化时没有保留同类复位边界。

**影响与建议：** 不再满足 A 结构时仍能完成 A 的在途专属配方，机器归属和加工状态不一致。尚未验证这能在用户整合包里绕过某种等级/成本门槛，不泛化为已证实安全越权。应在身份切换时明确终止/迁移旧加工，并校验活动配方对当前机器的归属；若支持一条配方属于多台机器，还需明确组/并行/冻结修改器在切换时的处理，不能只加一个 belongsTo 判断便声称所有迁移安全。同一机器动态段调整与真正更换机器 ID 应分别验证，不必一律取消合法的结构复查。

## 正常恢复对照

| 检查 | 实际结果 |
|---|---|
| 已消费催化剂的时长加成 | 原时长 8、催化剂 duration×0.5，消耗催化剂后保存；新控制器恢复后仍按 4 tick 总时长完成，没有因仓口已无催化剂而丢失加成 |
| 已付款延迟需求 | 保存前已经支付绿宝石，恢复后不要求第二颗；开工煤与催化剂也不重复扣取 |
| 未付款延迟需求 | 保存时未到触发点、没有绿宝石；相同内容的新配方实例恢复后到期仍正确停住，补入一颗后只支付一次并完成 |
| 输入组、进度和冻结并行 | 组 1 与 progress 保留；两并行样例按 10 FE/t 恢复、最终产生 2 个产物，没有按初始一并行误结算或再次扣开工煤 |
| 脚本修改器与自定义数据 | 持久能源×2 正确恢复，没有重复叠成×4；临时修改器保留到正常完成时清除，持久修改器和自定义 counter=7 保留 |
| 配方已被删除 | 恢复后清空缺失的在途配方，不凭空生成产物，未到期的钻石不扣；已付煤不返还属于取消策略，本轮不新增“移除定义必须退款”的要求 |

这些结果来自真实 NBT 方法、新控制器实例及当前 tick 入口。仓口库存由装置维持在已付后的状态，没有执行完整世界的仓口序列化、物理磁盘读写或跨进程重启。

临时修改器在 abort/销毁后的普通机生命周期仍留 P11 与工厂子批对照；本轮没有把对“结束/销毁”含义的推测直接列为新缺陷。工厂 pendingFactoryState/threadList 的恢复代码虽被普通 load 触及，但实际多线程状态尚未验收。

## 1.12.2 比较与边界

除机器身份复位外，读取本地 ActiveMachineRecipe(NBTTagCompound):51 起、RecipeThread.deserializeActiveRecipe 等恢复调用：旧版同样按 recipeName 在当前 RecipeRegistry 找配方，再恢复 tick/parallelism，并不是保存完整开工定义。因此不能声称旧版任意热更/换位需求天然安全。P06-03 的证据是**当前内存冻结与存档恢复的直接不一致及新成本被跳过**，无需假设旧版所有重载行为正确。

本轮只通过 RecipeManager.replaceRecipes 模拟配方表替换，没有完整触发 Forge 资源重载监听链。静态复核 MachineLoader/MachineRegistry 的更新、控制器 resolveRecipe，以及全仓相关复位调用，没有发现一个会在相邻重载入口统一取消这些普通在途加工的生产调用；不把搜索结果当作实机 `/reload` 验收。

没有新增有测量依据的性能优化项。后续需要真实存档恢复、服务端重启/区块卸载、不同朝向/动态结构、机器更新期间的客户端状态，以及多人/真实脚本重载验证，分别归 P06 后续、P07、P10、P11。
