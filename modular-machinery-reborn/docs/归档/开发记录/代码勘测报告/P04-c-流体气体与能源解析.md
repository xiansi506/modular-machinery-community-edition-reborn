日期：2026-10-29。基线 **0.121.0 / Minecraft 1.20.1 / 协议 12**，Git HEAD `f94ba299e37f0975ac5255f90671f990bacfc61a`。本轮只勘测、复现和记录，没有修改业务代码、构建正式包、启动游戏、部署或提交推送。

## 范围与验证方法

检查 `RequirementTypes.FluidType/EnergyType`、`FluidRequirement`、`EnergyRequirement`、`MekanismModule.GasHandler`、`GasRequirement` 的字段、单位、边界、方向/阶段和网络往返；复核 builder 对流体/能源的输出与 `MachineRecipeJS` 参数转发。`GasIo`、`IngredientIo`、`EnergyMath`、`EnergyAccess/LongEnergyStorage` 仅检查理解这些需求所需的契约及少量正常结算，完整事务/并行与后端集成分别留给 P05/P08/P09。

离线夹具从当前源码重新编译 18 个相关核心类，使用真实 Forge 注册表及 Mekanism **10.4.16.80** API，在独立进程创建气体注册表并登记测试气体，手动调用实际兼容模块的需求注册方法。运行真实解析器、FriendlyByteBuf、FluidTank、LongEnergyStorage 和 MachineRecipe 的 start/tick。没有运行 Forge 模组生命周期、真实网络、管道、ME、Flux/DE、Rhino 或 JEI。

| 类型 | 现行字段与默认值 | 单位/阶段 |
|---|---|---|
| fluid | fluid 必填；amount 缺省 1；chance 缺省 1；perTick 缺省 false | int mB；输入开工/输出完工，perTick=true 改逐 tick |
| energy | energyPerTick 缺省 0；方向来自 io-type | long FE/t；始终逐 tick；并行/时长补偿另算 |
| gas | gas、amount 必填；chance 缺省 1 | int mB；开工/完工一次性；要求已注册现代气体 ID |
| gas_pertick | 与 gas 共用字段读取器，类型本身决定逐 tick | int mB/t；气体 API 的载体量为 long |

本版文档明确以 `fluid + perTick` 替代 `fluid_pertick`，后者没有注册；本地 1.12.2 的 `RequirementTypeFluidPerTick.createRequirement` 也返回 null。没有将这个既定类型合并方式计作缺口。

## P04-07：不存在的流体 ID 被默认空流体接受（P2）

**分类与确认：** 加载诊断/功能问题，离线原生复现。错误流体名称没有在加载时被拒绝，得到无法满足的空流体需求。

**最小复现：**

```json
{"type":"fluid","io-type":"input","fluid":"audit:no_such_fluid","amount":1000}
```

真实注册表 `containsKey(audit:no_such_fluid)` 为 false，`getValue` 却返回其默认值 `Fluids.EMPTY`。实际解析成功，需求 `fluid().isEmpty()` 为 true，执行副本仍为空；实际 `MachineRecipe.canStart` 无法满足它。显式 `minecraft:empty` 也被接受为空需求。

**原因与位置：** `recipe/RequirementTypes.java:351-361` 仅判断 `getValue` 是否 null。当前 Forge `ForgeRegistry.getValue:209-218` 对查不到的键回退 defaultValue，因此“非 null”不能证明流体已注册。相邻 gas 查找已有排除 EMPTY_GAS 的逻辑；物品读取也明确排除了 AIR。

**2026-10-31升级载体入口扩展：** [P06-c2a](P06-c2a-升级定义实例与效果汇总.md)发现UpgradeLoader.private readMapping也仅检查非null；真实ITEMS不含audit:no_such_item，仍把默认Items.AIR作为合法载体映射返回。表现为错误配置未拒绝/载体无效，没有免费升级复现，沿用P04-07同一注册表默认值校验根因。上文“物品读取排除AIR”针对配方物品读取器，不覆盖该独立升级入口。

**旧版与边界：** 本地 1.12.2 `RequirementTypeFluid.createRequirement` 使用 `FluidRegistry.getFluid` 并在 null 时拒绝，不能把该判空模式直接等同现代带默认值注册表的行为。此次证明到实际解析/副本/开工检查，没有运行控制器 GUI 或观察游戏日志，也没有发现此输入导致服务端崩溃。

**建议：** 结合注册表存在性/别名规则确认有效键，拒绝 EMPTY 作为配方资源，并报出配方 ID 与原始名称。保留有效现代 ID、裸名称默认命名空间和既有注册别名。回归包含未知键、显式空流体、无效 ResourceLocation、正常水/熔岩和网络往返；不要只改为另一个同样会返回默认值的 getter。

## P04-08：缺少或拼错能源速率时，按零耗能配方加载（P2）

**分类与确认：** 作者输入校验/加工成本一致性问题，离线复现到实际 recipe tick。

下面两种输入均成功加载，得到 `energyPerTick == 0`：

```json
{"type":"energy","io-type":"input"}
```

```json
{"type":"energy","io-type":"input","energyPertick":40}
```

在没有任何能源仓的实际 HatchCollection 上，生成执行副本后 `MachineRecipe.canTick` 和 `tick` 均成功。第二种包含作者可能拼错大小写的预期耗能，实际不要求也不扣除 40 FE。

**原因与对照：** `recipe/RequirementTypes.java:392-395` 缺少 energyPerTick 时直接补 0，构造器允许零速率。旧版 `RequirementTypeEnergy.createRequirement` 明确要求字段存在且为 number；当前 typed builder 则拒绝零/负速率。不能把 JSON 未声明值与作者显式写出的合法零值混为一谈。

**建议：** 对能源需求先校验 rate 字段存在和类型，再做精确 long 范围读取，缺失时报字段定位。显式 0 是否继续允许应保留/明确现行语义，不因补必填校验就擅自改变所有已有零速率配方。补遗漏字段、拼写错误、显式 0、负数、正确整数、typed/raw 路径的回归。未确认玩家越权修改服务器配方或完整机器免能运行的实机场景。

## P04-09：同路径气体可遮蔽显式命名空间指定的资源（P3，条件性）

**分类与确认：** 资源身份一致性风险，在真实气体注册表构造冲突并原生复现。标准注册表只有 Mekanism 氧气时，正常解析已通过；触发还需要整合包/附属模组注册同路径的 `modular_machinery_reborn:oxygen`。当前项目没有内置这样的气体注册项。

**复现：** 先正常登记 `mekanism:oxygen` 并验证解析/往返；随后额外登记另一个 Gas 到 `modular_machinery_reborn:oxygen`。真实注册表对明确的 `mekanism:oxygen` 仍返回原气体，但同样写 `"gas":"mekanism:oxygen"` 的实际需求解析器返回了新 MMR 气体，执行副本也保留这个错误身份。

**原因与位置：** `compat/mekanism/MekanismModule.java:260-275` 把输入解析成 ResourceLocation 后，先用 MMR 命名空间加同一个 path 查找，再回退原始键。代码注释明确选择了这条优先策略；本项记录它对显式资源 ID 的实际冲突影响，而不把优先策略当成实现遗漏。需求种类的旧命名空间别名与化学资源自身的注册身份应分别评估。

**建议：** 完整 ID 优先按写出的命名空间精确解析，简写/历史别名通过明确规则处理；若继续保留当前优先策略，应把这种遮蔽行为和冲突诊断公开给作者。测试同时存在/仅存在一侧/两侧都不存在以及复制后的资源身份。此处没有做真实附属模组注册时序或管道结算验收。

## 已登记问题的扩展

### P03-09：从 int 延伸到能源 long 读取，不新增编号

以下均运行实际 JSON 解析器，原值在转换后才做限幅：

| 输入 | 实际结果 |
|---|---|
| energyPerTick = 9223372036854775808（Long.MAX_VALUE + 1） | getAsLong 回绕后被构造器归零 |
| energyPerTick = 18446744073709551617（2^64 + 1） | 1 FE/t |
| energyPerTick = -18446744073709551615 | 1 FE/t |
| energyPerTick = 1.9 | 1 FE/t |
| energyPerTick = 1e1000 | 0 FE/t |
| fluid/gas 的 amount = 4294967297 | 均为 1 mB |

位置为 `RequirementTypes.java:358,394` 和 `MekanismModule.java:338`。旧版能源/流体/气体读取器也使用 getAsLong/getAsInt，数值越界的一部分属于沿袭缺陷；本轮不把它们重复登记成新漏洞。合法 long 的精度没有因此失效，下面另列正向验证。建议统一整数读取助手时同时覆盖 long，不只修机器定义的 int 字段。

### P03-07：非布尔 perTick 会改变结算阶段，不新增编号

`RequirementTypes.java:359` 直接 `getAsBoolean`：字符串 `"ture"` 被解释为 false，配方仍加载。用实际 100 mB 水罐、每份 10 mB 的需求执行 `start` 后再执行 3 次实际 recipe tick：布尔 true 最终剩 70 mB；字符串 "ture" 最终剩 90 mB，变成只在开工支付一次。该行为扩展原布尔校验问题，不另编号。

建议要求 JSON boolean，覆盖 true/false、遗漏、字符串、数字和 null。此处的 perTick 开关是本版新增 JSON 表达，旧版对应逐 tick 类型的 JSON reader 返回 null，不能把开关强制描述成旧版同名字段的回归。

## 正常路径、对照与未计为新问题的观察

- fluid 输入/输出、逐 tick 标志、概率、selector-tag、固定并行标志在实际网络往返中保留。直接由 Java 构造的带 NBT FluidStack 可无损复制，getter 返回的栈被修改后不污染定义。
- gas/gas_pertick 的两个方向、旧需求命名空间别名、气体类型、Integer.MAX_VALUE 数量、概率与通用元数据在正常注册表中往返保留。缺 amount、零/负 amount、错误 chance 类型/范围、未知气体和 EMPTY_GAS 均拒绝。本轮只查需求，不把成功注册需求等同真实气体端口已验收。
- 能源 1、9007199254740993（大于 2^53）、9000000000000000000 和 Long.MAX_VALUE 的 JSON/网络值均精确。每个值都用真实 LongEnergyStorage 分别验证实际 recipe tick 消耗到零、或从零生成到该值。另验证精确乘 2、乘 2 后乘 0.5、0.5 修改器向下取整，以及最终溢出按文档饱和。这些正常路径已通过，不重复报告 0.118.4 已修复的精度问题。
- typed builder 的混合流体/能源配方经完整 serializer 往返后，标志与大额 long 均保留，没有剩余字节；typed 零流体/能源数量被拒绝。这里只运行 Java builder，没有运行 Rhino/JavaScript Number 转换。
- 现行 JSON fluid 读取器忽略 nbt/nbt-display。实际测试中，声明 `nbt:{grade:"high"}` 的需求仍匹配无标签水，不匹配携带该标签的水。旧版虽然解析这些字段并保存到 tagMatch/tagDisplay，但标准 RequirementFluid 结算使用 required.copy()，本地标准 JEIComponentFluid 也直接提供 required，未见把上述两个字段附回去。本轮不将这些旧 setter 的存在等同旧版已实现对应的运行功能，也不据此新增一个移植缺口。若后续决定支持流体 JSON NBT，需单独定义匹配、产物、显示和错误字段规则。
- 流体缺 amount 默认 1，与摘要侧的差异仍沿用 P01-03，不在此再次计数。零/负流体数量被构造器限到 1，气体对零/负数量明确拒绝，属于需要统一说明的现行差异；本轮没有把所有限幅策略都算成新漏洞。
- 本轮没有性能基准或新的已证实性能优化项；没有把减少几行代码或改变缓存结构当成性能收益。
