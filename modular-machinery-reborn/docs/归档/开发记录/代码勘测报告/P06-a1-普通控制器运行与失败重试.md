## P06-01：最后一 tick 的需求与完工输出不共享容量规划（P2）

**分类：** 合法资源组合下的加工阻塞与额外支付。配置由配方作者提供；没有依赖恶意网络包或故障处理器。这里有两个方向相反的实际复现，根因相同，合并为一个编号。

### A. 逐 tick 输入本能腾出空间，却永远不允许执行

一 tick 配方：开工消耗 1 煤，每 tick 消耗 10 default Will，完工输出 10 default Will、max=100。输入和输出端口指向同一余额 100 的有效测试环境，二者访问相同资源身份。

- 连续调用实际控制器 tick 三次：煤只扣一次，从 3 变为 2，配方保持激活、progress 一直为 0，Will 一直为 100。
- 对相同需求执行实际 recipe.tick → recipe.finish 对照：前者把 Will 从 100 降到 90，后者补到 100，均成功。

**原因：** 控制器 `nextProgress >= maxProgress` 时先检查 canFinish（931），它看见旧环境已达到输出上限，直接 return；本 tick 的输入永远没有机会腾出空间。与 P05-02 不同，这里不是事务内部的“实仓模拟忽视虚拟变化”，而是控制器根本没有把即将发生的 tick 变化纳入最终空间检查。

当前 BloodMagicBackend:59、83 确实按世界/区块标识 Will，两个方向的仓口可能访问同一环境；但本轮只运行测试 Access，**没有实际血魔法世界复现**，也不把旧版 Will 的需求种类与本版新增逐 tick 能力混为一谈。

### B. 逐 tick 输出先占掉完工空间，付费后反复无法结束

一 tick 配方：1 煤开工、每 tick 5 FE、每 tick 输出 10 水、完工再输出 10 水。两项流体输出使用**同一个正常原生输出 FluidTank**，容量 100、初始 90。该例不使用共享魔法端口或受限/异常存储。

| 操作 | 实际结果 |
|---|---|
| 第一次控制器 tick | canFinish 单独看 10 水能放下；随后扣 5 FE、逐 tick 注水到 100，实际 finish 已无空间而失败；配方仍激活、progress 回到 0 |
| 取走 10 水，再 tick | 又扣 5 FE、又逐 tick 注水到 100，仍无法 finish |
| 取走 20 水，再 tick | 本次逐 tick 与完工的合计 20 水都有空间，成功结束；累计已付 15 FE，而一 tick 加工本来只需一次 5 FE 支付 |

**原因与位置：** `MachineControllerBlockEntity.java:930-970` 分别执行 canFinish、canTick/tick、finish；两个检查各建独立事务，不能发现两种输出在同一 tick 竞争空间。finish 返回 false 后，又把已支付完的进度退到 maxProgress-1，下一次重试重新支付最后一 tick。

该例中逐 tick 流体已实际产出，不应描述成“只有能源凭空消失”，也没有据此泛化为所有输出配方都能免费刷资源。问题是最终共享预算没有成立，且完工重试重复支付 tick。普通无逐 tick 输出竞争的“输出满则停住且不扣 FE”对照正常。

**建议：** 最终 tick 的逐 tick 需求与完工需求在同一候选状态中联合检查，区分“最后 tick 尚未支付”和“已支付完、仅等输出”的状态；finish 迟到失败后不能简单退进度再付一遍。实际提交与事件顺序还需保留 RecipeTick END 的既定语义、结果概率和合法回调变化，不能不加区分地合并/撤销外部副作用。回归至少包含输入腾空间、两类输出争空间、正常满输出免费等待，以及 finish 失败后的重试。

这不要求重做 0.118.1 的单 tick/延迟需求修复；本轮检查的是当前控制器跨阶段资源组合。

**2026-10-31扩展：** [P06-b1](P06-b1-工厂普通线程调度与失败重试.md) 已在实际工厂控制器tick/FactoryHostImpl中复现同样的逐tick水输出/完工水输出竞争及重复最终tick支付，沿用P06-01，不另编号；工厂普通满物品输出的免费等待对照正常。红石对照同时确认工厂引擎会保留已付批次，因此下面的P06-02仍限普通控制器。

## P06-02：红石通电会中止已支付加工，断电后再次扣一次性材料（P2）

四 tick 配方：每批 1 煤、每 tick 5 FE、完工 1 石头；煤初始 3，能源 100，输出为空。

1. 正常 tick：煤剩 2、能源 95、progress=1，配方激活。
2. 装置将强红石读数改为 15，再实际 tick：activeRecipeId 清空、progress=0，煤仍为 2、能源仍为 95，没有产物。
3. 红石读数恢复为 0，再 tick：重新开工，煤再扣为 1、能源 90、progress=1，原来的已付料加工没有恢复。

**位置与影响：** `tickServer:609` 读取强信号，721-725 的红石分支调用 abortCraft；`abortCraft:1457-1467` 清除进度、激活配方、并行/分组和冻结修改器。一次性材料在开始时已经实际扣除，没有返还。正常玩家用红石控制机器即可经过这条分支；离线测试改变的是 Level 返回的信号，没有运行真实红石方块网络。

**1.12.2 对照：** 本地 TileMachineController.doControllerTick:65-69 在有强信号时只设置 redstoneEffected 并 return，没有清除 RecipeThread/ActiveMachineRecipe；信号撤销后的 canCheckStructure 会要求复查。这里是暂停与取消的行为差异，不能把“停机时不扣 FE”当成加工已安全保留。

**建议：** 普通控制器的红石门暂停加工并保留已开工状态；恢复后沿用原配方、进度、输入组、并行和冻结修改器，不再次执行 start 或 startCommands。真实结构失效/明确销毁配方仍可走原取消分支，不应为了修复红石暂停而让已拆毁机器继续运行。补充真实红石、跨暂停存读档和与结构变化组合的验证，后两类属于 a2/P07。

## 通过的运行对照

| 场景 | 实际结果 |
|---|---|
| 普通两 tick 加工 | 一次扣 1 煤；第一 tick 扣 5 FE、progress=1；第二 tick 再扣 5 FE并产出 1 石头，清除激活状态；未重复支付开工材料 |
| RESET / STILL / DECREASE | 先正常运行到 progress=2，再断能源；分别保留 0/2/1 进度，但都仍激活。补能后从对应进度推进，不再扣煤 |
| cancelIfPerTickFails=true | 失败后清除激活配方、进度归零，已付煤不返还，符合显式销毁语义；与红石暂停问题区分 |
| RecipeCheck START / END 取消 | 直接 Java handler 否决时均未扣煤/FE，配方未激活 |
| RecipeTick START 暂停 | 已扣开工煤，但该 tick 不扣 FE、不进度；解除 handler 后继续，未再次 start |
| RecipeTick END 暂停 | 该 tick 已扣 5 FE、不进度；这是接口明确的语义，未当成新漏洞；解除后继续 |
| 普通物品输出已满 | 一 tick 配方扣一次开工煤后保持激活，连续等待不扣 FE；腾出槽后仅支付一次最终 tick 并产出 |
| 有配方但缺输入 / 没有配方 | 前者 IDLE 且有失败键，后者 NO_RECIPE 且无失败键；均未错误开工 |
| 输入组锁定及延迟输入重试 | 选择第一个能开工的组 1；它缺延迟材料时，组 0 即使有煤也不被挪用，进度与 FE保持；补回组 1 后延迟材料只扣一次并最终完成 |

“事件对照通过”仅指本轮直接 Java handler 在实际派发位置产生的结果，不等于完整 Forge 插件、Rhino 重载或任意回调副作用已验收。未新增有实测依据的性能优化项。

## 注释与前批线索复核

MachineControllerBlockEntity:1477-1483 和 FailureAction 类注释仍称“普通机 progress=0 即未开工，RESET 会再付一次性输入”。实际普通机已经以 activeRecipeId 区分开工，applyFailureAction 只改进度，本轮 RESET 对照证实不会重新支付。这里记录为**过时维护说明**，不照着旧注释杜撰一个 RESET 吞料问题，也不因修文档而改坏目前正确的状态模型。

P05-08 的 startFailure 溢出仍有明确 API 复现和诊断调用者，但本轮普通空闲搜索的 startableGroup 会先设一并行、正常并行搜索也有支付边界，未确认这种普通自动开工路径能自行选出其溢出样例。运行中修改器/工厂失败事件的可达性继续在相应子批核对，不扩大发生范围。

暂留 a2 的线索：机器 ID/定义变化时对在途执行副本的保留、pendingExecutionState/冻结修改器与输入组的存读档恢复；普通机 abort 时临时脚本修改器的生命周期继续由 a2/P11 核对。这里只追踪调用，不将其写成已确认问题。
