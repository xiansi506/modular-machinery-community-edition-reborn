## P05-08：正常检查拒绝溢出后，失败诊断再次预留并抛 ArithmeticException（P2）

**触发与原生证据：**

| 输入条件 | 正常检查 | 随后实际 startFailure |
|---|---|---|
| 物品输入 Integer.MAX_VALUE、固定 2 并行、原生仓仅 1 煤 | canStart/start 均返回 false，煤不变 | 抛 ArithmeticException |
| 流体输入 1500000000、固定 2 并行、原生仓 100 水 | canStart 返回 false，水不变 | 抛 ArithmeticException |
| 气体输入 1500000000、固定 2 并行、本地气体池 100 氧气 | canStart 返回 false，气体不变 | 抛 ArithmeticException |
| 普通物品输入 2、原生仓 1 煤 | 正常短缺 | 返回正常失败键，不抛异常 |

数量本身在配方允许的 int 范围内；需要当前固定并行使总量超出 int。夹具显式设置两并行，未证明普通机器在所有缺料情形都会选出该并行。也未证明普通玩家能上传配方或任意设置这些参数。

**原因与位置：** ItemRequirement.reserve、FluidRequirement.reserve、GasRequirement.reserve 以 Math.multiplyExact 拒绝过大总量；MachineRecipe 的 suppliedModifiersPlan、checkStart/checkPhase 等路径捕获 ArithmeticException 并返回 false，但 `recipe/MachineRecipe.java:721-734` 的 startFailure 直接再次 reserve，没有相同边界处理。因此“普通缺料/数量过大”本可作为失败结果返回，读取失败原因时反而变为未捕获异常。

**实际调用链：** DiagnoseCommand:455 在 canStart 失败后调用 startFailure；MachineControllerBlockEntity:1704、1967 有诊断/失败记录调用，FactoryEngine:490 在逐 tick 失败事件中读取该方法。这些调用者没有在相邻调用处转换该 ArithmeticException。潜在影响是异常向诊断命令或 tick 调用方传播；**本轮没有启动游戏，不写成已经实机导致服务器崩溃或存档损坏。** P06 仍需核对真实固定并行、运行期修改器变化和失败事件的组合可达性。

**2026-10-31补充：** [P06-b1](P06-b1-工厂普通线程调度与失败重试.md) 已通过真实工厂控制器tick/FactoryHostImpl补出该组合：合法两并行开工后，运行期物品输入倍率改为1500000000，再遇到缺电，构造失败事件时重新诊断已付开工料发生精确乘法溢出，异常传播出控制器tick，失败handler尚未收到事件。该证据扩大已确认的实际调用范围，沿用P05-08；Level/修改器条件仍由离线装置提供，没有真实Forge/Rhino游戏崩溃证据，也未证明普通空闲搜索会直接选择超量开工样例。

**建议：** 检查与失败原因生成共用可表达“数量过大”的预留结果，或在同一边界把 ArithmeticException 转换为稳定失败键；不能只在某个 GUI/命令层吞掉异常，也不要删除支付路径的精确乘法检查。覆盖多资源、固定并行、修改器放大量与普通短缺对照。

## P05-09：自动输出接收器执行抛错后，已经提取的能源没有补偿（条件性 P2）

**最小复现：** 原生 LongEnergyStorage 余额 100，收发限额均 1000，输出上限 40。测试目标的真实 IEnergyStorage 模拟接收答应 40，但 EXECUTE 在修改目标之前抛 IllegalStateException。实际调用 `EnergyAccess.push` 后异常向外传播，源剩 **60**、目标仍为 **0**，源丢失 40；源自身有足够的退款能力。

这需要外部目标发生执行异常，不是正常接收路径普遍丢能，也没有确认用户安装的 Flux Networks、Draconic Evolution 或某个 Forge 能源方块实际会按此方式抛错。测试故障接收器负责提供异常条件，源与移动函数为当前生产代码。

**原因与调用入口：** `energy/EnergyAccess.java:22-30` 在第 26 行先 extract 源，第 27 行再执行目标 receive；只有目标正常返回短接收量才到达退款分支。异常路径没有记录/恢复处理。普通能源输出仓 `MachineHatchBlockEntity.tickEnergyOutput:344` 实际调用 push，并可对接外部能力，不是没有生产调用者的闲置工具方法。

**正向对照：** 相同原生源与一个“模拟答应 40、执行仅收 10”的测试目标配对，push 返回 10，源剩 90、目标 10，总量仍为 100。说明现有正常短接收退款有效，问题在执行异常分支。

**建议与约束：** 为可恢复的原生源定义外部转移失败协议，记录源/目标的已知变化，并对目标在写入前/部分写入后抛错分别验证；失败诊断要保留原始异常和结算事实。**不能无条件捕获异常后把源全部补回**：目标若已经收到了资源再抛错，会由丢能变成复制。任意外部能力没有通用事务接口，本项目应明确可保证的异常恢复边界；真实可选能源后端留 P09 验证。

## P05-01 的输出移动扩展：方向包装器不能作为可逆退款源

把同一个原生余额 100 的源包为 `new EnergyPort(source,false)`，目标模拟收 40、执行仅收 10。实际 push 提取 40 后尝试退回 30，但输出方向包装器拒绝 receive，最终抛 `Energy destination refused transfer and source refused its refund`；源为 60、目标为 10，损失 30。沿用通用“假定逆向可恢复”的 P05-01，不新增编号。

**当前标准仓口的对照很重要：** tickEnergyOutput 传入 backing `this.energy`，没有传入该输出方向 EnergyPort。原生 backing 的退款对照通过，不能用包装器样例声称普通仓口在正常短接收下也会丢能。包装器是当前真实项目类型，目标的部分接收由测试实现提供；其他实际调用方/真实外部限制仍待 P07/P09。

## 跨资源组合与异常检查

本轮七组运行结果均退出 0；PASS 包含缺陷和预期失败的成功复现，不表示已修复。

| 场景 | 实际行为 |
|---|---|
| 一次性混合 start | 5 煤、40 水、40 氧气、40 测试魔力一起支付；测试魔力执行只移动一半时，前面资源全部恢复。逐 tick 能源在 start 保持 100，没有提前扣除 |
| 五资源同 tick | 通过延迟物品输入，把 5 煤与每 tick 40 水/40 FE/40 氧气/40 测试魔力放进同一实际 tick；canTick 不写入实仓，tick 成功后各项准确减少 |
| 末端部分执行 | 测试魔力实际只移动一半，tick 返回 false；各资源写入计数确认五种资源确实都已被修改，随后余额全部恢复，延迟需求未被标记完成 |
| 写入后抛错 | 测试魔力先改余额再抛异常；五种资源均恢复，原异常保留，延迟需求仍未完成 |
| 预检查短缺 | 测试魔力预先为 0，tick 拒绝，煤、水、能源与气体均不部分支付 |
| 混合 finish | 物品输出满时不生成流体/气体/魔法；测试魔法末端短接收时已经写入的物品/流体/气体恢复；解除故障后重试一次，各输出仅产生一份。没有运行控制器自动重试调度 |
| 恢复步骤自身抛错 | 两个测试 restore 先后抛错，仍尝试其余恢复并还原原生物品；执行异常保持 primary，恢复异常通过 suppressed 保留，不互相覆盖 |
| 一个来源在提交前变化 | 预留物品与流体后，外部把水 100 改成 90；commit 整体拒绝，煤不扣，保留水的新值 90 |
| 能源名义用量 | EnergyUsage.of 正确处理固定不并行项和普通项、不改变原需求并行状态，累计超界按既定策略饱和到 Long.MAX_VALUE；它是名义 FE/t，不是实际转移仪表 |
| long 辅助边界 | signed 16-bit 菜单词重组得到准确非负 long；大余额的 FE 视图夹到 int 而不截断真实存量；Long NBT 与 modify(Long.MIN_VALUE) 按库存边界安全处理 |

以上“回调”主要是能力的部分执行、写入后异常和恢复故障钩子，**不是已运行的 Forge 事件监听器或 KubeJS 脚本回调**。脚本取消、脚本修改数量/输出、命令副作用、跨 tick 重试/卸载、两次独立事务竞争同一环境，分别归 P06/P07/P09/P11；不以本批结果承诺任意外部副作用可回滚。

## 本地 1.12.2 对照

- `hellfirepvp/modularmachinery/common/crafting/helper/RecipeCraftingContext.java:350-380,390-421` 按需求逐项执行 start/finish，之后运行命令。本版跨资源工作副本/统一恢复是新的机制，本轮验证其守恒，不把旧版逐项执行当成要求复制的原子性保证。
- 旧版 `TileEnergyOutputHatch.java:80-118` 根据实际 transfer 返回量再扣本地能源；现代 push 先提取源再执行目标，以避免超出源可支付量，但因此需要明确执行异常时的补偿边界。不能直接照抄旧版转移顺序并宣称任意目标都可事务恢复。
- 旧版 long 数量与当前 int 需求总量保护路径不同。P05-08 依据的是本版 canStart 与 startFailure 的直接不一致，未声称旧版有完全同形的诊断方法或已通过相同世界复现。
