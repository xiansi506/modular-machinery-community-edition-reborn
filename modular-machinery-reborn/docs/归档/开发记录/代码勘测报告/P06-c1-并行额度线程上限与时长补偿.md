## P06-11：时长缩短到已完成进度以下，仍强制支付额外逐tick需求（P2）

**条件与分类：** 运行中的脚本时长修改可改变当前目标工期。普通控制器与工厂普通线程均复现，不需要异常仓口、概率输出或共享输出争空间。此例使用默认关闭的能源时长补偿，和P06-01最终两阶段空间规划问题不同。

配方：原工期6 tick，开工1煤，每tick5 FE，结束1石头，failure-action=still。

| 操作 | 普通机/工厂的实际结果 |
|---|---|
| 正常运行4 tick | 煤只扣一次、progress=4，能源100→80 |
| 添加运行时duration×0.5 | 当前目标变为3 tick；已经完成的进度4足以达到新目标 |
| 将现有能源取空，运行下一tick | 输出有空位，却不结束，仍激活且progress=4、目标3，因为还要求逐tick5 FE |
| 再供5 FE，运行下一tick | 又实际扣5 FE后才产石头并结束 |

取空剩余能源是装置中的外部资源变化，前4 tick实际已支付20 FE；本例不是把80 FE外部取走也算作配方消耗。问题是完成判定已经满足时仍额外要求一次5 FE，不要求退还工期变化前已经支付的历史费用。

**原因与位置：** 普通控制器`MachineControllerBlockEntity.java:912-913`重算maxProgress后，`930`以progress+1进入最后tick路径，仍执行canTick/tick，没有先处理progress已达到新时长的状态。工厂`FactoryEngine.java:455-456`更新duration，`473-481`同样先询问下一tick/支付，再判断完成。资源短缺因此可把已经完成新工期的加工留住，其他失败动作还可能修改其进度；本轮实际演示的是STILL等待及补5 FE后完成，不将未运行的其他动作写成复现。

**旧源对照：** 本地1.12.2 ActiveMachineRecipe.tick:79-85先重算totalTick，若isCompleted直接返回working，不再ioTick；117-118按tick>=totalTick判断。旧版也有时长动态变化，不能仅用“每次游戏tick都要付资源”解释现代差异。旧源未运行，不能据此保证旧版所有延迟输入组合正确。

**建议：** 显式处理“当前目标工期已完成、等待结束结算”，区分它和“尚需支付最后一tick”。输出堵塞重试也不能重复支付历史tick；与P06-01状态设计协调，但保留普通一tick配方仍必须支付其唯一tick的规则。不要简单跳过整个MachineRecipe.tick就宣称完成：存在延迟触发项、实时检查、概率和事件时，需明确哪些未结算义务仍应处理，不能顺带豁免未付费用。补充普通/核心/普通工厂线程、缩短/延长、完成前后边界、满输出与暂停事件的回归；不重做0.118.1已经正确的常规一tick时序。

## P06-12：普通线程额度下调只限制新建槽，不能停止旧槽开新批次（P2）

**触发：** 公开脚本extraThreadCount在正常范围2→0；基础max-threads=0，无核心线程。无需超过short范围、手改NBT、无限线程数或普通玩家发包。两条不同配方各耗时2 tick，分别每批1煤/1铁锭，输入各3份。

1. extraThreadCount=2时实际创建两个普通槽并开工，输入各剩2。
2. 通过实际公开脚本方法调为0。下一tick两批正常完成，但随后立即分别付新一批输入，各剩1，两个线程仍工作，maxOrdinaryThreads实际已经是0。
3. 继续运行，三批各自都完成，才因原料耗尽空闲；不是只容许下调前已付的那一批。
4. 此时两个空槽仍在。补回各1份原料，再tick，又都扣料开工，额度仍为0。

**位置与原因：** `FactoryEngine.canAccept:230-240`无论额度多少都接受已有空闲普通槽；`nextFreeThread:337-341`先复用空槽，普通上限检查在`352`的新建路径才执行。`tryRestart:554`起也不检查普通线程额度，已完成旧槽可一直开始下一批。

当前Schema的max-threads说明将其定义为可同时运行的普通配方数，0表示没有核心就不运行；Host接口同样称当前允许的普通线程数。额度可以不强制销毁已经支付的加工，但这不等于旧槽永久获准开始新加工。该限制目前仅在创建时兑现，运行期减少额度没有相应排空/准入策略。

**1.12.2边界：** 旧TileFactoryController.offerRecipe先用已有空槽、hasIdleThread:521-533也不以当前额度排除旧空槽；旧FactoryRecipeThread.tryRestartRecipe没有现代期望的收缩判断。因此这项含继承的运行期限制缺口，**不声称旧版动态缩容正确，也不把它评为安全越权**。本版公开运行时额外线程数的功能契约仍需要明确落实。

**建议：** 额度减少时保留已付在途批次，但按明确且稳定的槽选择策略拒绝超额槽再次开工/立即重开；必要时完成后退休。不能只改nextFreeThread漏掉tryRestart，也不能reset整个引擎直接丢掉已付料，更不能误限不受普通上限约束的核心线程。回归至少包括2→0、N→较小N、忙/空闲混合、恢复额度、存读档及核心同时存在。若项目选择“只限制槽创建”的兼容策略，应明确改功能说明及状态展示，而不是继续称其为当前运行上限。

## P06-10：公开Java setter接受的大额线程数会被short存档截断（条件性P3）

**已确认的范围：** 方块实体公开Java方法和存档格式不一致，属于附属模组/API维护边界。**未确认正常脚本或普通玩家能触发这次溢出**；本轮对脚本入口的对照恰好证明它已有正确保护。

- `MachineControllerBlockEntity.setExtraThreadCount:402-404`只限制不小于0，实际接受40000，当前maxOrdinaryThreads也是40000。
- `saveAdditional:2517`写short，40000变为-25536；`load:2581`直接getShort读入，没有非负校正。
- 基础max-threads=0的恢复实例因此得到负的普通额度，不给正常1煤配方开工，煤保持1。没有为样例分配四万个槽。
- 真实`MachineControllerAccess.setExtraThreadCount:48`先限制到32767；调用它传40000，实际得到32767，存读档仍是32767。负值也经底层setter变为0。指南明确写0–32767，这条公开脚本路径正常。

**建议：** Java边界统一限制为可保存范围，或升级为int格式并兼容已有short；读取旧/异常负值时使用明确校正。当前仓内调用者是已做上限保护的脚本桥，不把直接Java复现改写成用户默认会遭遇的问题。旧版写short却读byte（TileFactoryController:591/659），本版修正为读short后仍存在int setter超宽；这不证明两代世界存档可直接互换。

控制器附近“没有仓内调用者/脚本尚未接线”的注释已经过时，只列维护清理，不根据它忽略当前脚本桥。

## 并行分配与时长补偿对照

| 场景 | 实际观察 |
|---|---|
| 原生并行控制器 | 默认普通级4；设置2/负值/超限得到2/0/4；存读档保留。两个当前值2+3求和，再加内部1受机器5限幅；同一集合内把第二个调0后立即读到新贡献 |
| 数值边界 | 两个INT_MAX测试贡献在集合中饱和，内部再加1也不int溢出；零贡献底数1，parallelizable=false返回1 |
| 普通机冻结与下一批 | 内部2+实际并行控制器当前2，先开4并行；控制器拨0后该已付批仍按4完成，下一批用2，不中途少付/多产 |
| 整配方预留约束 | 两条共享煤输入、5煤、输出仅余2空间、机器上限6，实际只开2；共付4煤、每tick6 FE、最终填入2产物。未把各需求独立上限相加 |
| 核心+普通并行账本 | ceiling5时核心3并行+普通3并行是合法状态：各线程有基础1，额外份额Σ(p-1)=4。重开排除自己的旧份额；上限降1时旧批仍冻结3，完成后下一批各为1。前四tick实际每tick15 FE |
| 事件并行边界 | 普通/工厂START把计算6降2，END再请求100，实际仍2并只付2；未突破前阶段已收紧额度 |
| parallelize-unaffected | 并行6需要煤6、固定钻石1，实际只付一钻石、产6份；固定需求不错误压成并行1 |
| 真实内存配置与整批支付 | 基础4 tick、10 FE/t，时长×0.5/×2分别用2/8 tick；普通/工厂均实跑。补偿开启总成本40 FE，关闭成本20/80 FE；各付一次开工料、产一次结果 |

工厂的并行额度扣的是每条配方的额外复制数p-1，不是把所有线程的p之和强制限制到结构上限。旧TileFactoryController.getAvailableParallelism:400-417也是相同账本，floor为1；不能把ceiling5时两个线程总数6当成超额漏洞。并行额度缩小保留已付复制数，与P06-12普通槽是否可开始**新批次**是两个不同层面。

### P05-05补充实际调度调用链

开启真实内存配置的时长补偿，基础2 tick、duration×2、需求1 FE/t，结构上限6，起始6煤/3 FE。实际普通和工厂自动开工都只选择3并行；第一tick煤剩3、FE剩2。相同初始6煤/3 FE的独立原生对照，将配方固定6并行后，实际canStart/canTick/start/tick均成功，煤变0、该tick只需3 FE。

此处验证的是**开工和一次tick的可支付数量**，没有声称同一仓总共3 FE足够完成后续全部4 tick。`EnergyRequirement.parallelLimit:145-152`先把单份0.5 FE取整到至少1再做除法，提前收窄到3，后续精确搜索找不回6。[P05-05](P05-c1-能源事务与并行补偿.md)保持原编号；本轮把原API反例扩展到真实控制器自动路径，不重写能源数值规则。

### 继承的时长取整观察，不新增缺陷编号

补偿开启时，基础4 tick、100 FE/t，时长×0.375产生原始1.5 tick，执行时四舍五入为2；补偿仍使用原始4/1.5的float倍数。实际工厂每tick支付266 FE，两tick共532，和名义400不完全相等。

旧版也使用未经整数工期取整的比率，再由执行工期四舍五入；本版还保持既定能源最终取整/最小正数策略。注释中“总成本保持不变”对非整除、极短工期等条件并不严格成立，建议补充这一边界或单独确定整数总预算策略；**不在本轮把继承规则直接替换，也不声称当前存在已约定的任意小数精确守恒保证**。本例与P05-05的上界低估不同，修并行预估不自动解决整批舍入差异。
