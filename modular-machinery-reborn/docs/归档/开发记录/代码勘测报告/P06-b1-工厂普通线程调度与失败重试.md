## P06-05：首个受限空闲普通线程让后续空闲线程与新槽位拿不到任务（P2）

**分类与触发：** 创作者使用公开线程视图 `setRecipes(list)` 限定普通线程可接配方。无需恶意客户端、异常存储或核心线程。未设置这种限制的普通调度对照正常。

最小复现使用 max-threads=2、普通线程 0/1。A、B 各运行一 tick 后耗尽自己的材料，形成两个空闲槽。C 需要一钻石、耗时三 tick；此时钻石已放入正常输入仓。

1. 将线程 0 限定为只接 A；线程 1 无限制，可以接 C。
2. 连续三次真实控制器 tick：两个线程都空闲，钻石不扣，C 不开工，hasIdleThread 仍为 true。
3. 再直接驱动实际引擎 220 tick：普通空闲线程 1 被正常清理；带脚本配方限制的线程 0 保留，仍拦住 C，连尚未用满上限时创建新线程也到不了。
4. 仅把线程 0 的限制清为空列表，同样输入、配方和机器下，下次真实控制器 tick 立即开工 C，扣一钻石、progress=1。

**原因与位置：** `factory/FactoryEngine.java:273-281` 只取一个 nextFreeThread，然后 nextCraft 返回 null 就 break 整个普通调度循环。`337-341` 总先返回列表里的第一个空闲普通线程，没有结合该线程能否接当前候选。线程 0 不接 C 的事实不能推出线程 1 或新槽也不接 C。`FactoryThread.java:282` 保护带 scriptRecipes 的空闲线程不被清理，因此并非简单等十秒就能自动恢复。

公开调用链为 `script/MachineControllerAccess.java:164` → FactoryThread.setScriptRecipes；手动接触底层线程是装置方式，实际功能入口并非不存在。没有在本轮运行脚本引擎。

**建议：** 对空闲线程分别求可接受且能付费的候选；一个线程不匹配时继续检查其他线程，最后才考虑是否需要新建普通槽。限制每次调度中无进展的重试，避免改成无限 while；维持核心线程优先、配方 ID 去重、线程上限、资源支付后重新检查及稳定线程编号。回归要同时覆盖“两个空槽”“只有一个受限空槽但可新建”“上限满”“线程规则使输入变得可付”等组合。

本地 1.12.2 的 TileFactoryController.offerRecipe:432-453 直接把上下文给首个空闲普通线程；FactoryRecipeThread 的 recipeSet 主要进入线程搜索任务。本版新增的普通线程公开配方限制与调度选择需要共同成立，不能只凭旧代码也取首个空槽就判定新场景正确，也不声称旧版通过了本版脚本场景。

**2026-10-31扩展：** [P06-b2](P06-b2-核心线程同步与规则变更.md)已在实际控制器中复现另一种空闲目标：通用核心带物品输入×2修改器时付不起仓内1煤，核心阶段尝试失败后，普通fallback又选中同一核心并break，导致原本只需1煤、尚可新建的普通槽不开工。保留其修改器、只将该核心接受列表改为无关配方，普通槽就能开工。仍属P06-05，不另编号；修复需兼顾核心fallback，而不只跳过有配方列表限制的普通空槽。

## 既有 P06-01：工厂也会重复支付最后一 tick

使用一 tick 配方：开工一煤，每 tick 5 FE、输出 10 水，完工再输出 10 水。正常输出 FluidTank 容量 100、初始 90，无故障处理器。

| 操作 | 实际工厂结果 |
|---|---|
| 第一次 tick | 一煤扣除，FE100→95，逐 tick 水90→100，finish 失败，线程仍激活且 progress=0 |
| 取走10水再 tick | FE95→90，水再次补满，finish 再失败 |
| 取走20水再 tick | FE90→85，逐 tick 与完工都能放下，最终结束；一煤始终只扣一次 |

`FactoryEngine.java:473-478` 的 canFinish 先单独看旧仓，`480-481` 再支付逐 tick，`531-535` 实际 finish 失败后退到 duration-1，重复了普通控制器的相同根因。输出的逐 tick 水已实际产生，不能描述成所有资源凭空消失或泛化为免费刷资源。普通一 tick 物品输出满的对照：保留已付煤、等待期间不扣 FE；清空输出后仅付一次 5 FE并产一石头。

继续沿用 [P06-01](P06-a1-普通控制器运行与失败重试.md) 的联合最终预算和“已付最终 tick、只待结算”建议，不另计一个新问题。本轮工厂例验证了流体竞争方向，没有重跑 Will 方向，也没有真实可选后端世界。

## 既有 P05-08：工厂运行期能实际走到未捕获诊断溢出

这次不再只对 API 手动设置一个开不了工的超量并行：

1. 原生输入有4煤、能源100；机器并行上限/内部并行为2，配方允许并行，耗时6，每复制一份开工1煤、每 tick 5 FE。
2. 真正工厂 tick 正常开工两并行，煤剩2、progress=1；其开工费用完全可付。
3. 用实际 MachineScriptState 添加有限的、仅影响物品输入的持久倍率 1500000000，并把能源降为0，模拟运行期资源不足。修改器是管理员/脚本作者的配置条件，不是普通玩家任意上传。
4. 下次实际控制器 tick：canTick 先正常报告能源不足；构造 FactoryRecipeFailureEvent 时，startFailure 重新预留已付的开工物品，1500000000 × 2 的精确乘法抛 ArithmeticException。
5. 异常直接传播出控制器 tick；失败 handler 收到次数为0，线程仍保留 progress=1 和原来的已付煤状态。未执行清除/失败动作，也未发生新的支付。

调用链是 MachineControllerBlockEntity 工厂分支:737 → FactoryEngine.tick/tickThreads/tickThread:490 → MachineRecipe.startFailure:721-734 → ItemRequirement.reserve 的 Math.multiplyExact。更新 [P05-08](P05-d-跨资源异常与覆盖收口.md) 的可达性证据；仍未运行 Forge 游戏，**不能写成已经实机确认服务器崩溃、世界损坏或无需作者条件就必现**。修复既要稳住诊断数值边界，也要解决下面的诊断阶段错误。

## P06-06：逐 tick 失败事件诊断的是开工输入（P3）

**分类：** 失败原因错误，影响事件消费者和作者诊断；未证实单凭此项就能丢资源或越权，故按 P3，不因为存在失败事件就夸大严重程度。

实际配方6 tick、开工1煤、每 tick 5 FE。唯一一煤已正常支付，运行到 progress=2，再把能源清零。实际事件 `cause()` 返回 `craftcheck.failure.item.input`，虽然此时并不需要再付开工煤；正确失败阶段是能源逐 tick。对纯5 FE/t、没有一次性输入的配方，在同样缺电时，事件 cause 为 null。RESET/STILL/DECREASE 三种机器失败动作都复现错误煤原因，动作本身与补能后的恢复则正常。

**位置与原因：** `FactoryEngine.java:487-490` 把 recipe.startFailure 的结果当作逐 tick 失败原因。`MachineRecipe.java:723-725` 只走 isStartPhase，明确排除了逐 tick 需求；所以并不是当前 tick 支付返回了错误键，而是取错了阶段。FactoryRecipeFailureEvent 文档虽然公开说明目前从 startFailure 取值，这也无法让原因与本次失败相符。

本地 1.12.2 `RecipeCraftingContext.ioTick:238-298` 从实际逐 tick doIOTick/resetIOTick 结果收集失败消息，`TileFactoryController:293` 再将线程当前状态消息传入失败事件。这里只做旧源静态对照，没有运行旧版游戏。

**建议：** 逐 tick 检查/提交返回带失败阶段和原因的统一结果，再用于事件；覆盖能源、流体、延迟触发项、提交迟到拒绝及多需求共享资源，保留“不必还需要已付开工料”的语义。单纯把 startFailure 重命名、把 null 兜底为“缺物品”或再次执行真实支付都不能解决问题。读取原因也应无资源副作用。

## 通过的对照与优化候选

| 场景 | 实际观察 |
|---|---|
| 两条不同普通配方及立即重开 | A耗时2、5 FE/t，B耗时3、7 FE/t；各两批，最终各2产物、共62 FE；一次性输入各付两次。A完成事件先于下一批启动，重开当 tick 不多付下一批 tick；max-threads=2未越界 |
| 共享唯一开工煤 | 两个不同配方都需要同一煤，只有一条开工；支付后候选重查，没有重复占用同一份输入 |
| 共享5 FE逐 tick | 两条配方均已付各自开工料；只有第一条推进1、第二条保持0，余额0，无双花或负数；第二条仍武装等待下一次能源 |
| RESET/STILL/DECREASE | 缺电后保留0/2/1进度，仍激活；补电继续，未再次扣开工煤 |
| 事件检查及暂停 | RecipeCheck START/END 否决都不支付；FactoryRecipeTick START取消不付tick资源，END取消保留已付资源且不推进；解除后继续原批 |
| 销毁覆盖 | failure handler 能把默认true改false保留，也能把默认false改true销毁；销毁不退开工料，符合显式行为 |
| 输入组与延迟输入 | 组1开工后不借组0的料；缺延迟煤时保持进度/FE，补回组1后只付一次延迟煤并完成；同配方立即重开仍使用原组，不擅自挪用组0 |
| 工厂红石门 | 强信号期间引擎 tick 计数、进度、FE不动，撤信号后同批继续，不重复付煤；P06-02仍明确限普通控制器，不能推广到工厂 |
| 空闲清理 | 无规则/状态的普通空槽在实际引擎200 tick超时及20 tick扫除后删除；脚本限定槽保留，正是P06-05不能靠等超时恢复的条件 |

**优化候选 P06-O1（计数证据，尚无耗时基准）：** 32条无资源需求配方、1个输入组、4个空普通槽，实际控制器一个 tick 内调用 host.availableRecipes **5次**，4槽都已启动后的下一 tick 为0次。源码结合blocked集合可推导本次 runnable 单独创建 **32+31+30+29+28=150** 个单组执行副本，尚不含每次prepareCraft/ActiveCraft的副本；150是由实际调用次数与已知列表长度推导，未声称直接仪表统计了所有分配。

当前 `searchAndStart` 每次 begin 成功后重跑整个 runnable，哪怕最后一槽已填满也先重建一次再发现没有目标。当前每次扫描还会 prepareStart/canStart，输入成本随候选配方数R、输入组G、启动槽数T增加，大致为O(T×R×G)加上需求成本。可先去掉无剩余目标时的尾部重建，并考虑本 tick 保留定义/组候选、逐次重新验证实际支付；不能跨真实支付直接缓存canStart，也需处理回调修改规则/库存、催化剂和新配方对象。没有耗时/GC/服务器TPS数据，不将其描述成已证实严重卡顿，亦不把固定调用计数当已实现加速。

FactoryEngine/FactoryThread 的长注释仍有“无事件/无脚本层”“普通线程保留maxThreads+1”等旧说明，与当前实现和严格上限测试不符；仅列维护清理建议，不能照这些文字再次报已不存在的行为。
