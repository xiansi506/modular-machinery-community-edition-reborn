## P04-11：机器配方复用重建需求时丢失高级选项（P2）

**原因：** `DynamicMachineAdapter.copyModified:76-91` 先完整网络复制，再对 item/fluid/energy 重新构造对象；最后仅回写 selector-tag 和 parallelize-unaffected，没有回写 scriptOptions。即使声明的 modifiers 为空，也经过这条路径。

**实际复现：** 源物品输入带 `trigger-time:5`、`script-checker:"audit_checker"`、`fuel-time:true`、selector-tag 和固定并行。实际 generateAll 生成的配方中，后三项中的选择标签/固定并行保留，但 scriptOptions 为空，triggerTime 从 5 变成 0；原需求 isStartPhase=false，生成需求变成 true。该复现直接说明延迟输入变成开工输入，checker/燃料语义也失去对应元数据；没有运行实际脚本回调。

**影响与建议：** 机器之间复用配方会改变作者声明的需求行为，涉及通用选项的类型不限于物品。重建后统一复制不可变定义元数据，运行期状态按执行副本规则另行处理；不要靠继续增加两三个 setter 漏掉未来字段。回归包含无修饰符、触发/重复、输出检查、脚本、燃料/耐久和三个重建类型。本地 1.12.2 的 RequirementItem.deepCopyModified 对 checker、itemModifierList、consumeDurability 等也有明确复制逻辑，不能以旧版只改数量为由省略现行元数据。

## P04-12：重复的归属机器/等价别名产生相同配方 ID，加载器抛异常（P2）

**触发：** 声明 machine 数组包含 `"target"` 和 `"modular_machinery_reborn:target"`，两者解析到同一台实际存在的机器。重复写相同 ID 也有相同风险。

**实际复现：** 仅一个父机器源配方，generateAll 返回两条同 ID 配方。原生 RecipeManager.replaceRecipes 抛 IllegalStateException；进一步运行实际 RecipeAdapterLoader.apply，同样在回注时抛异常。没有使用伪造的 ID 碰撞，碰撞由正常别名解析与重复遍历共同产生。

**位置：** `RecipeAdapterRegistry.generateAll` 的 declaration.machineIds 遍历（约 57-75）与 generatedId；`RecipeAdapterLoader.apply` 最后 replaceRecipes。确定性哈希函数本身正常：同声明/归属/源得到相同 ID，恰好暴露了重复归属未去重。

**建议：** 在归属解析或生成边界按解析后的 ResourceLocation 去重，或明确拒绝重复归属并报声明位置；保留不同声明/不同目标的独立身份。补重复字符串、裸名/完整 ID、不同有效目标以及原配方 ID 与生成 ID 冲突的诊断。此次证明到加载器 apply 抛异常，完整在线重载、客户端同步及失败后继续加工未验，不声称已观察实机停服。

## P04-13：适配器数值烘入丢失合法 long 精度，并可能把超范围时长变成 1 tick（P2）

**原生结果：**

| 源与修饰符 | 实际生成结果 |
|---|---|
| 源能源 9007199254740993 FE/t；空 modifiers | 9007199254740992 FE/t |
| 源时长 Integer.MAX_VALUE；duration ×2 | 1 tick |

**原因与位置：** `DynamicMachineAdapter.copyModified` 的能源重建把 long 交给 double 版 RecipeModifiers.apply；空修饰符也先丢失超过 2^53 的低位，再 Math.round 转回 long。`copyOf:64` 对时长 Math.round 得到 long 后强制转 int，回绕成负数再被 Math.max(1,...) 限成 1。AdapterMinecraftFurnace 中的时长/物品数量烘入也存在相同先强转 int 再限幅的形状，本轮没有逐个复现其超大输入。

**建议：** 能源复用精确 long 修饰算法/共享数值契约，空修饰符保持原值；时长和数量应在转换前检查范围并按明确的饱和/报错策略处理。保留适配器已采用的历史舍入规则，不应为修复溢出随意把所有 round 改成 floor。回归无修饰符、加法/乘法、分数、最终溢出和跨重载稳定性。此问题位于适配器烘入，普通能源解析/执行的 0.118.4 精度修复仍然正常，不把后者重复报告为未修复。

## P04-14：超出 float 范围的修饰系数被接受为 Infinity（P2，极端作者输入）

实际解析 `{"target":"energy","io":"input","operation":0,"multiplier":-1e1000}` 成功，value 为 Float.NEGATIVE_INFINITY。把该修饰符用于实际 EnergyRequirement 的 100 FE/t，perTickDraw 得到 0。

**位置：** `RecipeModifier.requireFloat:231-238` 只确认 JSON number，再 getAsFloat，没有有限值检查。源 JSON 指数是合法数字表示，但不能由当前 float 系数表示；不应等到运行算法才决定如何处理无穷值。本地 1.12.2 RecipeModifier.Deserializer 同样 getAsFloat，因此这里是继承的校验缺陷，不是新移植回归。

**建议：** 加载时拒绝转换后非有限的单个系数，附字段/来源；组合多个有限系数仍可能溢出，聚合后的策略另需在 P05 验证。此次没有运行整台机器或实际资源仓，不把单个需求速率计算写成实机免费加工已验收。

## 已有编号的扩展与正常结果

- **P03-09：** operation=1.9 与 4294967297 都被实际解析成 MULTIPLY（1），应在 getAsInt 前检查精确整数和范围，不另编号。
- **P03-07：** affectChance 字符串 "ture" 被接受为 false，使机会修饰变成数量修饰的匹配类别；旧版 Deserializer 对此字段明确要求 boolean。沿用布尔校验编号。
- 所有目标 × 两个方向 × 两个操作 × 机会标志的网络往返通过；普通 (value + adds) × multipliers 及方向/机会隔离正常。样例输入值 4、加 2、乘 3，再仅输出乘 2，输入得 18、输出得 36。
- 确定性 ID 在源数值修改后保持稳定，目标改变则隔离；源时长/数量修改会重建新内容。没有依靠固定枚举序号建立身份。
- 实际原版熔炼源可生成输入、输出、20 FE/t 和历史 120 tick 时长；移除源后没有生成结果。该时长是旧版适配器约定，不要求复制原版熔炉自身的 200 tick；经验数据的现行省略也有源码说明，不另报缺口。
- 实际加载器正常 apply 后移除声明占位，保留原配方并加入生成配方；无声明的再次 apply 不改变 ID 集合。此处验证的是 apply 幂等，不等于完整 reload/失败事务验证。
- 非 item/fluid/energy 类型的修饰符烘入未扩展，是当前首版适配器明确记录的覆盖限制；没有在本轮新增气体/魔法或第三方配方适配器。
- P04-01～03 的网络复制限制也涉及适配器使用的同一复制通道，沿用已有编号，不因另一个调用者而重复登记。本轮未逐条重跑这些复制夹具。
- RecipeModifier 的目标列表和“种类仍是常量”等类注释已有过时内容，需维护；这属于诊断/注释整理，没有证明新的性能收益，不单独计漏洞。
