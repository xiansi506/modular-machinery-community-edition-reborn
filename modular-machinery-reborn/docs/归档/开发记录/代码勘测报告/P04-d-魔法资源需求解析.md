| 需求 | 已核对的数量/默认值与选择字段 |
|---|---|
| mana、lifeessence | amount 必填，非负整数，上限 Integer.MAX_VALUE；无变体；min/max 默认 0/Integer.MAX_VALUE |
| aura | amount 必填非负整数；aura-type 必填资源 ID；min-aura/max-aura 默认 Integer.MIN_VALUE/Integer.MAX_VALUE |

普通魔法 perTick 缺省 false，写出时要求 boolean；压缩空气的逐 tick 属性由需求类型决定，显式 perTick 必须一致。空气旧 time 仅兼容读取，实际加工时长仍由 recipeTime 决定。空气为 mL，压力为 bar；灵气保留 API 原始单位，没有另乘 100000。

## P04-10：意志类型在 JSON 与 typed 创建入口的大小写处理不一致（P3）

**分类与确认状态：** 创建入口一致性/作者易用性问题；JSON 和构造器行为已原生复现，typed 调用链静态确认，完整 Rhino 调用未运行。

实际 JSON `will-type:"VENGEFUL"` 被 `MagicRequirements.Handler.read:32-37` 归一化为 `vengeful`，随后正常加载、复制。直接传入相同字符串的 MagicRequirement 构造器则抛 Invalid will-type，小写 vengeful 正常。`MachineRecipeJS.willInput/willOutput/willPerTick:115-127` 把调用者字符串原样传给 `magic`，在生成交由 JSON 解析的对象之前先构造 MagicRequirement，因此大写参数先被拒绝，无法到达 JSON 的归一化步骤。

**影响与边界：** 同一意志变体采用不同创建入口时，接受范围不同。文档说明 will-type 大小写归一化，当前标准小写写法正常；没有发现这会选中错误资源或绕过成本检查。不把原生构造器测试写成真实整合包脚本报错已验收。

**位置与建议：** `magic/MagicRequirement.java:27`、`magic/MagicRequirements.java:32-37`、`kubejs/MachineRecipeJS.java:115-127`。在 typed 边界复用相同的变体归一化和验证，或明确限制该入口只接受规范小写；不必放宽内部构造器对规范值的约束。回归包含五种变体、大小写、非法值、typed/raw 脚本与网络往返。

## P03-09 扩展：整数校验发生在 double 转换之后

`MagicRequirements.number:15-20` 先 `getAsDouble()`；`MagicRequirement:18-23` 再比较 floor 与 int 范围。常见小数和溢出会拒绝，但这时原 JSON 的精确小数部分可能已经消失。

| 实际 JSON amount | 实际原生解析结果 |
|---|---|
| mana/lifeessence/aura：1.0000000000000001 | 三者均接受为 1 |
| mana/lifeessence/aura：2147483647.00000001 | 三者均接受为 Integer.MAX_VALUE |
| mana：1e-1000 | 接受为 0 |

最后一项还通过实际执行副本和 MachineRecipe.start：提供一个余额为 0 的有效测试魔力端口，开工成功，余额仍为 0。此输入原本是正的非整数，按声明的整数字段规则应在加载阶段拒绝。没有使用真实魔力仓或证明某个玩家可以上传该输入。

**正向对照：** 1.5、2147483648、负数和非有限数在普通魔法整数入口被拒；压缩空气的 `getAsBigDecimal().intValueExact()` 对近整数小数 1.0000000000000001 也会拒绝。这里不是所有整数校验都失效，而是先转 double 丢掉原始精度后的边界遗漏。

**旧版对照：** 本地 1.12.2 `kport/modularmagic/common/utils/RequirementUtils.getRequiredInt` 使用 getAsInt，本身也会截断；其 getRequiredDouble 甚至调用了 getAsInt。本版普通小数资源的读取已改善，不能描述成旧版所有边界均更严格。当前代码声称整数校验时仍应基于原始 JSON 数值进行精确验证。

**建议：** mana、aura、LP 及其整数阈值在转换前读取精确 int，再转为内部需要的 double；WILL/EMBER 继续采用允许小数的有限值规则。不能为了修复整数入口就把所有魔法资源都限制成整数。沿用 P03-09 编号，与前面 int/long 读取一并处理。

## 正常检查结果

- 32 组实际需求往返：五种普通魔法的输入/输出 × 一次性/逐 tick，以及空气两种类型 × 输入/输出 × 正压/零压/负压。保留 family、variant、数量、上下限、方向、阶段、selector-tag 和固定并行标志；空气压力和类型身份也保留。
- 55 个非法 JSON 用例被拒：缺数量、错误类型、负数、巨大指数、常见整数小数/溢出、倒置上下限、错误 aura-type/will-type、非法 pressure、缺压力、矛盾逐 tick 标志和非法旧 time。整数零、压力零和负压按现行设计接受，没有自动当成漏洞。
- 默认意志类型/0～100 边界、灵气负下限及原始数量、余烬数量别名和小数、压力条件专用的空气 0 数量正常读取。aura-type 语法合法并不证明真实世界中存在对应灵气类型；实际端口匹配留 P09。
- 混合 mana、compressed_air_pertick、ember 的完整配方经实际 serializer 往返，无剩余字节，空气仍为专用需求类。未将一次成功往返当作后端资源支付验收。
- 本地 1.12.2 RequirementTypeAura 和 RequirementAura 的上下限分别用于扣除后保留下限、生成后上限；当前文档与此一致。没有把输入不使用输出上限等既定语义误报成缺陷。
- 空气数量、负压和旧 time 的现行约定已对照项目联动说明；本轮未重新验收旧气动/余烬集成或真实现代 API，未用历史离线套件的通过结果替代本轮证据。
