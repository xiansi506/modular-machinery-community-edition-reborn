## P06-05扩展：通用核心线程自身付不起，会拦住能开工的普通线程（P2）

本次不需要限定普通线程的配方列表。创建一个recipes为空的运行时核心线程any，表示可运行本机器任意配方；max-threads=1，尚无普通线程。公开ThreadAccess给any添加持久的“物品输入数量×2”修改器。唯一配方耗时4，基础开工费用1煤；普通输入仓放1煤。

1. 连续三次真实控制器tick：核心线程始终空闲，煤仍为1，普通线程数量仍为0。
2. 此时核心需要2煤，确实付不起；可新建的普通线程没有该修改器，1煤足够，线程上限也未占用。
3. 只把any的接受列表改为一个无关配方ID，保留×2修改器、仓库和机器设置不动。下次tick立即创建普通线程，以基础1煤开工，progress=1；核心仍空闲且修改器保留。

**根因仍是槽选择：** `FactoryEngine.java:265-271`已尝试过所有空闲核心，any无可付候选；进入普通分配循环后，`nextFreeThread:347-350`却再次返回这个空闲且recipeSet为空的核心。它再次prepare失败，`279-281`直接break，永远走不到`352-357`的普通槽创建。已有普通空槽时它们先被返回，因此本例明确要求没有可先复用的普通空槽，不扩大为所有通用核心都阻塞。

与[P06-b1的P06-05](P06-b1-工厂普通线程调度与失败重试.md)共用“一个空闲目标没有可接任务就终止全局调度”的根因，故不新编号。修复时还需避免在核心阶段已经失败后，fallback阶段重复挑同一个无法推进的核心；继续尝试其他目标或合法新槽，同时保持真实支付重检、核心优先、普通上限及配方ID去重。

## P06-07：removeCoreThread实际拒绝正在运行的线程，指南却承诺完成后移除（P3）

**分类与严重程度：** 公开API与使用文档不一致，属于作者功能/说明契约问题。代码有明确的busy保护；本轮没有据此断言这个保护本身是安全漏洞或所有忙线程必须无条件删除。未发现此项直接复制资源或损坏存档，按P3。

`docs/进阶/高级脚本指南.md:184`写：删除运行时核心线程声明，“已支付的批次完成后移除”。但 `script/MachineControllerAccess.java:127-130` 在current.isWorking时抛出 `IllegalStateException("Wait for the core thread to become idle before removing it")`，不会执行声明删除，也没有记录待移除请求。

实际公开API复现：运行时核心runtime持有一个3 tick配方，每批1煤、每tick5 FE、产1石头，输入4煤、能源100。

| 操作 | 实际结果 |
|---|---|
| tick1开工 | 煤剩3、progress=1、能源95 |
| 调用公开removeCoreThread | 收到busy异常；声明仍在，进度与库存不变，没有排队移除 |
| 在该批FactoryRecipeFinish回调中再调用 | 仍收到busy异常；事件发出时active槽尚未清空 |
| 完工回调结束 | 引擎立即开下一批，再扣1煤，progress=0但isWorking仍true；不是等完工后自动删除 |

对照直接从实际MachineScriptState删除运行时声明（不是建议作者绕过公开API）：本已付费的第二批仍推进到完成，产物总数2、煤剩2、能源70；不再开第三批，下次同步移除核心槽。证明引擎已有“删除声明后保留在途批次、完成后退出”的路径，公开删除方法没有提供指南承诺的请求方式。

现有API可以在槽空闲时删除声明，本轮也实际验证了这一正向路径。问题并非“核心线程完全删不了”。持续供料时完成后立即重开，甚至完工回调里仍视为working，因此仅让作者“等完成事件再删”也不成立；作者仍可另行否决重开使它先空闲，这需要明确流程，而不是文档所写的一次调用即排空删除。

**建议：** 明确选定公开行为。如果保留busy保护，修正指南并提供先阻止下一批开工、确认空闲后删除的可行示例；如果要兑现现有指南，让公开请求移除运行时声明，由现有核心同步/tryRestart保留已付批次并阻止重开。两者都必须保留“固定机器声明不由此API删除”的规则，并覆盖同名静态回退、满输出延迟完成、失败销毁、完工事件和存读档。当前勘测未选择或实现其中一种修复。

真实Rhino异常呈现与事件回调异常隔离留P11；本例在直接Java调用处捕获预期异常，没有把壳Level临时分离当成游戏调用的权限验收。

## 通过的核心线程对照

| 场景 | 实际结果 |
|---|---|
| 静态专属核心+通用核心+普通槽 | 依声明顺序先分配两个核心，普通上限1只再开1槽；第四配方暂不启动。前三批各产一次，空闲核心经过240引擎tick仍保留，普通槽最终清理 |
| 标识与查找 | 两个核心事件标识为-2/-3，普通为0；getRecipeThread按标识得到正确对象。删掉并重新创建运行时核心后获得新标识，不复用旧槽身份 |
| max-threads=0 | 只禁止普通槽，核心仍能开工；不把核心数错误计入普通上限 |
| 专属集合与机器归属 | 指向别的机器的已存在配方、未知配方ID均不开工、不扣煤；非空集合不会退回任意配方 |
| 重复ID | 两个核心声明同一配方，只有一条实际开工，扣一次材料；没有借核心绕过全局活跃ID去重 |
| 静态/运行时同名合并 | 运行时声明覆盖同名固定声明，只产生一个槽；空闲时删除运行时覆盖，下次同步恢复固定集合，槽对象/标识保留；固定线程本身仍存在 |
| 运行时覆盖允许集合 | createCoreThread同名更新在下次同步更改接受集合，已付旧批仍完成；旧配方不重开，新配方下一次搜索开工，身份不变 |
| 显式ThreadAccess覆盖 | setRecipes直接改变槽接受集合，后续声明同步不覆盖此显式设置，符合hasScriptRecipes优先规则；旧批结束后受新集合约束 |
| 临时/持久修改器 | 在途旧批允许当前线程能源/产出修改器生效；完成后临时产出×2消失，持久能源×2保留，新配方产出不继承上批临时效果 |
| 核心失败显式销毁 | 失败事件携带正确负标识，handler要求销毁时清空激活/临时状态，持久修改器和核心槽保留；已付煤不退款、不产额外物品，符合显式销毁语义 |
| 开工检查中删除 | RecipeCheck START和END中删除尚空闲的运行时核心，均不扣料、不为已失去声明的槽开工；下一次同步删除该槽 |
| 开工回调中新增 | 只新增声明，不修改正在遍历的引擎核心map；下一次同步才创建并开工，未发生ConcurrentModificationException |

上述“实际公开API”仅指方法主体加实际引擎，受前述Level/Java handler边界限制，不等同真实服务端脚本全链路。

## 顺序维护观察与旧源码对照

现有核心从静态声明[first,second]创建并空闲后，将当前声明重排为[second,first]，供给只够一条配方的一煤：本版仍让原first先开工，coreThreads返回旧插入顺序，既有负标识也保持。syncCoreThreads按名称刷新/增删，没有重排LinkedHashMap中的既有键。

FactoryEngine字段/访问器注释称“声明顺序”，重排后这句话不准确。未找到用户教程承诺动态重排可改抢料优先级，因此仅列维护观察：应明确保留创建顺序，或定义重排何时影响调度；若调整顺序要保持事件标识稳定，不能直接重建全部核心丢掉已付状态。没有时间/GC基准，本轮不新增性能优化编号。

本地1.12.2对照：

- `DynamicMachine.java:77、99-104`按名字保存LinkedHashMap核心预设；`FactoryRecipeThread.java:44、54-66、161-172`保存专属集合并用于线程搜索，空集合使用机器全部配方。本版空集合/名称模型与之相符。
- `TileFactoryController.updateCoreThread:477-509`增加缺少的名称、刷新集合，并直接移除不再声明的线程，全部预设为空则clear；它没有本版对已付批次排空的保护。保留已付现代批次属于本版明确策略，不把此差异当移植错误，也不据旧源码声称旧版任意删除不会丢料。
- `FactoryRecipeThread.tryRestartRecipe:142-159`完成后立即尝试下一批；本版同样立即重开，实测进一步说明为什么公开busy删除不能靠等待finish事件自然成功。未找到与本版同签名的旧运行时removeCoreThread API，不虚构两者应完全同形。

本地旧源码只做静态对照，没有运行1.12.2游戏。
