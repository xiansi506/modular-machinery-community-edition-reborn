# P03-c：配置配方与配置默认值

日期：2026-10-29。基线 0.121.0，Git HEAD `f94ba299e37f0975ac5255f90671f990bacfc61a`。本轮检查 `ConfigRecipes`、`ConfigRecipePack`、`ModConfig`、`HatchConfig`、`MagicConfig`，并追踪机器解析使用默认值及资源包发现的必要调用。未改业务代码，未运行游戏。

## 已确认发现

### P03-11：单份配方的错误 type 可使目录扫描抛异常（P2）

配置配方写成 `{"type":{}}` 时，`validate` 在 JSON 解析的 try/catch 之外调用 `getAsString()`，抛出 `UnsupportedOperationException`；`readAll` 只捕获 IOException，所以异常会向外传播，阻断扫描。实际离线调用 `readAll` 和 `onAddPackFinders` 都观察到该异常。资源包构造也调用同一个扫描入口，因此不能保证这种错误仅隔离到单份配方。尚未验证真实 Forge 事件总线、启动或 `/reload` 对异常的最终处理，不直接写成已实测的游戏崩溃。

位置：`recipe/ConfigRecipes.java:83-90,107-130,138`、`recipe/ConfigRecipePack.java:27-29`。配置由作者控制。建议严格检查 type 的类型，并确定逐文件拒绝或整次加载失败的策略；对对象、数组、null、数字、缺失和正确字符串分别验证，错误应带文件路径。

### P03-12：空目录启动后，首次添加配置配方不能仅靠 reload 发现（P2）

`onAddPackFinders` 在 `readAll().size()==0` 时直接返回，没有向资源包仓库注册来源。之后添加第一份配置配方，仓库 reload 只遍历已经注册的来源，无法发现这个配置资源包。离线使用实际 AddPackFinders 监听方法和 `PackRepository` 复现：空目录收集来源为零；写入配方后仓库 reload 仍无该包；重新调用发现事件并注册来源的对照可找到包。

当前本地 Forge 源码中的 `ServerPacksSource.createPackRepository` 在仓库创建时发布 AddPackFindersEvent；当前 ReloadCommand 字节码使用现有仓库进行 reload，支持上述调用链。测试未实际执行游戏命令。位置：`recipe/ConfigRecipes.java:134-156`。建议无条件注册可重新扫描的来源，在来源发现阶段决定是否输出包，并覆盖缺目录、空目录、首份新增和最后一份移除。

### P03-13：工厂默认值在首次类加载后固定（P2，配置更新场景）

`MachineDefinition.DEFAULT_MAX_THREADS`、`DEFAULT_HAS_FACTORY` 和 `FactoryThreadModel` 对应常量在静态初始化时读取配置；之后 schema 用这些常量为省略字段的机器填默认值。离线通过真实 ForgeConfigSpec 更新配置，从默认 10/false 改为 20/true 后，配置 getter 已返回新值，但重新解析机器仍得到 10/false。显式字段不在这个测试范围内。

位置：`machine/MachineDefinition.java:68-76`、`factory/FactoryThreadModel.java:54-66`、`machine/MachineSchema.java:226-236`。验证采用同一进程先初始化类、再替换内存配置；未验证实际配置文件监听和首次启动的类加载顺序，不能据此断言所有启动配置都失效。建议解析时查询当前配置，或明确并落实重启要求；同时核对工厂控制器的启动预声明限制，不把重载变成注册新方块的入口。

## P03-02 的补充影响：两端本地默认配置

机器原始 JSON 的同步还缺少服务端已经采用的默认值上下文。实际 schema 在模拟的服务端通用配置下解析省略 `max-parallelism` 的 JSON，结果为 64；换成模拟客户端配置后，实际 `parseForClient` 对同一文本得到 128。配置通过真实 ForgeConfigSpec 设置，未进行双进程联网。模组注册配置类型为 COMMON，当前 Forge ConfigSync 字节码只选择 SERVER 配置进行握手同步，不能假定 COMMON 自动保证两端一致。

这与 P03-02 缺少变量上下文共同影响同步定义的自包含性，保留该编号、不重复计数。应同步服务端最终采用的字段或完整解析上下文，并验证默认并行、工厂和颜色等相关设置；测试本轮只直接覆盖 max-parallelism。位置：`config/ModConfig.java:432-435,496-498`、`machine/MachineSchema.java:188-207`、`network/MachineDefinitionSyncPacket.java:133`。

## 已观察的失败行为与正向验证

- 错误 JSON 在 `validate` 中记录错误后仍会被资源包暴露。实际 MultiPackResourceManager 和 SimpleJsonResourceReloadListener.scanDirectory 测试表明，它可遮住低优先级的同 ID 合法资源，最终该 ID 不出现在解析结果；低优先级资源单独存在时正常。这符合资源包覆盖后不自动回退的行为，不单凭此将其算作漏洞；修复时须明确是保持失败、跳过坏覆盖，还是拒绝整次重载。
- 已有 ConfigRecipePack 重新打开时能读取修改后的内容；旧实例保留旧快照，改名为非 .json 后新实例不再暴露原资源。使用实际构造器和资源读取完成验证，未调用完整 RecipeManager.apply。
- `HatchConfig` 和 `MagicConfig` 容量 accessor 基本上查询当前 spec，但已创建仓口的容量是在构造阶段保存的；文档已有重新加载方块/世界的要求，本轮不将该已说明的限制自动计为缺陷。菜单整数截断仍归 P02-02。
- 配置配方扫描会在发现及打开资源包时读取磁盘；尚未测量大型目录的读取量与耗时，不声称存在已验证的性能故障。
