### ⚠️⚠️ `git push` 的 TLS 陷阱：必须加 `-c http.sslBackend=openssl`

**症状**：`git push` 报

```
fatal: unable to access 'https://github.com/…': schannel: AcquireCredentialsHandle failed:
SEC_E_NO_CREDENTIALS (0x8009030e) - 安全程序包没有可用的凭证
```

**关键：这与凭据/令牌无关。** 把令牌直接写进 URL 也一样失败，所以**不要**去折腾 `gh auth`、
凭据助手或重新登录。已排除：`gh auth status` 正常、`gh auth token` 取得到（40 字符）、
`gh api user` 返回 `xiansi506`、远端 URL 正确、无代理、系统时间正确、`credential.helper` 两处都配了。
真正的现象是**本机 git for Windows 的 Schannel 后端连 TLS 都握不上手**（同一台机器上
`curl.exe https://github.com` 也返回 **HTTP 000**，而 Go 写的 `gh` 能通）。

**修法**（已实测推送成功，`8d85cc3..9691b1f main -> main`，退出码 0）：

```powershell
git -c http.sslBackend=openssl -c http.version=HTTP/1.1 push origin main
```

**判定指纹**：`gh api user` 能通 **而** `curl`/`git` 报 schannel → 就是这个坑，不是认证问题。
**顺带**：该命令会打印一行 `sh.exe: *** fatal error - couldn't create signal pipe, Win32 error 5`
（MSYS 的噪声，与沙箱的命名管道限制有关），**它出现在成功推送的输出里，不是失败信号**——
别被它误导成没推上去；看 `main -> main` 那行和退出码。

### ⚠️ 构建命令有一个新陷阱

仓库里 `gradle.properties` 的 **`use_local_deps=false`**（开源仓默认走 maven，克隆即可构建）。
**本机离线构建必须显式覆盖**，否则会因缺少第三方 jar 而失败：

```
gradle.bat -p "...\modular-machinery-reborn" clean build --offline --no-daemon --console=plain -Puse_local_deps=true
```

三个第三方 jar（`jei-15.49.jar` / `kubejs-1.20.1.jar` / `rhino-1.20.1.jar`）仍在本地 `libs/`，**但没有入库**。

### ⚠️ 许可证：GPL-3.0 是义务，不是选择

上游 MMCE 是 **GPL-3.0**，本移植版必须沿用（copyleft；且不能改成 MIT/Apache）。已落位 `LICENSE`（上游 GPL-3.0 全文，逐字节复制）与 `NOTICE.md`（来源、修改声明、第三方依赖）。

**`license` 与 `authors` 两个字符串写在 `src/main/resources/META-INF/mods.toml`，不在 `build.gradle`。**
0.30.1 修这两个字段花了三遍，就是因为先假设它们在 Gradle 里——**要改元数据，直接改那个模板**。

2. 机器结构由数据包定义（`data/<ns>/machinery/*.json`）驱动。每 10 tick 检查一次：把控制器朝向对应的预旋转结构拿到世界里比对。搜索顺序**复刻旧版 `checkStructure`**（0.14.0，M5a）：① 先试**蓝图槽里那台**机器；② 若控制器是绑定机，再试**自己那台**，且若它 `requires-blueprint` 而插的不是它则**直接不成型**；③ 否则遍历全部定义，**跳过所有 `requires-blueprint` 的**——所以需要蓝图的机器只能靠蓝图成型，取走蓝图即解散。匹配到的机器注册名记入方块实体。0.5.x 之前是写死的「同层 3×3 八格环」，已在 0.6.0 删除。
3. 右键控制器**只打开原版控制器界面**（0.12.0 起控制器只有 1 个蓝图槽，没有工作槽，不再把手上物品塞进去）。界面为原版 `guicontroller_large.png` 整块 blit，窗口 176×213，文本缩放 0.72、起点 (12,12)、行序逐行复刻旧版；蓝图槽 (151,8)，玩家栏 (8,131)，快捷栏 y=189。状态 5 项；红石强充能时**只显示** `redstone_stopped` 且机器停止（`Level#getDirectSignalTo` 对应旧版 `World#getStrongPower`）。附加模组可经 `api/ControllerGuiInfoEvent` 加行。
4. 服务端每 tick 驱动配方生命周期：配方只在 `machine` 字段等于**当前成型机器**且其**一次性输入可支付**时选出；选定后立即扣除输入并记下配方 id（进行中的配方不会再被重新匹配掉）。之后每 tick 扣除能源与 per-tick 流体，倒计时到 0 时按**必定产出**检查空间并写入产物（逐条独立掷概率）。产物放不下则保持进度且**不消耗当 tick 的资源**（旧版会照扣；0.4.x 更严重，会每 tick 销毁 1 个输入与一份能源，已在 0.5.0 修复）。
5. 结构破坏会中断进行中的配方并丢弃已支付的输入（这是**结构失效**路径，与 `failure-action` 无关）。**`failure-action` 自 0.25.0 起被消费**（D17）：已开工的配方某一 tick 付不出资源时，机器自己声明的那一个取值决定这一 tick 的代价——`still` 保持进度（缺省，也是 0.25.0 之前两条失败点的实际行为）、`decrease` 每失败一 tick 退一格、`reset` 清零。`requires-blueprint` 自 0.14.0 起强制。
6. **仓口持有存储并暴露能力**（`MachineHatchBlockEntity`）：物品仓暴露 `IItemHandler`、流体仓暴露 `IFluidHandler`、能源仓暴露 `IEnergyStorage`，容量按 `HatchTier` 取自旧版枚举。控制器在结构检查时遍历成型结构坐标收集它们（`HatchCollection`），加工时输入取物品输入仓、FE 取能源输入仓、产物写入物品输出仓。仓口存储写入 NBT，世界重载后保留。**控制器本身不暴露任何能力**（0.12.0 起与原版一致）：它只有 1 个蓝图槽，机器的一切进出都必须经过仓口。
7. 仓口与机箱都采用旧版模型：**一家族一个方块 + 方块属性**（仓口用 `size`、机箱用 `casing`），变体由 `PropertyBlockItem` 在放置时写入。方块状态文件因此只有 11 个（6 仓口 + 1 机箱 + 1 通用控制器 + 3 绑定控制器），而非每变体一个。
7b. **右键仓口打开该仓口的界面**（0.13.0，M4b）。窗口统一 176×166，玩家栏 (8,84)、快捷栏 (8,142)。物品仓按等级选 `inventory_<tier>.png`（槽位孔已画在贴图里，坐标与贴图是一套绑定规格，逐档照抄旧版）。流体/能源共用 `guibar.png`，条形区 (15,10,20×61)，框 u=176、填充 u=196。流体按颜色渲染其图集贴图后叠框；悬停显示数值；**点击储罐**把手上容器与储罐交互（走菜单按钮，非自定义包）。流体仓在储罐变化时发方块更新（把存档状态当更新标签）以便客户端渲染流体类型；物品槽走菜单、能源数值走容器数据，均不发方块更新。单一菜单类型 `machine_hatch` 服务所有家族与等级；按旧版惯例**玩家槽在前（0..35）、仓口槽在后**。
8. 控制器分两种口味，共用一个方块实体类型 `machine_controller`：通用 `machine_controller`（不绑定机器）与绑定控制器。绑定控制器的集合 = **3 台内置机器**（`alloy_furnace_controller` / `iron_centrifuge_controller` / `transformer_controller`）**∪ 配置目录里作者声明的机器**（每个 `registryname` 一个 `<路径>_controller`）。绑定关系记在方块实例上，方块实体在构造时从方块读取。
9. **机器定义有三个来源**，且 mod 自**不携带任何机器**：
   - 配置目录 `config/modular_machinery_reborn/machinery/`：构造期扫描 → 注册 `<registryname>_controller`。文件**含 `parts` 即完整定义**，**不含即「控制器声明」**（只给 `registryname`，定义留在数据包，可 `/reload` 热改结构）。
   - 数据包 `data/<ns>/machinery/`：reload 时加载。无声明时只能用通用控制器。
   - **KubeJS 脚本**（0.28.0，v2a）：`MachineRegistryEvents.registry(event => event.machine('x').part(…))`，
     只做**核心字段**（注册名 / 本地化名 / 图案与部件）。`onServerReload` 里开一轮脚本周期，加载器 `apply`
     时把脚本层合并到数据包与配置目录之上。**脚本机器只能配通用 `machine_controller`**（方块在构造期注册，
     D8），但**蓝图自动有**（蓝图按 `MachineRegistry` 现做）。
     **注意绑定的形状（0.28.1 修的）**：事件组必须以 `EventGroupWrapper` 的形式交给脚本，直接绑原始
     `EventGroup` 会让绑定「存在但一个事件都没有」——脚本第一行即
     `TypeError: Cannot find function registry in object MachineRegistryEvents.`。另外 KubeJS 6 **没有**
     `onEvent('<id>', …)` 这种写法（占位函数直接抛「no longer supported」），`MachineRegistryEvents.registry`
     是唯一入口。详见 [`docs/专项/KJS-勘测.md`](docs/专项/KJS-勘测.md) §9。
   - 同 `registryname` 冲突时优先级 **脚本 > 配置目录 > 数据包**，且脚本覆盖别的来源时日志会点名该 id；
     **删脚本 → 下一次 `/reload` 起那台机器不存在**（层不跨轮缓存）。启动后新增的机器需**重启**才有专属控制器，
     加载器会明说；有声明无定义会告警为死方块。
   - **两条路径共用同一份校验**（`machine/MachineSchema.java`）：脚本侧的报错与 JSON 侧的报错是同一句代码生成的。
     脚本侧读法是**严格**的（未知字段直接报错并列出全部已知字段），数据包侧保持**宽容**（只告警）。
     **0.31.0 起两条路径读的字段集完全相同**——11 个扩展字段都有了脚本方法，`rejectDeferred` 已删除
     （`DEFERRED_ROOT_FIELDS` 置空保留，复现器段 Z3 仍以它的字段名不变量为契约）。见 `移植方案-v2.md` 的 D-记录与
     `docs/KJS-配方指南.md` §六/§七。
10. 作者控制器的 blockstate 与 item model 由**运行时合成资源包**提供（`GeneratedControllerPack` + `AddPackFindersEvent`），否则会渲染成缺失模型；这是旧版 `RegistryBlocks.writeControllerModel` 的等价做法。所有控制器共用一个模型，无声明时不贡献该包。
11. **配方来源**：数据包 `data/<ns>/recipes/**`，以及配置目录 `config/modular_machinery_reborn/recipes/**`。后者由 `ConfigRecipes`/`ConfigRecipePack` **作为一个强制 SERVER_DATA 数据包暴露**（1.20.1 没有注入配方的钩子），`recipes/a/b.json` → 配方 id `modular_machinery_reborn:a/b`，改文件 `/reload` 生效。目录为空时不贡献该包。
12. **内容全部外置（0.11.0）**：机器、变量集与 9 份配方都在 `example-datapack/`，随版本归档。全新安装是纯框架——没有机器、没有配方，只有通用 `machine_controller`、机箱与仓口。

## 4. 配方接口

配方是**需求列表**，形状与旧版一致，但**根级必须带 `type`**（0.13.1 修复的坑）。原生 JSON 示例：

```json
{
  "type": "modular_machinery_reborn:machine",
  "machine": "alloy_furnace",
  "registryName": "alloy_furnace_diamond",
  "recipeTime": 5,
  "requirements": [
    { "type": "modularmachinery:energy", "io-type": "input",  "energyPerTick": 100 },
    { "type": "modularmachinery:item",   "io-type": "input",  "item": "minecraft:coal", "amount": 32 },
    { "type": "modularmachinery:item",   "io-type": "output", "item": "minecraft:diamond", "amount": 1 }
  ]
}
```

> ⚠️ **根级 `type` 不是可选项。** 原版 `RecipeManager` 先读它决定交给哪个序列化器；缺了就在**我们序列化器被调用之前**丢弃该文件，日志只留一句 `Missing type, expected to find a string`。旧版 mod 自己加载配方，所以旧版 schema 没有这个字段——**从旧版直接抄来的配方必须补上**。`ConfigRecipes` 会在缺失时输出明确错误并说明该写什么。
>
> 注意区分：**根级** `type` 是 `modular_machinery_reborn:machine`；`requirements[]` 里每项的 `type` 是需求种类（`...:item` / `...:fluid` / `...:energy`）。

KubeJS 示例：

```js
ServerEvents.recipes(event => {
  event.recipes.modular_machinery_reborn.machine({
    machine: 'alloy_furnace',
    recipeTime: 100,
    requirements: [
      { type: 'modular_machinery_reborn:energy', 'io-type': 'input', energyPerTick: 40 },
      { type: 'modular_machinery_reborn:item', 'io-type': 'input', item: 'minecraft:copper_ingot', amount: 2 },
      { type: 'modular_machinery_reborn:item', 'io-type': 'output', item: 'minecraft:iron_ingot', amount: 1, chance: 0.75 }
    ]
  })
})
```

**字段与语义**

- `machine`：解析为注册名（可写全限定，也可只写路径由本模组命名空间补全），与控制器处**实际成型的机器**比对。
- `recipeTime`：总时长（tick）。
- `requirements[]` 的 `type` **接受双命名空间**（`modularmachinery:item` 与 `modular_machinery_reborn:item` 等义）；已实现五类：`item`、`fluid`、`energy`、`interface_number_input`（0.24.0）、`ingredient_array_input`（0.26.0）。未知类型**加载报错**，不静默跳过。
- `io-type`：`input` / `output`。
- 物品 `item` 支持三种写法：`minecraft:coal`、物品标签 `#forge:ingots/iron`、已映射的旧矿辞名 `ore:ingotIron`（映射表见 0.8.0 归档 README）。未映射的矿辞名与 `@meta` 语法都会报错。
- `amount`；产物另有 `chance`（0–1）与 `minAmount`/`maxAmount`（输入用区间会报错）。
- 能量用 `energyPerTick`（速率）；流体用 `fluid` + `amount`，可加 `perTick`。
- **时序**：输入在**开工时**扣除；能量与 per-tick 流体**每 tick** 扣除；产物在**完工时**写入，**每条独立掷 `chance`**。完工前的空间检查按**必定产出**的数量。

修改字段时必须同时检查 `MachineRecipe`、`ModRecipeSerializers`、KubeJS schema、JEI 展示和示例脚本。

## 5. 资源命名规则

- 命名空间固定为 `modular_machinery_reborn`。
- 仓口贴图为预合成的整块贴图，格式 `textures/block/<家族>_<等级>.png`，例如 `item_input_hatch_ultimate.png`、`fluid_output_hatch_vacuum.png`。
- 机箱贴图同为预合成，格式 `textures/block/blockcasing_<变体>.png`。
- 对应模型放在 `models/block/` 和 `models/item/`，方块状态放在 `blockstates/`（每家族一个，含全部变体）。
- 语言键格式：`block.modular_machinery_reborn.<物品注册名>`，即**每变体一个键**（`blockcasing_vent`、`item_input_hatch_tiny`），另有家族键供方块自身描述 ID 使用。
- ⚠️ 变体 BlockItem 必须覆写 `getDescriptionId()`：`BlockItem` 默认返回**方块**的描述 ID，同家族所有变体会塌缩到同一个键。此坑已在 0.5.0 踩过一次。
- 新资源加入后，必须检查模型引用的 PNG 是否真的进入 JAR；资源名大小写不要混用。

### 0.26.0 新增：`ingredient_array_input` 的最小实机清单

> 依「必查 7」：本版给需求引擎加了**第五类需求**，JEI 的**配方页**与**机器开工**都走新代码路径，因此交付时必须附这份「打开哪里、放什么、应该看到什么」。**在用户确认之前，本版只标记为「已构建、未实机验证」。**

准备一份配方（放 `config/modular_machinery_reborn/recipes/` 或数据包，`/reload` 生效）：

```json
{
  "type": "modular_machinery_reborn:machine",
  "machine": "alloy_furnace",
  "registryName": "array_smoke_test",
  "recipeTime": 40,
  "requirements": [
    { "type": "modularmachinery:energy", "io-type": "input", "energyPerTick": 20 },
    { "type": "modularmachinery:ingredient_array_input", "io-type": "input",
      "items": [ { "item": "minecraft:diamond", "amount": 2 },
                 { "item": "minecraft:emerald", "amount": 2 } ] },
    { "type": "modularmachinery:item", "io-type": "output", "item": "minecraft:stone", "amount": 1 }
  ]
```

### 0.28.2 新增：KubeJS 机器入口的「重载歧义」修复（最小实机清单）

> 0.28.1 实机失败在**文档里那行标量调用**上：`.part(1, -1, 0, 'minecraft:stone')` 的报错来自**列表那个同名
> 重载**（`Coordinate 'x' was given no value.`，栈帧落在 `part(List,…)`）。根因是
> `part(int,int,int,Object...)` 与 `part(List,List,List,Object...)` **同名、同参数个数、同为变长**，
> Rhino 先按名字找方法，多重候选时只能比转换权重、权重相等则由 `getMethods()` 顺序决定——**JVM 规范不定义
> 该顺序**，所以这次调用的含义是未定义行为。修法是把列表形式改名为 `parts(…)`，**标量写法一字未改**。
> 根因、实测权重与两段断言见 [`docs/专项/KJS-勘测.md`](docs/专项/KJS-勘测.md) §10。

- [ ] **标量 `.part(x, y, z, 方块)` 零报错**：用 `docs/KJS-配方指南.md` §七 那段
      `mmce_machine_test.js`（四个 `.part(...)`）→ `/reload` → **没有任何**
      `Coordinate 'x' was given no value.`，日志出 `posted; 1 machine definition(s)` 与
      `scripted_smoke -> 4 parts, size 3x1x3`。**这一条是本版的核心。**
- [ ] **数组写法 `.parts([x…], [y…], [z…], 方块)` 真的能用**：另写一台
      `event.machine('scripted_wall').parts([-1, 0, 1], [0], [-1, 0, 1], 'minecraft:iron_block')`
      → `/reload` → 日志里是 **9 parts**（3×3 笛卡尔积）。0.28.1 在这里是
      `ClassCastException`（脚本数组到 Java 是 `List<Double>`）。
- [ ] **旧的数组写法被明确拒绝**：同一段写成 `.part([-1,0,1], [0], [-1,0,1], 'minecraft:iron_block')`
      → KubeJS 报一条**类型转换**错误，点名标量签名 `part(int, int, int, java.lang.Object[])`；
      改成 `.parts(…)` 即通过。不是静默走错方法。
- [ ] **小数坐标被点名拒绝**：`.parts([1.5], [0], [0], 'minecraft:stone')` → 报错说明该坐标不是整数、
      并指出会被截断；机器**不注册**（不会被悄悄取整成 `1`）。
- [ ] **`/reload` 两次，机器还在**（与 0.28.1 同）：第一次之后**再 `/reload`**，`posted; 1 machine
      definition(s)` 再来一遍且计数仍是 1，机器仍能成型。
- [ ] **删脚本 → `/reload` → 机器消失**：删掉 `mmce_machine_test.js` → `/reload` → `scripted_smoke`
      不再出现，`posted; 0 machine definition(s)`，原本能成型的结构**不再成型**。

### 0.28.2 的离机断言（段 Z8b / Z10）证明什么、不证明什么

- **Z8b 能证**（读**类文件成员表**，`javap`，与 Z6 读 `register()` 同一做法）：`part` **只声明一次**且签名是
  `(int, int, int, java.lang.Object...)`，`parts` 另有一个名字。同名歧义一旦回归，这里立刻红——不需要

- **Z10 能证**（**真的**载入反混淆 KubeJS + Rhino，与 Z9 同一个 child-first 子加载器）：用 KubeJS 自己的

  **逐字等于**数据包会携带的那份；再用 `parts([-1,0,1],[0],[-1,0,1], …)` 断言笛卡尔积的 JSON；并实测

- **不能证**：游戏内可用（不启动服务器、不跑 `ScriptManager`、没有脚本注册的监听器、没有事件投递）；

## 发布必查项（两次事故换来的，务必执行）

> 0.23.0 补上**必查 4**：复现器/校验脚本自己会腐坏，跑不起来时先确认它本身还能编译。

### 必查 1：jar 必须已 SRG 重混淆

**未重混淆的 jar 会在模组构造期崩溃**（v0.19.0 事故：`java.lang.NoSuchFieldError: CREATIVE_MODE_TAB`，`ModBlocks.<clinit>`）。运行时是 SRG 命名，原版成员必须以 SRG 名引用；Forge 自己的名字不做重映射，所以失败表现为**第一个原版引用处的单个 `NoSuchFieldError`**，不是连锁失败。

```powershell
$jdk = "C:\Program Files\Microsoft\jdk-17.0.11.9-hotspot\bin\javap.exe"
$bc = & $jdk -classpath <jar> -c -p com.reborn.modularmachinery.block.ModBlocks 2>&1
# 官方名 CREATIVE_MODE_TAB 必须查不到；SRG 名 f_NNN_ 必须查得到
```

**构建产物、归档件、部署文件三处都要查。**

### 必查 2：先构建，后跑复现器（顺序不能反）

`reobfJar` 会**原地改写** `build/libs/<name>.jar`；而离机复现器的校验任务 `dependsOn jar`。**先构建再跑复现器，会把已重混淆的产物重新执行 `jar` 并还原成未重混淆版本** —— 正是必查 1 的崩溃状态，**这也是 v0.19.0 事故的实际成因**。

**正确顺序：复现器 → `clean build` → 重混淆检查 → 部署。**
### 必查 3：同一模组每种 `ModConfig.Type` 只能注册一次

**两次同类型注册会让 Forge 在启动期抛异常**（v0.21.0 事故：`java.lang.RuntimeException: Config conflict detected!`，`ConfigTracker.trackConfig`）。`ConfigTracker` 以文件名（`<modid>-common.toml`）为键，第二个 `COMMON` 撞上同一个键。

动配置前先 grep：

```powershell
Select-String -Path src/**/*.java -Pattern '\.registerConfig\('
# 真实调用（排除注释）必须只有 1 处；ForgeConfigSpec.Builder() 也只应实例化 1 次
```

**0.27.0 顺带**：新增的两个 MOC 键（`general.modular-controller-compatible-mode`、`general.disable-moc-deprecated-tip`）进的是**同一个 `build()` 的同一个 builder**，真实 `.registerConfig(` 仍只有 1 处（渲染出的键 13 → 15）。同一个 builder 里用**显式路径列表**定义每个键，所以下面的路径累加陷阱在新键上不适用——但渲染核对照旧要做。

**顺带记住**：`ForgeConfigSpec.Builder` 是**路径累加**的（`push()` 追加到运行中的上下文，`pop()` 不回到调用者起点）。在循环里 `push(名字)` 会让第二个键变成 `a.b.第二个名字…` 逐级加深——**文档里的路径可能从来不是代码真正写出的路径**。验收时应把 spec 渲染出来与真实配置文件对比，而不是相信文档。

### 必查 4：复现器本身会腐坏（0.23.0 补）

`_audit/m6c-verify/` 的离机复现器**连着两个版本编译不过**（它引用了重构时删掉的 `UpgradeBusConfig`），而当时的「通过」是**陈旧的**——它跑的是上一次编译出的 class。**复现器跑不起来时，先确认它本身还能编译，再对生产代码下任何结论。**

同一条教训在 0.23.0 又出现两次：新写的断言用了不存在的 `check(String,boolean,boolean)` 重载（`javac` 直接失败），以及 `CommentedFileConfig` 在 `build()` 之后**必须显式 `load()`**——不 `load()` 时 spec 拿到的是空配置，`isCorrect()` 会把「空文件」判成需要修正，于是断言会因为一套完全无关的原因失败或通过。**离机复现器的每一处「通过」都要问一句：它到底驱动了什么。**

**共同教训**：两次事故都是**「本项目第一次做某件事」**。每当某版本引入「第一次」的东西，**先查那个机制本身的约束**，别等它崩。

### 必查 6：验收证据必须落到 `_audit/`，并且是**复现器自己写出来的**

已连续**六次**出现「声称的支撑文件不在读者会找的地方」。

| 次 | 现象 |
|---|---|
| M6b | `_audit/` 下的 `acceptance-log.txt` 是**上一轮**的旧日志 |
| M6e-1 | 证据在 `factory-run.txt`，而不在代理暗示的 `acceptance-log.txt` |
| M6e-2 | 复现器输出进了 **Gradle 守护进程日志**（`.gradle-home/daemon/…`，**易失**），`_audit/` 里的产物文件里一行 PASS 都没有 —— 已抢救为 `m6e2-run.txt` |
| 0.24.2 安装包 | `acceptance-0.24.2-screen-layout.txt` 是 765 行 Gradle 日志，**PASS 行为 0**，而报告里写着 601 PASS |
| 0.24.4 | `acceptance-0.24.4-screen-alignment.txt` 与两份 `fault-injection-0.24.4-*.txt` 同样是 765 行 Gradle 日志、0 行 PASS |
| 0.24.5 | `fault-injection-0.24.5-*.txt` 第一行是 UTF-16 的 Gradle wrapper 输出（`To honour the JVM settings…`，即壳抓的是 wrapper 而不是任务）；`_audit/m6c-verify/m6e2-run.txt` 等若干文件是从守护进程日志里**手工抢救**回来的 |

**根因**：复现器的 stdout 被 Gradle 收走，最后落在**守护进程日志**里；而守护进程日志会被 Gradle 自行清理。「记得把输出拷贝过去」这条指令已经下过六次而无效，所以改成**结构上不可能丢**。

**现行要求（从 0.24.6 起）**：

1. **复现器自己写自己的证据。** 它在 `main` 的第一行就把 `System.out`/`System.err` 同时写进一个文件（tee，不是重定向：控制台照旧打印全部内容），目标固定为 `_audit/m6c-verify/harness-run-<版本>.txt`，并在输出的第一行与最后一行打印**绝对路径**。
2. **文件里必须有计数行**：`SUMMARY: <pass> PASS / <fail> FAIL (<total> checks)`，它由“逐条检查的同一组计数器”直接算出，不是事后数文件里的 PASS 行。报告里引用的计数必须是**从该文件里读出来的**。
3. **失败语义不变**：任何一条检查失败，任务仍然非零退出；写证据绝不能吞掉失败。环境性的 3 条 FAIL（配置迁移检查）照旧保留、照旧计数，不允许靠重写用户配置来搞绿。
4. **存放点不再取决于启动方式**：Gradle 任务、裸 `java` 命令、不同工作目录，都得写同一个文件；守护进程日志不再是证据来源。

**更一般的原则**：验收声称必须能指向一个**可复现、可打开、位置稳定**的产物。找不到证据时，先怀疑证据的存放，而不是接受结论。**但更好的做法是让产生证据的那个程序自己把它放到那里**——靠人记住的流程，已经失败六次了。

### 必查 7：新增可见界面 / 每帧调用的路径，交付前必须有「最小实机清单」

v0.24.0 的事故：控制器界面新加了一行「哪个需求拒绝了开工」，其中 `-1`（「没有失败」的哨兵）被直接丢给 `List.get()`，而 `drawInfo` **每帧**调用它 —— **机器一切正常时打开界面必崩**。该界面在那一版的报告里明确列在「未验证（没有像素、没有客户端）」里，**第一次在游戏里打开就中了**。

**规则：**

1. **哨兵值（-1 / null / indexOf 未找到 / 任何「无」的表示）绝不允许未经边界检查进入列表下标访问。** 列表下标只应有一个受守卫的入口（如 `failureKeyAt(int)`），线缆传来的值一律视为不可信。
2. **界面每帧调用的方法，其无数据/null 分支必须有离线断言**（为可驱动性抽出真实方法，而不是内联 `if`），并做**故障注入**证明「把 bug 放回去就会失败」。**从未失败过的断言不算证据。**
3. **凡新增可见界面或交互的版本，交付时必须附带「打开这个界面、点这几下、应该看到什么」的最小实机清单**；在用户确认之前，该版本**只标记为「已构建、未实机验证」**，不标记为可用。

**更根本的**：离线复现器能证明算术与状态，**证明不了渲染与交互**。把「未验证」写进文档是诚实的，但**不足以代替一次真实的打开**——这面墙已经撞了三次。
