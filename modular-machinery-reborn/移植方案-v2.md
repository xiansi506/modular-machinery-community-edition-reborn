# Modular Machinery: Community Edition Reborn — 移植方案 v2

> 本方案取代 `移植计划.md`。依据：`_audit/` 差异盘点（2026-09-29）。
> 目标平台不变：**Minecraft 1.20.1 / Forge 47.2.0 / Java 17**。
>
> **两条硬约束（由项目所有者指定）**
> 1. **GUI 必须复刻原版**：使用原版 23 张 GUI 贴图与原版布局与信息层级。现有程序化绘制（`g.fill` 纯色面板）作废。
> 2. 不再以「阶段 1 已完成」这类只验注册的弱标准作为完成证据。

---

## 1. 为什么必须换方案

差异盘点显示，现行 `移植计划.md` 把阶段 1、2 标为「已完成 / 第一版已完成」，但按「迁移」口径这严重高估了实际进度：

| 旧计划的说法 | 实际情况 |
|---|---|
| 阶段 1「基础部分已完成」 | 48 个等级仓口是新版**自创方块**（旧版根本没有等级仓口方块），且全部无行为；另有 6 个核心方块家族与 30 个模组兼容方块零迁移 |
| 阶段 1 验收「创造栏能找到所有注册对象」 | 只证明注册成功，不证明任何功能 |
| 阶段 2「第一版已完成」 | 旧版 13 个机器 JSON 根字段**全部**无对应实现；结构是硬编码 3×3 八格环 |
| 阶段 3「控制器内部能力已完成」 | 存在破坏性缺陷：产物槽满时每 tick 销毁输入与能量（`MachineControllerBlockEntity.java:56-62`） |

根因：旧方案把「重实现」与「迁移」两种工作混在同一套阶段里，用同一套弱验收，导致进度感与真实缺口脱节。

**本方案的对策**：每个工作项必须标注工作类型，且验收一律以「可观察行为」为准。

| 标记 | 含义 | 验收要求 |
|---|---|---|
| **M** 迁移 | 保留旧版语义与资源 | 必须能与旧版行为逐项对照 |
| **R** 重写 | 旧功能，用 1.20.1 惯用法实现 | 必须能演示等效行为 |
| **N** 新增 | 旧版没有的东西 | 必须说明为何需要，且不得计入迁移完成度 |

「已注册」「有贴图」「有物品名」在本文中**一律不构成完成证据**。

## 2. 必须先定的设计决策

以下 7 项如果不先定，后续返工代价极大。前 3 项是本方案的核心建议。

### D1（关键）等级模型：回到原版「一个方块 + size 属性」，撤销 48 独立方块

**旧版事实**：每个仓口家族只有 1 个方块，等级由 `PropertyEnum("size")`（`BlockBus.java:38`、`BlockEnergyHatch.java:34`、`BlockFluidHatch.java:39`）+ 每级一个 BlockItem 表达。等级真值：

| 家族 | 等级 | 级数 | 依据 |
|---|---|---|---|
| 物品输入/输出 | tiny, small, normal, reinforced, big, huge, ludicrous | **7** | `ItemBusSize.java:22-28` |
| 流体输入/输出 | 上述 7 级 + vacuum | 8 | `FluidHatchSize.java:27-34` |
| 能源输入/输出 | 上述 7 级 + ultimate | 8 | `EnergyHatchData.java:33-40` |

**建议**：1.20.1 无方块 metadata，但 `PropertyEnum` 机制可直接平移为 `EnumProperty<HatchTier>`。做法：

- 注册 **6 个方块**：`item_input_hatch`、`item_output_hatch`、`fluid_input_hatch`、`fluid_output_hatch`、`energy_input_hatch`、`energy_output_hatch`，各带 `size` 属性
- 注册 **46 个 BlockItem** = 7×2（物品）+ 8×2（流体）+ 8×2（能源），放置时写入对应 `size`
- **撤销**新版自创的 `item_input_hatch_ultimate` / `item_output_hatch_ultimate`：旧版物品仓口只有 7 级，也没有对应贴图；这是 0.4.3 拿荒谬级贴图顶替的来源
- 撤销 4 个「无等级基础仓口」：旧版不存在这个概念，它还会导致注册集合不对称

**理由**：这是复刻原版 GUI 的前提。原版物品仓口界面的贴图就是 `inventory_tiny/small/normal/reinforced/big/huge/ludicrous.png` **7 张，一一对应 7 个等级**。保留新版的 8 级模型会导致第 8 级无贴图可用——即当前 `ultimate` 缺图的根源会以另一种形式重演。

### D2（关键）GUI 复刻策略：blit 原版贴图 + 轻量 1.20.1 组件，不移植 4730 行旧框架

旧版 GUI 是 38 文件 / 4730 行的通用组件框架（`WidgetController` / `DynamicWidget` / 五态按钮 / Row/Column/ScrollingColumn）+ 847 行的 `WorldSceneRenderer` 预览渲染栈。**不建议 1:1 移植**：其中大量代码依赖 1.12.2 的 `GlStateManager`、`Tessellator`、`drawTexturedModalRect`、`GuiScreen` 体系，逐行改造成本高于重写，且会引入旧框架的历史包袱。

**建议做法**：保留原版的**视觉与布局规格**，实现一个面向 1.20.1 的轻量渲染层：

- 核心 API：`GuiGraphics.blit(ResourceLocation, x, y, u, v, w, h)` 直接使用原版 PNG，坐标逐项对齐旧版 `drawTexturedModalRect`
- 用一个 `TextureRegion` 小类替代旧版 `TextureProperties(texRes, texX, texY, w, h)` 的概念
- 组件只需 4 类：面板/贴图区、物品槽（复用 `AbstractContainerScreen` 的原生槽渲染）、进度/能量/流体条、按钮与滚动条（滚动条用于 ME 样板仓与升级列表）
- **禁止**再用 `g.fill` 拼面板

这样视觉与原版一致（因为像素来源就是原版 PNG），工作量却从「移植 4730 行」降到「实现约 300–500 行渲染辅助 + 每屏布局」。

### D3 机器定义层：JSON 数据驱动，字段与旧版对齐

旧版 13 个根字段全部要在 1.20.1 侧有对应物（`parts` 为核心，`modifiers` / `dynamic-patterns` 可后置），加载走 1.20.1 的 `SimpleJsonResourceReloadListener` / `AddReloadListenerEvent`。机器定义放在数据包（`data/<ns>/machinery/*.json`）而非 assets。

### D4 端口能力层：每仓口独立 BlockEntity

控制器按成型结构收集仓口能力（`IItemHandler` / `IEnergyStorage` / `IFluidHandler`），而不是像现在把容器塞在控制器里对外暴露。这是旧版语义，也是仓口 GUI 有内容可显示的前提。

### D5 结构：多层 + 任意形状优先，`@meta` 与变量集次之

`parts[]` 的 `x/y/z`（支持数组笛卡尔积）、`elements`（`ns:block@meta`）与多层结构属第一优先；`selector-tag`、`nbt`、`modifiers`、`dynamic-patterns` 按里程碑分期。

### D6 兼容层单独立项，不阻塞主线

AE2 / GregTech / TC6 / TConstruct / EXU2 / Astral Sorcery / Nature's Aura / Botania / Blood Magic 共 30 个方块与 14 类 JEI 集成，全部作为**独立可选模块**（`compat/<modid>/`）分期，不进入主线里程碑的完成度统计。

> ⚠️ **口径变更（所有者 2026-10-04）**：**兼容层与 CraftTweaker 等价 API 已进入本项目目标**，
> 「不进入完成度统计」这句**随之作废**。**不变的是实现形状**——仍然逐个模组、独立可选、隔离在 `compat/`，
> 因为已核实**本机除 Botania 外没有任何相关模组的 API jar**，每个模块都必须先取得依赖并勘测其 1.20.1 API。
> 排期见 [`docs/剩余项实施顺序.md`](docs/剩余项实施顺序.md) 波 5，规模与依赖清单见其 §5.1 / §10。

### D7 脚本入口：保留 KubeJS，但标注为 N 类

KubeJS 入口是新版自创（旧版只有 63 处 `@ZenClass` 的 CraftTweaker API）。

> ⚠️ **本节立场已两次变动，末态如下（所有者 2026-10-04）**：
> ① 原文「建议保留并补齐 CraftTweaker 等价能力，但**不得计入「迁移完成度」**」——
> 这是当时的写法：**保留 KubeJS、把 CT 能力当作额外项**；
> ② 0.27.0 之后升格为「KubeJS 入口**是发布必需特性**」（理由从「对齐旧版」变为「给包作者一个可用入口」）；
> ③ **2026-10-04 定形**：「CraftTweaker 等价 API」**取「扩 KubeJS 入口」这一形状**——
> **不移植 CT 桥本身**，而是把旧版脚本**能写的东西**（旧版 63 处 `@ZenClass` / 3210 行桥所覆盖的那套 DSL）
> 用 KubeJS 入口提供。见 [`docs/剩余项实施顺序.md`](docs/剩余项实施顺序.md) 波 5.1。
> **不变的是**：这条入口仍然**不计入「旧版有而新版无」的迁移完成度**（旧版本来也没有 KubeJS）。

### D8（已实施 · 0.9.0）采用「每机器一个控制器方块」，但绑定清单必须在构造期已知

旧版为每台机器动态注册 `<机器名>_controller`（`RegistryBlocks.java:422-440`），并在 `has-factory` 或配置默认开启时额外注册 `<机器名>_factory_controller`；`isFactoryOnly` 的机器只生成工厂控制器。控制器自带该机器专属的 blockstate（`RegistryBlocks.java:508-546` 为每台机器复制一份 `block_machine_controller.json`），并按机器 `color` 字段动态染色。

**旧版默认开启该机制**：`Config.onlyOneMachineController`（`Config.java:90-91`）默认 **false**，注释为「When enabled, Modules no longer register a separate controller for each machine」；只有通用 `blockcontroller` 是无条件注册的（`RegistryBlocks.java:187`）。因此这不是可选项，而是旧版的**默认行为**——M8 予以恢复。

| 方块 | 绑定机器 | 结构校验范围 |
|---|---|---|
| `machine_controller` | 无 | 遍历全部定义（数据包新增机器靠它） |
| `alloy_furnace_controller` | `modular_machinery_reborn:alloy_furnace` | 只校验该机器 |
| `iron_centrifuge_controller` | `modular_machinery_reborn:iron_centrifuge` | 只校验该机器 |
| `transformer_controller` | `modular_machinery_reborn:transformer` | 只校验该机器 |

绑定控制器只检查自己那台机器的结构，对应旧版 `TileMultiblockMachineController.checkStructure` 校验控制器自带的 `DynamicMachine`。名称走旧版自己的键形状 `%s控制器` / `%s Controller`；每机器各一个 blockstate，共享 `block/machine_controller` 模型（同旧版做法）。

#### 唯一无法照搬之处：绑定清单必须是编译期常量

- 方块与物品必须在 **mod 构造阶段**通过 `DeferredRegister` 注册，注册表随后冻结，运行时与数据包重载都无法新增方块；
- 机器定义放在**数据包**里（`data/<ns>/machinery/`），在构造之后加载、且可 `/reload`。

旧版之所以可行，是因为它在 `initialize()` 里**先加载机器定义、再注册方块**，全部发生在注册表冻结之前。本方案把定义交给数据包后二者互斥：**要保留「每机器一个方块」，机器清单就必须在构造时已知。**

因此绑定清单落在 `ModBlocks.BOUND_CONTROLLER_MACHINES`，并由加载器校验：清单中的名字若没有对应定义，会输出告警说明该方块永远无法成型。数据包新增的机器仍可用通用控制器——这与旧版对「启动后新增机器」的限制一致。

- ~~**每机器工厂控制器**（`has-factory` 时的 `<机器名>_factory_controller`）~~ —— **0.22.0（M6e-1）已补**：声明文件里加 `"has-factory": true` 即在构造期注册该方块，`has-factory` / `factory-only` 已求值。见 D15。
- ~~**MOC 兼容命名空间**（`modularcontroller:<机器名>_controller`，用途是让旧存档继续加载）：对 1.20.1 新模组无意义。~~ **0.27.0 已实施，且这句话本身是错的**：它对**新模组**无意义，但对**从旧 ModularController / 旧 MMCE 存档升级上来的玩家**有意义——方块注册 id 由存档里的 ResourceLocation 反序列化，**id 不存在则世界打不开**。已登记为 **D20**，并已交付。唯一与旧版不同的是**实现形状**：旧版用 `Config.mocCompatibleMode` 当门（`Config.java:99-105`），而 1.20.1 在注册表事件触发时**读不到任何配置值**，所以本移植**无条件注册**、并把该键如实标为惰性。

### D9（已实施 · 0.10.0）机器定义的作者来源：配置目录，且它才是能给出专属控制器的那一条

D8 留下的问题是：绑定清单若只是编译期常量，**整合包作者自己加的机器就永远只能配通用控制器**，等于「每机器一个控制器」对作者无效。旧版没有这个矛盾，因为它的机器定义本来就在配置目录里、且在注册方块之前读取：

- `ModDataHolder.java:44` — `machineryDir = config/modularmachinery/machinery/`
- `ModDataHolder.java:72` — `copy("default_machinery", machineryDir)` 把内置机器拷进去
- `MachineRegistry.preloadMachines()`（`CommonProxy:150`，preInit）从该目录发现机器，供随后的方块注册使用

**0.10.0 恢复该结构**：

| 来源 | 路径 | 能否得到专属控制器 |
|---|---|---|
| 配置目录（**推荐的作者来源**） | `config/modular_machinery_reborn/machinery/` | ✅ 能 |
| 数据包（M1 路线，保留不变） | `data/<命名空间>/machinery/` | ❌ 只能配通用控制器 |

- 同一 `registryname` 冲突时**配置目录胜出**（本机实例的显式覆盖）；数据包用户不受影响，只是其机器用通用控制器。
- 目录被读两次：构造期只取 `registryname` 用于注册方块；每次 reload 读取完整定义。
- 启动后新增的机器要**重启**才有专属控制器，加载器会明说，并同时报告「有控制器但机器没加载」的死方块。
- 作者机器的 blockstate/item model 由**运行时合成资源包**提供（`GeneratedControllerPack` + `AddPackFindersEvent`），等价于旧版 `RegistryBlocks.writeControllerModel` 把 `block_machine_controller.json` 复制给每台机器。
- 示例见 `modular-machinery-reborn/examples/pack-author/`。

#### 明确未做

- **配方的配置目录来源**：旧版还有 `config/modularmachinery/recipes/`（`ModDataHolder.java:73`），本方案尚未对齐，作者的机器需要数据包放配方。这是配置目录故事的另一半，列为后续项。

### D10（已实施 · 0.11.0）内容外置：mod 不携带机器与配方

项目的明确要求：**mod 自带机器全部删除，内容改以数据包形式提供**。0.11.0 执行了这一决定。

| 变化 | 内容 |
|---|---|
| 机器与变量集 | `data/modular_machinery_reborn/machinery/**` → `example-datapack/data/.../machinery/**` |
| 配方 | `data/modular_machinery_reborn/recipes/**` → `example-datapack/data/.../recipes/**` |
| jar 内 `data/` | **文件数 0** |
| 随包控制器 | 3 个（`alloy_furnace_controller` 等）随机器一并删除——机器没了它们永远无法成型；blockstates 11→8、物品 62→59 |
| 全新安装 | 纯框架：无机器、无配方，只有通用 `machine_controller` |

#### 配套：控制器声明（解决了 D9 遗留的「数据包机器不能有专属控制器」）

D9 的配置目录要求放**完整定义**。0.11.0 放宽为：**含 `parts` 即定义，不含即声明**。声明只给 `registryname`，用于构造期注册 `<registryname>_controller`；定义可留在数据包，并可 `/reload` 热改结构。

于是数据包机器也能有专属控制器，且结构仍是可热改的——这是 D8/D9 那条「方块只能在构造期注册」约束下的最优解。

加载器对两种失配都会出声：有声明无定义 → 告警说明该方块永远无法成型；有定义无声明 → 列出回退到通用控制器的机器。

#### 配套：配置目录配方来源

新增 `config/modular_machinery_reborn/recipes/**`（对应旧版 `ModDataHolder.java:73`）。1.20.1 没有注入配方的钩子——配方只能来自 `RecipeManager` reload——因此**把该目录当作数据包暴露**（`ConfigRecipes` / `ConfigRecipePack`，`AddPackFindersEvent` 的 `SERVER_DATA`），而不是另开加载路径。目录为空时不贡献该包。

同 id 与数据包冲突时按常规数据包优先级竞争，文档建议使用不同 id。

### D11（已实施 · 0.14.0）蓝图优先于绑定控制器；`requires-blueprint` 的定义在通用搜索中被跳过

`MachineRegistry.findMatch` 现在按旧版 `TileMultiblockMachineController.checkStructure` 的顺序判定。两处值得单独记下的决定：

1. **蓝图优先，包括优先于绑定控制器自己的机器。** 旧版在 `parentMachine` 之前先查 `getBlueprintMachine()`（`:701-710` vs `:713-726`），所以往 `transformer_controller` 里插合金炉蓝图、且合金炉结构匹配时，它会变成合金炉。这与 D8 写的「绑定控制器只校验自己那台机器」表面上冲突，但**如实复刻**——它需要玩家主动插蓝图才会发生，且悄悄收紧会让本模组与旧版行为不一致。若要改，改动点在 `findMatch` 第二步之前。
2. **通用搜索跳过 `requires-blueprint` 的定义**（旧版 `checkAllPatterns:740`）。这不是优化而是该字段的语义本身：需要蓝图的机器**只能**通过蓝图成型。副作用是「取走蓝图 → 机器解散」无需额外代码。

`requires-blueprint` 保持**可选**：旧版内置机器没有一个设置它（`default_machinery` 里要么缺省要么 `false`），本模组的内置机器因此也不设。

### D12（已实施 · 0.19.0）机器定义新增 `max-parallelism` / `internal-parallelism` / `parallelizable` 三个根字段

**这是本项目对旧版 schema 的第三处有意偏离，理由是 D3/D9/D10 的同一条。** 旧版机器定义 JSON **没有**这三个根字段：它们的值来自 `AbstractMachine` 的 Java 字段，唯一的外部入口是 CraftTweaker 脚本里的 `MachineModifier.setMaxParallelism` / `setParallelizable`（`MachineModifier.java:43-84`），而内置默认值是编译期配置（`Config.maxMachineParallelism = 2048`、`AbstractMachine.internalParallelism = 0`、`Config.machineParallelizeEnabledByDefault = true`，`Config.java:38-47`）。

本项目的路线是**机器定义由数据包与配置目录提供**（D3/D9/D10），包作者没有 Java，也没有 CraftTweaker。若不把这三点放进定义：

- 数据包/配置目录的机器**永远无法并行**——`internal-parallelism` 无处分身，`max-parallelism` 只能用全模组一个常数；
- 「按数据驱动的机器」比内置机器少一项能力，而 M6d 的并行控制器对一个上限恒为默认值的机器毫无意义（它改不了任何东西）；
- M6c 的验收将无法进行：分册要求「把 `max-parallelism` 设成 >1 并数出 N 份产出」，而设置它的地方不存在。

**字段与默认值**（默认值一律照抄旧版，故既有定义行为不变）：

| 字段 | 类型 | 缺省 | 语义 | 旧版对应 |
|---|---|---|---|---|
| `max-parallelism` | 非负整数 | `2048` | 并行度的**硬上限**，任何来源的并行数都被夹到它以下 | `AbstractMachine.maxParallelism` / `Config.maxMachineParallelism` |
| `internal-parallelism` | 非负整数 | `0` | 机器**自身**能同时跑几份（并行控制器的贡献在此之上累加） | `AbstractMachine.internalParallelism` |
| `parallelizable` | 布尔 | `true` | 是否允许并行；`false` 直接否决，不看前两项 | `AbstractMachine.parallelizable` / `Config.machineParallelizeEnabledByDefault` |

**为什么「缺省即保持现状」**：旧版 `TileMultiblockMachineController.getMaxParallelism()`（`:293-304`）是「从 `internalParallelism` 起底 → 累加结构里的并行控制器 → 截断到 `maxParallelism` → `Math.max(1, …)`」。三个字段全部缺省时该式等于 `max(1, 0 + 0) = 1`，即**恰好一份**；而按旧版默认值写全（`2048 / 0 / true`）得到同一个 1。因此 M6c 落地后，既有的机器定义一条不写也仍然是「一台机器一次跑一份」，与 0.18.0 完全一致——这一点由 0.19.0 的离线验收脚本 J 组断言。

**校验规则（比旧版严格，理由是定义文件由人书写）**：

- `max-parallelism` / `internal-parallelism` 必须是整数且 ≥ 0，否则加载报错并说明该写什么；
- `internal-parallelism > max-parallelism` 是自相矛盾（机器自己的并行量超过了上限）→ 加载报错。旧版由 `AbstractMachine.setInternalParallelism` **悄悄**把 `maxParallelism` 抬上去（`:110-115`），本项目改为出声；
- `parallelizable: false` 而 `internal-parallelism > 1` 并不矛盾（只是那台机器仍然只跑一份），因此只告警、不报错，并说明要么打开 `parallelizable`、要么删掉 `internal-parallelism`；
- 未知根字段（不含 `//` 注释键）会告警并列出已知字段名，避免把拼写错误当成"已接受"。

**没有采纳的退路**：分册 §3.4 提到的「只给配置目录机器读这三个字段」。否决理由与 D10 相同——那会让数据包机器成为二等公民，而 D10 存在的意义正是消除这个差别。

**同批一并求值的 `modifiers`**：它自 M1 起被列为「识别但不求值」，0.19.0 起真正生效（每个条目指出一个结构位置，该位置放着被接受的方块时其配方修改器参与本机器的配方结算）。这是分册 §5.2 明确要求的「`modifiers` 与升级携带的修改器同类型不同来源，一次性把两者的求值路径分开实现，不要合并成一条」中的第一条来源；升级那一条要等 M6b 的实例层。

### D13（已实施 · 0.20.0）并行控制器：新增第二条结构收集路径，账算在一个纯函数里

**这条记录回答的是分册 §4/§5 点名的那个缺口：本项目从来没有「把非仓口方块归属到某台机器」的机制。** 唯一会被结构扫描收集的东西是 `MachineHatchBlockEntity`（`MachineControllerBlockEntity#collectHatches`），升级总线（M6b）与并行控制器（M6d）都需要第二条路径。分册同时给了禁令：**不要把这类方块伪装成仓口**——那会污染 `HatchKind` 与「结构位置接受哪些方块」的集合。

**决定**（三部分，缺一不可）：

1. **第二条收集路径与第一条并列，不合并**。`MachineControllerBlockEntity` 在同一个结构检查里走**同一份** `machine.pattern().positions()`，对每个位置先试仓口、再试
   `machine.ParallelController`。结果是两个互不相干的收集物：`HatchCollection`（仓口，进入配方引擎）与 `ParallelControllerCollection`（并行控制器，只贡献一个整数）。**没有**搜索半径、没有方块更新握手、没有假仓口。`ParallelController` 是一个只有一个方法族的窄接口，M6b 的总线可以照抄这条路径而不必改动它。
2. **账算在纯函数里**。旧版 `TileMultiblockMachineController#getMaxParallelism`（`:289-300`）现在是
   `machine/ParallelismLimit.resolve(definition, controllerParallelism)`：`max(1, min(max-parallelism, internal-parallelism + Σ控制器))`。D12 的三个根字段一个没动，控制器和只是在起底与截断之间插进去——**三个字段全省略时结果仍是 1**，0.19.0 的行为逐位不变。这样做的直接理由是方案第 5 节禁止用「界面上出现了数字」验收：纯函数能被 `_audit/m6c-parallel-verify/` 的离机复现器直接驱动，事实是「一次完工真的消耗了 N 份、产出了 N 份」。
3. **控制器必须被机器定义接受**，这不是可选项：旧版内置机器里只有 `assembly_line` 的结构清单列了 `modularmachinery:blockparallelcontroller`，其余机器根本不接受它。因此示例数据包把 `alloy_furnace` **屋顶正中**那一格改成同时接受 `blockcasing[casing=plain]` 与 `parallel_controller`，并把它的 `max-parallelism` 从 64 抬到 **2048**（旧版 `Config.maxMachineParallelism` 的默认值）——否则 5 个等级里只有前三个能被区分，而分册 §2 的 M6d 验收写的正是「super → 256」。

**同批的两处次要决定**：

- **等级数值进配置文件**（分册 §3.4 的建议）。这是本项目第一个配置文件：`config/modular_machinery_reborn-common.toml`，键路径照抄旧版 `parallel-controller.<tier>.max-parallelism`，默认 4/16/64/256/512，范围 `1 .. Integer.MAX_VALUE`。等级枚举本身仍是编译期常量（方块注册不可延后，D8 的同一条理由）。
- **网络：读走菜单 `ContainerData`，写用一个自定义包**。分册 §5.1 建议全走菜单，本项目把「能走菜单的都走菜单」——控制器的上限与当前值经 `ParallelControllerMenu` 的 `ContainerData` 双向同步到屏幕，与 0.19.0 给控制器菜单加的 6~9 号索引同一套路。**唯一偏离在写方向**，且是被协议格式逼出来的：菜单唯一可用的客户端→服务端通道 `ServerboundContainerButtonClickPacket` 把容器号与按钮号**各编成一个字节**（`javap -c -p joined-1.20.1-…-srg.jar` 实查为 `readByte`/`readByte`），而并行数上限默认 512、可配到 2048 以上，原版「把玩家输入的绝对值发过去」塞不进一个带符号字节。于是新增本项目第一个 `SimpleChannel`（`network/ModNetwork`），消息 `ParallelControllerUpdatePacket` 用一个 varint 携带数值，服务端照旧版 `PktParallelControllerUpdate.java:38-47` 重新校验。

**这不是 M6b 的替代品**：升级总线仍待实施，它需要的「总线如何知道它属于哪台机器」在本条之后有了一条现成且经过验证的路径（第 1 部分），但总线自己的槽位、能力与界面不在本片内。

### D14（已实施 · 0.21.0）升级总线：复用 D13 的第二条收集路径（补一次反向绑定），升级的效果声明成 `modifiers` + `stackable`

**这条记录回答的是分册 §4/§5 点名的同一个缺口在 M6b 上的落法，以及 M6a 那个「没有消费者」的数据层在接上消费者时必须补什么。**

**第一部分：归属。** D13 已经为并行控制器建好第二条收集路径（同一份 `machine.pattern().positions()`，先试仓口、再试窄接口 `ParallelController`，产物是一个互不相干的集合）。总线**复用了这条路径**，`MachineControllerBlockEntity` 不改结构检查的骨架，只在同一个循环里多收一个 `UpgradeBusUtility` 桶。

但总线的接口必须比并行控制器宽一格，这不是设计偏好而是语义要求：

| 维度 | 并行控制器（M6d） | 升级总线（M6b） |
|---|---|---|
| 方向 | 单向：被**计数** | 双向：被**询问**，且要在自己的界面里说出它属于哪台机器 |
| 接口 | `ParallelController`（2 个方法） | `UpgradeBusUtility`（绑定 + 已绑定表 + 内容 + 取修改器） |
| 额外动作 | 无 | 控制器在结构检查时回调一次 `bindMachine(pos, machineId)`，即旧版 `UpgradeBusProvider#boundMachine`（`TileUpgradeBus.java:236-245`） |
| 解除 | 不需要（每 tick 重算） | 总线自己每 20 tick 对账删除失效绑定，即旧版 `doRestrictedTick`（`:66-92`） |

**方向与旧版一致**：旧版也是控制器**绑定**、总线**对账解除**。没有搜索半径、没有方块更新握手、没有假仓口，总线的槽位永远不进 `HatchCollection`。

**第二部分：升级怎么变成配方修改器。** 旧版没有声明——CraftTweaker 的 `MachineUpgradeBuilder#addModifier(stackAble, key, modifier)`（`:138-159`）挂一个 `MachineTickEvent`（START 阶段）处理器，调 `controller.addModifier(key, modifier)`，由 `RecipeCraftingContext` 与结构修改器汇合。本项目没有脚本桥（D7），因此把**升级的效果本身**声明进 M6a 的 schema：

| 新字段 | 类型 | 缺省 | 语义 | 旧版对应 |
|---|---|---|---|---|
| `modifiers` | 数组 | 空 | 该升级贡献的配方修改器。**每个条目的形状与机器定义 `modifiers[].modifier` 逐字段相同**（`target` / `io` / `operation` / `multiplier`，可选 `affectChance`），因为它是同一个 `RecipeModifier` | 旧版无声明，只有 CraftTweaker 回调 |
| `stackable` | 布尔 | `false` | `true` 时一份 n 个的载体把该修改器**按份数重复施加**（旧版 `:152-156` 的 `multiply` 循环，即 `value^n`）；`false` 时整叠只算一次 | `MachineUpgradeBuilder#addModifier` 的 `stackAble` 参数 |

这是本项目对**升级** schema 的第一处扩展（机器 schema 的偏离见 D12）。`ADD` 型修改器无论 `stackable` 与否都只算一次——旧版那个循环是照着 `MULTIPLY` 写的，`RecipeModifier#multiply` 对 `ADD` 只会把值乘起来，本项目如实照做而不是替它补一个语义。

**第三部分：两条来源在一个 `RecipeModifiers` 里汇合，但计算路径不合并。** 分册 §5.2 明令「不要合并成一条」。落地方式是：

1. 结构修改器照 M6c 原样算（`evaluateModifiers` → `MachineDefinition.flatten`）；
2. 总线修改器单独算（`UpgradeEffects.of(bus.upgrades(), machineId)`，按 `UpgradeType.isCompatible` 过滤，即旧版 `UpgradeBusProvider#getUpgrades` 的行为）；
3. 两者用**已经存在的** `RecipeModifiers#andThen` 拼成一个集合交给配方引擎——那个方法的注释从 M6c 起就写着「for combining a machine's structure modifiers with an upgrade's」。

**第四部分：账仍然算在纯函数里。** `UpgradeEffects` 是 `UpgradeStack`（升级 + 份数）到 `RecipeModifiers` 的纯函数；`UpgradeEffects.read(IItemHandler[, lookup])` 是旧版 `TileUpgradeBus#onUpgradeInventoryChanged` + `updateUpgrades` 的等价物（**照抄语义，不照抄 `synchronized`** —— 分册 §5.1/§7）。因此离机复现器能直接驱动：`_audit/m6c-parallel-verify/` 的 O 组 **57 PASS**，断言的是**真的少 tick 了、真的多产出了、不兼容的真的没生效**（0.21.0 起共 **170 PASS / 0 FAIL**）。

**没有采纳的退路**：把升级效果硬编码成几个已知种类（速度/产量/能耗）。否决理由与 D12 同：数据包作者没有 Java，硬编码等于让作者永远只能用内置那几种升级。

**同批的两处次要决定**：

- **总线等级数值进配置文件**（分册 §3.4 的建议，M6d 已为并行控制器做过一次）：`config/modular_machinery_reborn-common.toml` 的 `upgrade-bus.<tier>.max-upgrade_slot`，默认 3/6/9/12/18，范围 `1 .. 18`（上界 18 是旧版的硬编码上界，`UpgradeBusData.java:26`）。等级枚举本身仍是编译期常量（D8 同一条理由）。
- **网络：本片不需要任何新包。** 读方向走菜单 `ContainerData`（升级数量 / 绑定机械数 / 槽位数），绑定机械表走方块实体自己的 update tag，槽位内容走菜单既有同步，升级**声明**本来就在客户端（reload 两侧都跑）。总线界面是只读的，唯一交互是滚动条，纯客户端。因此 `network/ModNetwork` 的协议版本保持 `1`、消息 ID 0 仍只属于并行控制器——**没有新增包，也没有改动已有包**。

### D15（已实施 · 0.22.0 / 0.23.0）工厂控制器：语义与注册（M6e-1），界面、贴图与配置（M6e-2）

> **状态**：本记录的第一至四部分（线程是什么、注册复用哪条路、线程模型与旧版的差别、结构归属不适用）
> 由 **0.22.0（M6e-1）** 落地。第五部分（界面、两张贴图、两个配置键）由 **0.23.0（M6e-2）** 落地，
> 见本节末尾的 **M6e-2 补充**。

**这条记录回答三件事：工厂的"多线程"到底是什么、`has-factory` 这种构造期约束复用了哪条路、线程模型与旧版 `FactoryRecipeThread` 的差别。**

**第一部分：线程是什么。** 旧版自己的类注释就写着「不是真正意义上的线程 / Not a thread in the true sense of the word」（`FactoryRecipeThread.java:33-38`），代码完全支持这句话：`FactoryRecipeThread` 的全部内容都是**状态**（`activeRecipe` / `status` / 两个 modifier map / `isCoreThread` / `threadName` / `recipeSet` / `idleTime`），唯一带循环的方法是 `addRecipe` 里的 `recipeSet.add`，`onTick()` 只是转发到 `activeRecipe.tick`。没有 `Thread`、没有 `Executor`、没有 `synchronized`、连 `volatile` 都没有——`TileFactoryController#doThreadRecipeTick` 在服务端主线程里顺序遍历所有槽位。

因此**并行与工厂是两件事**，本片沿用旧版的划分：
- **并行**（M6c/M6d）= 同一条配方一次结算 N 份，`N` 由 `ParallelismLimit` 算出，需求按 `N` 倍数量移动；
- **工厂线程** = 一个槽位跑一条配方的**一次**结算；多个槽位让一台控制器同时跑**多条不同配方**，各有各的进度、各自已付的输入、各自完成。

**第二部分：注册——复用 D9/D10 的配置目录声明机制，不新增机制。** `has-factory` 的布尔值必须在**构造期**可知，因为它决定 `<机器名>_factory_controller` 这个方块是否存在，而方块只能在 mod 构造阶段注册（D8）。项目里已经有**形状完全相同**的问题与解法：`config/modular_machinery_reborn/machinery/` 里一份只写 `registryname` 的**声明**可以在构造期为数据包里的定义认领一个 `<机器名>_controller`，定义本身留在数据包里、继续可 `/reload` 热改（D9/D10）。

本片**直接沿用**它，只把声明文件多读一个字段：

```json
{ "registryname": "example_factory", "has-factory": true }
```

- **没有新增机制、没有新增目录、没有破坏 `/reload`**：结构定义仍在数据包里，改结构依旧只需 `/reload`；变化的只是"这台机器有没有工厂方块"这一位，而它本来就只能在重启时确定。这正是 D8/D9/D10 那条「方块只能在构造期注册」约束下的同一个答案，而不是第二个答案。
- **数据包机器拿不到工厂控制器时出声**：`MachineLoader` 在加载后逐个检查 `has-factory: true` 的定义，没有对应方块就打印**该写什么**（声明文件路径 + 内容范例），并指向本记录。
- **`has-factory` 的另一半在机器定义上，两半必须同时成立**：`FactoryThreadModel.factoryEnabled(blockIsFactory, definition)` = 「方块是工厂控制器」∧「定义带 `has-factory`」。这使"没有 `has-factory` 的机器不能用工厂控制器"成为一条**可离线断言**的判定，而不是一句文档。
- **`factory-only` 只解析 + 一致性告警**：旧版用它决定「不注册普通控制器」（`RegistryBlocks.java:431-433`），本项目的方块集在定义加载前就冻结了，因此无法对数据包定义执行它。写成 `factory-only: true` 而 `has-factory` 为 false 时加载器**告警**并说明两者矛盾——这是本片对旧版的一处**诚实偏离**，写在字段的 javadoc 里。

**第三部分：线程模型实现了什么、丢掉了什么。** 引擎是 `com.reborn.modularmachinery.factory.FactoryEngine`（纯逻辑，不 import `Level`），宿主接口 `FactoryHost` 由方块实体实现、由离机复现器实现——因此断言跑的是**生产代码**。

| 旧版 | 本片 | 理由 |
|---|---|---|
| `workMode` ASYNC/SEMI_SYNC/SYNC + `EXECUTE_MANAGER` + `executeGroupId` | 不实现 | 那是**控制器自身 tick** 的执行策略，不是配方的。分册 §5.1 明确允许同步读法，而本项目控制器本来就是同步的；三种模式算出同一个数，照抄只会误导 |
| `FactoryRecipeSearchTask` + `SequentialTaskExecutor` + `waitToExecute` + 超时 | 同步 `searchAndStart`（每 tick 试一次） | 搜索搬到 ForkJoin 只为不占主线程。同步之后没有 task 可等，串行执行器与超时也就没有了对象。保留的是可观察行为：**有活可干的那一 tick 就把槽位填上** |
| `currentRecipeSearchDelay()` / `recipeResearchRetryCounter` | 不实现 | 纯粹是为昂贵的异步搜索做的节流 |
| `RecipeCraftingContext` / `RecipeCraftingContextPool` / `CraftingStatus` | `FactoryEngine.ActiveCraft` + 控制器既有的 `ControllerStatus` | M2 的引擎没有上下文物件，配方的修改器是方法参数 |
| FactoryRecipe(Start/Tick/Finish/Failure)Event | 不实现 | 那是 CraftTweaker 桥的钩子（D7 已排除） |

**保留的行为**（含看起来像 bug 的地方）：`max-threads` 对**普通槽位**的平铺上限（旧版 `size() > getMaxThreads()` 让列表能到 `maxThreads + 1`，本片按 `size() < maxThreads` 封顶并如实记录）、核心槽位**不受** `max-threads` 约束、核心槽位的固定 `recipeSet`、20 tick 一次的闲置清扫与 `IDLE_TIME_OUT = 200`、`getAvailableParallelism` 的 `max(1, …)` 下限。

**两处有意的改进，如实记录**：
1. **一个槽位只持有一条配方**。配方的一次性输入在 `start` 阶段被扣走，所以把同一条配方交给两个槽位会**重复付款**。旧版靠「只把不在 `getActiveRecipeList()` 里的配方交出去」规避同一个危险；本片把它做成 `runnable` 过滤，并且 `ActiveCraft` 把并行数**存在线程上**（旧版的 `ActiveMachineRecipe` 本来就是每线程一个），因此"两个线程跑同一条配方"不会互相改坏对方的份数。
2. **空转不再制造槽位**。搜索先问「现在到底有没有可开工的配方」，没有就不创建线程——否则空闲工厂会每 tick 造一个空槽位、被 200 tick 清扫掉、再造一个，`isIdle()` 永远为假而清扫永远追不上。启动前的这一问是离机复现器发现的。

**第四部分：结构归属——不适用，因此**没有**复用 D13 的第二条收集路径。** D13 的第二条路径解决的是「某个方块站在结构里、要把它的贡献算进这台机器」。工厂控制器**不在结构里**：旧版把它当作控制器自身（`BlockFactoryController` 是**原点**上的方块，结构位置 `(0,0,0)` 在 `parts` 里被显式跳过），本项目的 `MachineControllerBlock` 同样是原点方块、不属于 `pattern().positions()`。因此本片既没有新增 `FactoryController` 窄接口，也没有第三次走位——**模式由方块类型决定，不由结构内容决定**。若将来出现"结构里另一台工厂控制器要参与"的需求（旧版没有），正确的做法仍然是 D13 的那条路，这里如实说明它为什么没被用到。

**没有采纳的退路**：把工厂做成真正的异步（线程池 + 状态可见性 + 持久化重做）。分册 §5.1 把它列为 M6 的最高风险项，并给出「先做顺序多槽」的建议；本片采纳该建议，也把「这不是并发实现」写进 `FactoryThreadModel` 的类注释。

#### M6e-2 补充（0.23.0）：界面、贴图与两个配置键

**界面**。原版 `GuiFactoryController`（389 行）整块复刻：面板 `guifactory.png` 整块 blit、窗口 **280×213**（280 是原版自己设的 `xSize`，而且这张 PNG **实际就是 280×213**——不是 256 图集切分，所以尺寸从 PNG 本身量而不是从文档抄）；左侧线程队列每页 6 个、元素 86×32 取自 `guifactoryelements.png` 的 `(0,0)`、步进 33 面板像素；滚动条是原版 `GuiScrollbar`（**原版**创造栏页签贴图，轨道 u=232、滑块 u=244）于 (94,8)、高 197；信息栏 0.72 缩放、面板起点 (113,12)、换行 `135/0.72`，行序与旧版逐行一致。容器坐标照抄 `ContainerFactoryController`：蓝图槽 **(255,8)**、玩家栏 x=**112**、y=131/189。

### D16（已实施 · 0.24.0）智能数据接口并入控制器：不移植独立方块，值存控制器、界面进控制器

**这条记录兑现的是项目所有者的决定**（设计文档 `docs/专项/M6d-b-智能数据接口并入控制器.md`），也是本项目对旧版**方块清单**的第一处**有意偏离**（D12/D13/D14/D15 偏离的是 schema，不是方块集）。

**决策与理由。** 旧版的「智能数据接口」是**独立方块**（`BlockSmartInterface` 120 行 / `TileSmartInterface` 179 行 / `GuiContainerSmartInterface` 203 行 / `PktSmartInterfaceUpdate` 60 行），并且是**结构组件**（`TileSmartInterface.SmartInterfaceProvider extends MachineComponent`，与仓口同性质，由结构扫描收集）。但控制器本来就是**唯一的访问入口**：`foundSmartInterfaces`（`TileMultiblockMachineController:135`）把每个接口登记为自己绑定的机械，`checkAndAddSmartInterface`（`:909-938`）写值，需求取值走 `getSmartInterfaceData(String)`（`:1113`）/ `getSmartInterfaceDataList()`（`:1128`），而旧版**唯一**读该值的消费者 `RequirementInterfaceNumInput` 拿到的也是控制器的 `ProcessingComponent`。**因此把值从「方块实体」搬到「控制器方块实体」、把界面从「独立界面」搬到「控制器界面」，访问路径一个字都不用改**——消失的只是一个中间方块。

**落地形态（三件套，缺一即空壳）。**

1. **机器定义的接口类型声明** —— 新根字段 `smart-interfaces`，**本项目 schema 的第四处偏离**（D12 之后）。**旧版在 JSON 里根本没有入口**：类型只由 CraftTweaker 注册（`MachineModifier.addSmartInterfaceType:27-38`、`MachineBuilder.addSmartInterfaceType:337-341`），`DynamicMachine.smartInterfaces` 的 `DynamicMachinePreDeserializer` 里一字未提。本项目走数据包（D3/D9/D10）+ KubeJS（D7），没有脚本可用，所以字段是必需的。形状与默认值：

   | 字段 | 类型 | 缺省 | 语义 | 旧版对应 |
   |---|---|---|---|---|
   | `type` | 字符串 | **必填** | 类型名，机器内唯一；需求按它取值 | `SmartInterfaceType#type`（旧版是 `Map` 的键，故也必须唯一） |
   | `default` | 数字 | `0` | 机器成型后、玩家未编辑时的值 | `SmartInterfaceType#defaultValue` |
   | `priority` | 整数 | `0` | 未指定的值绑定到哪个声明；大者胜（旧版 `Comparable` 反过来排，故 `priority` 大者在前） | `SmartInterfaceType#priority` |
   | `header` / `footer` | 字符串 | `""` | 值行上/下方的翻译键或字面量 | `headerInfo` / `footerInfo` |
   | `value` | 字符串 | 空 | 值行的 `String.format` 模板；空或不可格式化时回落 | `valueInfo`（旧版在 `IllegalFormatException` 时回落，本项目同样回落） |
   | `notequal` | 字符串 | 空 | 该类型自己的「数值不符」文案；空则用旧版默认键 | `notEqualMessage` |

   校验一律**响亮**（D12 的「定义文件由人书写」同一条理由）：不是数组、缺 `type`、`type` 为空、`type` 重复、`default`/`priority` 非数字、三个文案字段非字符串——逐条报错并说明该写成什么。

2. **`interface_number_input` 需求类型**（消费者）—— 旧版 112 行 `RequirementInterfaceNumInput` 的等价物，落在 `recipe/InterfaceNumberInputRequirement`，JSON 读取单独放在 `recipe/InterfaceNumberInputParser`（不持有 `DeferredRegister`，因此可离机驱动）。语义与旧版逐条相同：**不消耗资源，只做闸门**，`value >= min && value <= max`（两端**含**，旧版 `:82` 就是这个比较），查询不到类型时报 `component.missing.modularmachinery.interface.number`，数值不符时报 `craftcheck.failure.interface.number.notequal` 或类型自己的 `notequal`——三个键**逐字**沿用旧版文案。并行上照旧版：该类**没有**实现 `ComponentRequirement.Parallelizable`，所以 `getMaxParallelism` 直接跳过它，一份值只校验一次；修改器也碰不到它（`minValue`/`maxValue` 原样来自配方文件）。

   **一处必须记下的旧版事实**：旧版的 JSON 读取**从来产生不了这个需求**——`RequirementTypeInterfaceNumInput#createRequirement` 返回 `null`（`:9-11`），只有 CraftTweaker 桥（`RecipePrimer#addSmartInterfaceDataInput`）能造出它。原因是字段名撞车：接口类型名在旧版 schema 里也叫 `type`，与需求的种类判别字段同名。本项目先读种类再读 `interface` 字段，撞车因此不可能发生。这是**本项目第一次让它能从 JSON 出现**，不是照抄。

3. **值的存放与编辑界面** —— 值存在控制器方块实体上（`machine/SmartInterfaceStore`，**纯逻辑、无 `Level`**，因此可离机断言），编辑在控制器界面里（`MachineControllerScreen` 的 0.72 缩放文本块里加一行值 + 一个 `EditBox`，回车提交，走一个新网络包头 `SmartInterfaceUpdatePacket`：类型名是字符串，菜单的按钮通道装不下）。`SmartInterfaceStore#bind` 是旧版 `checkAndAddSmartInterface` 的投影：给未赋值的已声明类型填默认值、丢掉当前机器不再声明的类型（旧版同一处 `smartInterface.removeMachineData(realPos)`）。**访问路径未变**：控制器实现 `machine.SmartInterfaceValueSource`，`HatchCollection` 把它连同当前定义一起带进配方生命周期，需求读 `ports.smartInterfaceValue(type)`——即旧版 `需求 → 控制器 → 值` 这条链，只是中间那个方块没了。

**界面并入后保留了什么、去掉了什么**（设计文档的对照表，逐条实现）：

| 原版独立界面 | 本项目 |
|---|---|
| 标题「智能数据接口（已绑定：%s，当前：%s）」 | **去掉**。控制器只有一台机器（就是它自己），标题里的「已绑定/当前」两个数没有第二个取值 |
| 「上一个 / 下一个」 | **去掉**——合并带来的简化本身就是它 |
| 「当前值：%.0f」+ 输入框 | **保留**（`gui.modular_machinery_reborn.smartinterface.value` 逐字照旧版 `gui.smartinterface.value`），再加类型名（否则玩家看不出在编辑哪个声明） |
| 「未找到绑定机械。」 | **不再需要**（控制器必然知道自己是谁），连语言键都不加；复现器直接断言该键**不存在** |

**有意不做字符串类型，且这是有证据的决定。** 设计文档要求先确认字符串类型的消费者是否存在。证据链：① 旧版的方块枚举 `SmartInterfaceTypeEnum` **只声明了 `NUMBER`**（12 行，`enum SmartInterfaceTypeEnum { NUMBER; }`）；② 旧版里读接口值的**唯一**地方是 `RequirementInterfaceNumInput`，它的两个字段是 `float minValue` / `float maxValue`，对字符串没有意义；③ 全仓库对 `getSmartInterfaceData` / `getSmartInterfaceDataList` 的调用点只有接口声明（`IMachineController:213,221`）与旧版自身，没有第二个消费者。因此**不做字符串变体**并如实记录。旧版那两张 `blocksmartinterface_string` 模型/贴图与 `tile.modularmachinery.blocksmartinterface.string.name` 键是**死资源**（枚举里没有 `STRING`，`getSubBlocks` 只遍历枚举值）。

**没有采纳的退路**：把独立方块照搬过来。否决理由就是决定本身——它的存在意义只是「站在结构里让控制器找到它」，而控制器已经能直接找到自己；照搬会多出一次方块注册、一次结构扫描、一份 `boundData` 的每 20 tick 对账，却不多任何能力。

**配置：只加一个键，用于「说还是不说」。** `smart-interface.enable-smart-interface-bydefault`（默认 `false`）只决定加载器是否为「没有声明任何接口类型的机器」打印一句提示。**它不能决定机器是否能用接口**——那由机器自己的 `smart-interfaces` 声明决定，与旧版 `DynamicMachine#smartInterfaceTypesIsEmpty` 门住 `checkAndAddSmartInterface` 是同一条。**没有第二个配置类、没有第二次 `registerConfig`**（0.21.0 的事故不允许）；键是**平铺的字面量路径**，复现器仍然**从渲染出的 spec 里读回路径**来断言。

**验收**：复现器 **503 PASS / 0 FAIL**（0.23.0 的 352 项一项未删，M6d-b 新增 S/S2/S3/S4 共 151 项）。断言的是**真的读到了那个数、真的因为超出范围而拒绝开工、改回范围内同一条配方真的跑完并移动了物品**，不是「界面上出现了一个数字」。**看不到像素**：控制器界面里那一行与输入框的实际观感、回车提交的真实收发、客户端 update tag 的到达，全部未实机验证。

### D17（已实施 · 0.25.0）`failure-action` 消费：接到 0.24.0 已有的失败点上，不为它改状态机

**这条记录兑现的是 `docs/剩余项清点.md` §2 的 M1/M2 剩余项**（「`failure-action` 只解析不消费」，依据 L577 / L599），也是第 1 波的第 1 项。

**旧版语义（逐行）**：字段是**机器级根字符串**，取值 `reset` / `still` / `decrease`（`RecipeFailureActions.java:15-18`），在 `DynamicMachinePreDeserializer.java:44-51` 解析、由 `DynamicMachine.java:630-633` 存进机器（字段在 `AbstractMachine.java:29`，getter/setter `:35-41`）。**唯一的消费者**是**已经开始**的配方的**某一 tick IO 检查失败**：`ActiveMachineRecipe#tick:87-98` 在 `RecipeCraftingContext#ioTick:238-298` 失败时调用 `doFailureAction`，而 `doFailureAction:106-115` 就是全部效果——`reset` → `tick = 0`、`decrease` → `tick--`（仅在 `tick > 0` 时）、`still` → 什么都不做。因此它**每失败一 tick 生效一次**，**不是**每失败一个需求一次，也**不是**一次失败起始一次；字段属于**机器**，不属于配方；工厂线程 tick 的是同一个 `ActiveMachineRecipe`（`RecipeThread#onTick:54-62`），所以两条路径都受它管。**起始失败**（`canStartCrafting` 为假）与**产物放不下**（`RecipeThread#onFinished:64-86` 的 `canFinishCrafting`）**都到不了它**。缺省值不是 `reset`：`AbstractMachine.java:29` 取的是 `RecipeFailureActions.getDefaultAction()`，而 `loadFromConfig:38-46`（由 `Config.java:69` 调用）从配置键 `general.default-failure-actions` 读取，**缺省 `still`**。

**落地形态（连接，不是新机制）**：0.24.0 已经把「哪个需求拒绝了开工」（`MachineRequirement#startFailure` / `MachineRecipe#startFailure`）接到控制器上，但 `failure-action` 的消费点**不在那里**——`progress == 0` 时三种取值完全同效（没有进度可减、已经就是 0），起始失败路径根本没有可作用的对象。本项目**本来就有**两处等价的失败点，且两处此前都表现为「保持进度」（即 `still`）：

| 路径 | 位置 | 0.25.0 之前 | 现在 |
|---|---|---|---|
| 单配方 | `MachineControllerBlockEntity#tick` 的 `!recipe.canTick(...)` 分支（:434 附近） | 保持进度 | 调 `applyFailureAction()` |
| 工厂线程 | `FactoryEngine#tickThread` 的同一判断（:378 附近） | 保持进度 | 用 `host.failureAction()` 作用到 `ActiveCraft#setProgress` |

- 纯算术落在枚举上：`FailureAction#afterFailedTick(int)` 就是 `doFailureAction` 的三个分支，可离机驱动。
- 机器取值走既有查找：控制器侧 `MachineRegistry.byId(machineId).map(MachineDefinition::failureAction).orElse(DEFAULT_FAILURE_ACTION)`（原版的 `ctrl.getFoundMachine().getFailureAction()`），工厂侧经 `FactoryHost#failureAction()` 取得——与既有的 `maxThreads()` 同一条管线，因为引擎故意不认识 `Level` 与机器定义。
- **缺省 `STILL`**（`MachineDefinition.DEFAULT_FAILURE_ACTION`）：与旧版配置键的缺省一致，也恰好等于本项目此前在两条失败点上的实际行为，因此**不声明该字段的机器行为一字不变**。旧版那个全局配置键**没有**移植成配置键：本项目只有一个 spec、一次 `registerConfig`（0.21.0 的事故），想要别的取值就在机器自己的定义里写。

**唯一的有意偏离（已如实登记）**：旧版把 `tick` 归零后**配方仍是激活的**，所以 `reset` 只损失时间、**不会二次扣材料**。本项目单配方引擎里 `progress == 0` 就是「没有配方」——`MachineControllerBlockEntity#tick:392` 的开工门就架在它上面，而开工才会扣一次性输入——于是 `reset` 会结束该配方，并在下一次开工时**重新扣一次一次性输入**。要做到「零进度仍激活」得把「是否已开工」与「进度」分开表示，那是改状态机而非消费本字段，故**不做**，并在复现器里把实际行为断言下来（而不是留白）。工厂线程由槽位（`active != null`）决定是否激活，因此它**保持激活**，与旧版一致。

**校验一律响亮**（D12/D16 同一条理由：定义文件由人书写）：非字符串（数字 / 对象 / 数组 / `null` / `true`）与未知名字都被拒绝，并逐字告诉作者该写什么（三个取值、缺省是 `still`、以及每个取值的含义）。旧版只拒绝非字符串，且消息说的是取值表而不是类型；**未知名字会被静默地当成缺省值**（`getFailureAction(String):49-56`），本次改为报错——与 `parallelizable` / `max-threads` 等字段的约定一致。

**验收**：复现器新增 **W 节 42 项**（0.24.5 的 663 项一项未删）。断言的是：三种取值经**加载器自己的读取器**读回、缺省是 `STILL`、六种畸形值各自被拒且消息里带「该写成什么」、`afterFailedTick` 在 0/1/5/64 上的取值、**控制器**（免构造实例化后驱动生产方法，含「机器不在注册表里」与「没有机器 id」两条回落）与**真工厂引擎**（内存端口，饿掉每 tick 能源后按 `still`/`decrease`/`reset` 分别读回进度 3/0/0，并断言配方仍激活、一次性输入**只扣一次**、能源恢复后照样产出）三层的实际行为，以及两条边界：**永不失败的机器三种取值表现完全相同**、**产物放不下时保持进度（连 `reset` 也不例外）**。**红先行**：先写断言并跑出 **678 PASS / 24 FAIL**，再实现。两次源码级故障注入见 `迁移日志.md`。**看不到像素**：进度条的观感与「失败时界面表现」仍需眼睛，清单见发布目录 README。

**四处登记在案的翻译（其余逐字复刻）。**

1. **`canSendCommands` → `hasPermissions(2)`。** 旧版这个钩子的**方法体在本机不可得**（没有 1.12.2 反编译件），没有臆造：取 1.20.1 自己的同义物——标准命令权限等级 2（`Entity#hasPermissions(int)`，`javap` 实证存在）。两种可能读法（op 名单成员 / 等级 2 权限）对**创造模式里的普通 OP**都返回 `true`，而那正是这件工具的目标场景。**若所有者要求严格对齐旧版语义，需要 1.12.2 源码**。
2. **门拒绝时返回 `PASS` 而不是 `SUCCESS`。** 1.20.1 在方块之前问物品（`PlayerInteractionManager#useItemOn`），所以无条件返回成功会让**生存玩家打不开控制器自己的界面**——而 1.12.2 先问方块，不会。用 `PASS` 拒绝才保住了旧版的**实际**行为。
3. **三行日志（旧版没有）**：写出后提示这个文件是**片段**、下一步是把它 `parts` 并进一份带 `registryname` 的定义；跳过位置时警告并给出计数；片段很大时警告。**只警告、不拒绝**，文件字节与旧版一致。（所有者 0.29.0 指示：日志提示不算 schema 偏离，改写文件才算。）
4. **未加载区块里的坐标被跳过并计数**（有意偏离）。旧版 `world.getBlockState(pos)` 在 1.20.1 会**加载区块**（`Level#getChunkAt`，服务端线程上）；本项目结构匹配已明确不这么做（`MachinePattern.matches` 用 `isLoaded` 守卫），因此这类坐标**跳过并写进日志**，而不是被读成空气——一份在某个坐标写着 `minecraft:air` 的定义看起来像是故意的。

**一处按 1.20.1 语义翻译的描述符**：旧版写 `ns:block@meta`（`:422-424`，meta 即整个状态）。1.20.1 没有 meta，故「当时那个状态」的忠实对应物是**全属性具名**：`ns:block[facing=north,…]`，属性按**名字排序**（文件跨版本稳定），NBT 的键也排序（`CompoundTag` 是 `HashMap`，顺序本就未定义）。这正是本项目 `BlockMatcher` 读的语法，所以工具的产出**能被数据包用的同一套 schema 读进去**（复现器 AA4 断言：先被加载器**按名下拒绝**——`Missing required field 'registryname'`——补上 `registryname` 后被接受且每个 part 只接受当时那个状态）。

**验收**：复现器新增 **AA 节**（全量 1042 → **1171** 项；其中 0.28.2 的 1042 项一项未删，3 项已知环境性 FAIL 照旧）。
**红先行**：断言先用 `Class.forName` 写出，**实现前编译通过而断言失败**（`SUMMARY: 1042 PASS / 24 FAIL (1066 checks)`，24 条红逐条点名缺失的类与缺失的语言键；绿为 `1168 PASS / 3 FAIL (1171 checks)`）。
**五次故障注入**各自留下带 `SUMMARY` 行的证据文件：A 丢掉旋转变换（9 FAIL）、B 切换只加不删（8 FAIL）、C 门丢掉命令权限（6 FAIL）、D 描述符丢掉属性（5 FAIL）、E 重名计数从 1 起（5 FAIL）。
**其中两条红是断言自己写错**（AA 头两条红）：一条把「空片段」的收尾 `    ]}` 写成 `    ]\n}`（旧版 `BlockArray.java:440-441` 两行相邻、无换行），一条把「坐标是否被移除」用**文本搜索 `y:`** 判断，而 `energy:` 里就含 `y:`——两处都是**断言错、代码对**，已改正。

**证不了的（必须实机）**：点在哪、高亮长什么样、运行时文件落在哪个目录、中文提示的观感。清单见 `交接文档.md` 的 0.29.0 一节。

## 5. 验收总则

**可以作为完成证据**：可演示的行为、可自动化断言、与旧版的逐项对照表、截图比对。

**不可作为完成证据**（旧方案的问题所在）：
- 对象已注册 / 创造栏可见
- 贴图文件存在或有模型
- 有物品名或占位 GUI
- 代码「已加入」但没有可触发路径

**每个里程碑必须交付**：变更说明、构建结果、SHA-256、验收证据、以及本里程碑仍未覆盖的缺口清单（写入 `迁移日志.md`）。

**验收断言必须按运行时真实解析结果计算**：例如语言键检查要用 `Item.getDescriptionId()` / `Block.getDescriptionId()` 的实际解析值，而不是物品或方块的注册名。`BlockItem.getDescriptionId()` 返回方块 ID、Forge 扩展方法可能改变解析链——凡「按注册名推断」的断言都可能在游戏内失效（M0 已因此漏检一次）。同理，涉及覆盖点、事件时序、能力查询的断言都要以源码/字节码为准。
