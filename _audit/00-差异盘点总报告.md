## 1. 一句话结论

**已经迁移的是「外壳」——注册名映射、贴图素材、一个最小的加工闭环；没有迁移的是「这个模组之所以是它自己」的部分——数据驱动的机器定义层、需求/组件配方引擎、结构预览与蓝图工具链、升级与并行体系、以及全部模组联动。**

新版目前是一个**能跑通单配方的最小可玩原型**，而不是一个覆盖旧版功能的移植版。这本身不是错误（`移植计划.md` 开篇就写明是「保留玩法概念、重新实现」而非逐行改名），但**计划文件把阶段 1、阶段 2 标为「已完成 / 第一版已完成」，会让下一位接手者显著低估真实缺口**。

## 3. 五个必须知道的结论

### 3.1 旧版根本没有「等级仓口方块」，新版 48 个等级方块是自创设计

旧版每个仓口家族只有 **1 个方块**，等级由 `PropertyEnum("size")` 状态 + 物品 metadata 变体表达，资源层只体现为多张 overlay 贴图：

- `ItemBusSize.java:22-28`：TINY(1) SMALL(4) NORMAL(6) REINFORCED(9) BIG(12) HUGE(16) LUDICROUS(32) —— **7 级，无 ULTIMATE**
- `FluidHatchSize.java:27-34`：8 级，含 VACUUM
- `EnergyHatchData.java:33-40`：8 级，含 ULTIMATE

三条独立证据链互相印证：blockstate 变体数（`blockinputbus.json` 只有 7 个 `size=`）、overlay 贴图数（`overlay_inputbus_*.png` 只有 7 张，**无 ultimate**；`overlay_energyinputhatch_ultimate.png` 存在）、语言键数（`tile.modularmachinery.blockinputbus.*` 7 个）。

新版 `ModBlocks.java:29` 的 `TIERS` 是 8 个且含 `ultimate`，并用在了物品输入/输出仓口上——**制造出旧版从未存在的两个等级**。这直接解释了 0.4.3 为何要用荒谬级贴图顶替：那是在补自己引入的缺口。

### 3.2 旧版 `redstonesignal` 是死资源，`wrench` 无注册；新版把两者做成了物品

全量检索旧版 `src`：`redstonesignal` **零命中**（贴图存在但无人引用）；`wrench` 仅命中 `models/item/itemconstructtool.json:4` 的贴图引用，**无 Java 注册**。旧版 `RegistryItems.java:44-47` 只注册 4 个物品。新版把两者注册为可获取物品（`ModItems.java:16-17`）属于**新增内容**，迁移日志中「额外注册旧资源中存在的」这一表述本身没错，但读者容易误以为它们在旧版是可用物品。

### 3.3 模组的核心身份——数据驱动的机器定义——没有迁移

旧版机器 JSON 有 **13 个根字段**，新版**全部无对应实现**（逐条行号见 [02-structure.md](02-structure.md)）：`registryname`、`localizedname`、`prefix`、`color`、`failure-action`、`requires-blueprint`、`has-factory`、`factory-only`、`hide-components-when-formed`、`controller-bounding-box`、`parts`、`modifiers`、`dynamic-patterns`。

新版「结构系统」的全部内容就是 `MachineStructure.java` 的 23 行：控制器同层 3×3 环去掉中心共 8 格，**Y 偏移写死为 0**。而旧版内置机器实测即需 3~5 层（`alloy_furnace` 3 层、`power_transformer` 32 个 parts 跨 y=−1..3 共 5 层），`assembly_line` 更是一条长度可伸缩 **5~15 格**的产线。

同时，旧版的六种结构表达机制——`ns:block@meta` 描述符、`*.var.json` 变量集、`selector-tag`、`nbt`/`preview-nbt` 匹配、`modifiers` 方块替换、`dynamic-patterns` 伸缩结构——**无一在新版有对应实现**。新版已用 grep 确认不存在任何 ReloadListener / ResourceManager / 机器 JSON 加载代码。

### 3.4 新版仓口是占位壳，且结构判定不接受等级仓口

`ModBlocks.java:53-54` 只注册了 `machine_controller` 一个 BlockEntityType。53 个方块中 52 个是无能力、无库存、无等级数值的装饰壳（`MachineHatchBlock.java:13-19` 只有一个右键提示）。

更关键的是 `MachineStructure.java:17-22` 的白名单只认 5 种方块：铁块 + 4 个**无等级基础仓口**。这意味着：

- 放进 48 个等级仓口中的任何一个，**结构不会成型**
- `energy_output_hatch` 与 `fluid_output_hatch` 连无等级版本都没注册（`ModBlocks.java:36,40`），也不被接受

等级仓口目前的功能等价于装饰方块。

### 3.5 发现一个真实缺陷：输出槽满时持续销毁输入与能量

`MachineControllerBlockEntity.java:56-62`：

```java
if (be.progress >= be.maxProgress) {
    be.energy.extractEnergy(recipe.energy(), false);   // 扣能源
    be.items.extractItem(0, 1, false);                 // 扣输入
    ItemStack remainder = be.items.insertItem(1, result, false);
    if (!remainder.isEmpty()) be.progress = be.maxProgress;  // 产物放不下 → 停在“满”
    else be.progress = 0;
}
```

产物放不下时把 `progress` 设为 `maxProgress`，下一 tick `progress++` 即 `> maxProgress`，条件再次成立——**在输出槽被占满的期间，每 tick 反复扣掉 1 个输入物品和一份能量，却不产出任何东西**。这是资源凭空销毁，不是「卡住等待」。

修复方向（仅建议，本次未改动代码）：产物插入失败时应把 `progress` 夹到 `maxProgress - 1`（或改判 `insertItem` 返回值再决定是否扣除），并把扣除动作放到「确认能产出」之后。

## 5. 设计差异（新版自创 / 语义改变 / 旧有新无）

按影响排序：

1. **等级表达方式**：单方块多变体 → 48 个独立方块。注册表膨胀约 10 倍，且旧版机器 JSON/存档里的 `blockinputbus@0` 描述符在新版完全无对应物。
2. **资源容器归属反转**：旧版各仓口是带能力与容量等级的 TileEntity，控制器按结构收集；新版全部塞进控制器本体并直接对外暴露能力，仓口退化为装饰。
3. **「机器」降级为配方字符串**：旧版机器是注册进 `MachineRegistry` 的独立对象；新版控制器硬编码比对 `"basic"` / `"machine_controller"`。
4. **脚本技术栈整体替换**：旧版 63 处 `@ZenClass` 的 CraftTweaker API → 新版 16 行 KubeJS 桥、1 个 schema、5 个字段。旧版全树无 KubeJS 入口，**KubeJS 支持是新版自创**。
5. **JEI 类别模型退化**：旧版「每机器动态类别 + 结构预览 + 自定义 ingredient」→ 新版全局单类别两个槽位。
6. **GUI 实现路径反转**：新版改为纯程序化 `g.fill` 绘制；已拷贝的 `controller_legacy.png` 与旧贴图字节一致却**零引用**，23 张旧 GUI 贴图只剩 1 张。
7. **i18n 纪律回退**：`MachineControllerScreen.java:42-44` 硬编码中文「结构未形成」「能源 」「进度 」，而语言文件已就绪却未使用。
8. **命名空间与目录约定变化**：`modularmachinery`/`textures/items` → `modular_machinery_reborn`/`textures/item`，按旧路径查找新版资产必然失败。

## 6. 建议的下一步优先级

按「恢复模组身份」的收益排序，而不是按现有阶段编号：

1. **先修 3.5 的资源销毁缺陷**——这是当前唯一的破坏性逻辑错误，一行级修复。
2. **补端口能力层（原计划阶段 3）**——但需一并修 `MachineStructure` 白名单，否则等级仓口永远无法参与结构。
3. **重定义等级模型再谈能力**——先决定是沿用旧版「单方块 + 状态枚举」还是保留新版「一方块一等级」。这个决定会影响机器 JSON schema、存档兼容与注册表规模，越晚改代价越大；同时应处理新版自创的 `ultimate` 等级缺口。
4. **再实现机器定义层**——这是模组身份所在。最小可用版本应包含：`registryname` / `localizedname` / `parts[]`（含 `@meta` 与变量引用）/ `failure-action` / `requires-blueprint`；`modifiers` 与 `dynamic-patterns` 可后置。
5. **最后才补 GUI 与预览工具链**——旧版 4730 行动态 GUI 框架与 847 行预览渲染器不可能原样搬运，需要在 1.20.1 侧重新设计，属最大工作量项。
6. **同步修正文档口径**：`移植计划.md` 的阶段状态应区分「重实现」与「迁移」，并明确 48 个等级仓口与 KubeJS 是新版自创，避免后续接手者误判进度。
